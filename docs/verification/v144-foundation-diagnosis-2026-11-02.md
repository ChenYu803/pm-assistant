## 三处失配

### 1. 已实际复现：旧按钮名不存在

原 scripts/verify-v141-replay-foundation-scenario.mjs 第 165、178、186 行仍定位“开始本阶段工作”；当前 src/components/ProductIterationWorkbench.tsx 第 677 行为“新建会话，开始这一阶段”。新按钮仍调用 createSession，双端实际创建和持久化均成功。

原来 20 秒的超时并不是“系统还没准备好”，而是在等一个已被改名的元素；加长超时不会解决它。

### 2. 已实际复现：把 SSE 整包当 JSON

原场景 mutation 辅助函数第 27–32 行对所有修改请求统一执行 response.json()，第 212 行用它观察浏览器发送首条消息。

当前工作台 streamGeneration（第 137–138 行）发送 Accept: text/event-stream；对应 messages/route.ts 第 56–60 行按 Accept 返回 SSE 或兼容 JSON。原脚本因此收到正常 HTTP 200 的 event: token ... 数据后，报 Unexpected token 'e', "event: tok"... is not valid JSON。

这次失败来自测试解析器，不是服务端返回非法 JSON：服务端本来就没有承诺这条流式请求返回整包 JSON。临时对照已实际走到此处，并已通过阶段跳转、零写入完成、刷新锁定与重新打开等前序断言。

### 3. 正式流构造器已证实、后续浏览器步骤未跑到：停止状态分层不同

原场景第 235–237 行等待停止操作后，要求最初发送请求的 HTTP 状态为 409。当前 SSE 响应在开始传输时为 HTTP 200，最终业务状态放在 result 事件内。例如停止结果为 result 事件 data 中的 status=409，而不是把已经开始的 HTTP 200 改成 409。

最小协议实验实际得到 HTTP 200、Content-Type=text/event-stream、result 事件负载 status=409。本次没有继续改动临时场景来运行后面的停止操作，因此这是基于正式协议的确定性不兼容证据，不冒充第三次浏览器失败记录。

## 解决的真正难点

- **跨层假设一起变了，不只是替换文案。** UI 定位、消息传输格式、业务终态观察必须同时对齐。只修改三处按钮名不足以让旧脚本正确验证当前版本。
- **流开始不等于生成完成。** HTTP 200、收到 token、出现回复内容，都不能替代 result 终态和刷新后的持久结果；停止还应验证保留正文、failed/已停止状态及生成锁释放。现有业务断言不能为求通过而删除。
- **串行长场景遮住后续问题。** 旧脚本遇到首个异常便结束，甚至还没进入手机轮次。排除前一层后才暴露下一层，容易被误判为同一个功能反复修不好；应先收敛反馈环，再做一次完整流程验收。
- **隔离环境有固定启动成本，但并非无解的技术障碍。** 两次实验均约一分钟，说明可以快速定位。共享文件树、上下文隔离和中止生成后的后半程尚未全部重新验收，不能估计只需改几行就宣告完成。

总体判断：当前已知修复更像局部的测试维护，尚无证据要求重构产品架构；完整验收的工作量高于改按钮文案。用户若后续授权，优先适配测试的流式等待与终态断言，保留实际业务断言后再运行双端原流程，而不是退回旧 UI、强迫浏览器使用 JSON 或增加超时。
