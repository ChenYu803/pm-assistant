# v1.44 人工充值入账契约

## 业务入口

- 用户：个人中心 → 获取积分 / 联系充值（`/profile/recharge`）。账号 ID 来自登录会话与实时账号检查，不能在 URL 指定其他人。
- 管理员：用户管理 → 选定账号 → 账号积分 → 人工充值入账；充值记录位于 `/admin/recharges`。
- 页面与 `GET/POST /api/admin/recharges` 都独立验证指定管理员；写事务内再次锁定并复查操作者状态。普通用户没有购买积分发放接口。
- 人民币为最多两位小数的十进制字符串，单笔大于 0 且不超过 999999999.99 元；购买积分精确为实收 × 1000，不接受客户端发放积分、赠送或补偿类型。
- 交易参考号支持 1–128 位 ASCII 字母、数字及 `._:-`，去首尾空白、转大写。核验同一转账须始终使用同一参考号，不以大小写创建新转账。

## 资金与幂等

- 使用既有 0026 账本，无新增迁移。所有写入沿用 `lockCreditUsers`（账号 ID 排序），与赠送、预留、结算及退款的账号锁互斥。
- `credit_sources.business_type = manual_recharge`，`business_reference = 规范参考号`；既有唯一索引跨账号、跨管理员防重，不依赖应用进程内锁。
- 来源保存 `original_credits/available/reserved/paid_rmb`；来源及账本 `context_snapshot` 保存 `entryId/receiptReference/originalPaidRmb`。
- 账本 `manual_recharge` 保存操作者、账号、requestId、说明、时间、金额、完整前后余额和来源 allocations。来源与审计同事务提交；失败全部回滚，赠送与既有预留不变。
- 同一操作 ID 或同一参考号、相同账号/金额/说明返回原流水 `replayed=true`；不同内容返回 409 与 `existing` 原交易，管理员可核对原账号、实收和流水 ID。
- 只有已明确回滚的唯一键竞争/死锁最多重试两次；连接失败或提交响应未知不生成新操作。页面发送前保存账号隔离的 sessionStorage 草稿，30 秒请求超时、网络/5xx 或无法解析响应时保留原 ID 和内容，刷新后只能重试同一笔。已有待确认操作即使重试被 4xx 拒绝也保留；成功响应须核对原账号、参考号、实付、积分、业务说明及余额变化，凭据不完整或不一致时继续等待核对，不能先清草稿后解析结果。
- 后台余额与用户余额均读取统一账本；充值筛选支持完整账号 ID、完整邮箱或完整参考号，每页 20 笔，不将赠送/补偿混入实收充值。

## 给 #12 的退款交接

通过原充值流水 `allocations[].sourceId` 定位购买来源，读取 `paid_rmb` 与 `original_credits`；或由来源 context.entryId 回到原账本。不得假设所有来源的 business_reference 都是账本 ID，本票该字段承载全局唯一参考号。后续可退数量应以原购买来源剩余可用、未预留部分和已退实付计算；本票不执行退款、不接在线收款回调、不模拟真实收款。

## 上线输入与证据边界

`RECHARGE_WECHAT_CONTACT` 仅服务端环境读取；未填写或明显占位值时显示未开放与请勿转账。不把测试微信当真实渠道；发布前运营者必须补齐并核实真实微信，修改后重启应用。真实配置保存到仓库外受限运行环境，模板为空，不修改本机/生产凭据。

专项 `npm run verify:v144-manual-recharge` 仅随机隔离库、本机正式 HTTP 与浏览器，已知测试实收不代表真实用户转账或目标机验收。验证记录见 docs/verification/v144-manual-recharge.md。
