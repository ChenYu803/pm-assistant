# v1.44 人工退款与恢复契约

## 入口与权限

- 管理员从用户管理 → 账号积分 → 发起人工退款选择原充值。来源每页 20 笔，展示原实付、原始购买积分、当前可用、模型预留、退款锁定与当前可退金额；提交时再次计算。
- 后台退款与恢复页 `/admin/refunds` 查询账号、邮箱、原充值 ID、退款 ID 或外部参考号，每页 20 笔。每个页面、GET/POST/PATCH 接口独立鉴权，写事务锁定并再次验证操作者的指定管理员身份和正常状态。
- 用户从个人中心查看自己的退款记录、业务结果与最终余额；`GET /api/refunds?page=N` 仅用会话账号，不接受指定他人账号。余额、最近退款及流水通过 `GET /api/credits` 同一一致性快照读取。

## 来源与金额守恒

新增迁移 `0032_v144_manual_refunds`，为购买来源增加 `refund_held`，新增持久 `credit_refunds`。默认值 0 保留既有来源和历史账本；不改既有迁移、不回填虚构资金事实。仅通过原人工充值流水与来源 `context.entryId` 的双向关系定位购买来源，不把账号总余额或 `business_reference` 当作原充值实付。

退款人民币为十进制字符串，以分为最小单位，每笔大于 0、最多 999999999.99 元；对应购买积分精确为退款元数 × 1000。可退人民币取「原来源可用积分 ÷ 1000」与「原实付减已完成或锁定退款」的较小值，向下取整到分；不足一分的剩余积分不多退。赠送、已消费、模型预留及已锁定部分不可退。

所有退款写入复用 `lockCreditUsers` 的排序账号锁，与充值、赠送、会话/润色预留、消费、释放及待核对恢复互斥。发起把购买来源 `available` 移到 `refund_held`；原模型 `reserved` 不变。数据库约束保持各字段非负且可用 + 模型预留 + 退款锁定不超过原始积分。后台与用户界面明确区分模型预留和退款锁定，不将退款占用混入模型调用总冻结。

## 外部事实与内部记账

| 业务阶段 | 外部转账状态 | 内部状态 | 资金动作 |
| --- | --- | --- | --- |
| 发起，结果待核实 | unverified | held | 从可用移入退款锁定 |
| 已核实外部退款成功 | succeeded | held | 单独持久保存外部参考号和核实说明，锁定不变 |
| 内部扣账完成 | succeeded | completed | 扣除退款锁定，不再次扣可用 |
| 已核实未转账或转账失败 | failed | released | 原子释放退款锁定到同一来源 |

`POST /api/admin/refunds` 只创建记录并锁定积分，系统不执行微信转账。外部操作前须核查原记录、收款方和实际转账结果。结果不明时保持待核实；不能因接口失败就再次转账，不能当作外部失败释放积分。

`PATCH /api/admin/refunds/[id]` 的 `confirm-transfer` 必须提供真实已核实的外部参考号与说明；先单独提交外部成功记录，再独立尝试内部扣账。内账写入、提交响应或授权复查失败，返回待查询/待记账提示，已保存外部成功事实和积分锁定不撤回。页面只提供 `complete`（仅重试内部记账），禁止引导再次转账。重新查询可能显示已完成，应以持久结果为准。

`mark-failed` 只在已核实外部未退款或失败时使用，说明必填。失败结果、释放和审计同事务；写入失败时原锁定保留。未核实记录也可在确认从未转账后按此流程结束，不能仅因等待太久自动释放。成功/失败外部事实一旦记录不可改写，终态不可再扣账或释放。

## 幂等、审计和未知响应

- 操作者 + requestId 复用 `credit_entries` 的管理员全局唯一身份，与赠送、充值互斥；同身份同内容返回原退款，不同内容或其他业务身份 409。同来源只能有一笔 held；相同内容以新身份命中原笔时，追加 `manual_refund_reference` 零变动审计，永久关联实际请求管理员、别名身份与原退款。原笔完成或释放后再重试别名，仍返回同一退款，不能新锁积分。不同内容 409 并提示先处理原记录。已完成部分退款后允许以全新身份发起真实新部分退款，受剩余额度约束。
- 外部参考号去空白、转大写并全局唯一；同一外部交易不能登记到两笔退款。重试核实必须与原外部状态、参考号和说明一致；complete 重试只返回唯一终态。
- 发起和别名审计使用客户端 requestId；阶段操作使用退款 ID + 阶段名，均保留全局唯一约束。发起、外部确认、内部完成和失败释放分别追加 `manual_refund_hold/transfer`、`manual_refund`、`manual_refund_release` 流水，保留实际阶段操作者、时间、说明、前后余额、原充值/来源和外部参考号。原充值和历史消费不改写。
- 两种表单发送前按管理员、账号/退款 ID 隔离保存在 sessionStorage；网络、30 秒超时、5xx、响应缺少一致凭据时保留原操作。已有待确认操作遭遇 4xx 也不能证明首次未提交，继续保留。只有首次明确拒绝且无历史未知提交时可解除草稿以修正输入。成功须核对原退款、金额、来源和阶段状态后清草稿。
- 页面查询到已确定的外部事实与旧待确认登记冲突时，展示原登记与最新状态，显式核对后解除本地旧草稿；成功且仍锁定时仅转入内部记账，完成或释放终态关闭旧登记。未知状态不可据此解除草稿，解除动作本身不写资金。
- 服务器重启不丢锁定和外部事实；可从后台查询与恢复，无需直接改数据库。数据库完全不可写时无法记录新增外部事实，但此前持久发起记录仍锁定该笔积分；恢复后先核实并登记原转账，不能重新转账。

## 迁移与证据边界

迁移只由既有初始化/部署流程追加应用；本票只在随机隔离库验证，不操作日常/生产账本或凭据。目标机迁移前按部署纪律备份源码、配置与数据库并核对可恢复副本，迁移与发布验证交由发布票。

运行 `npm run verify:v144-manual-refund-browser` 验证1440/390界面、未知响应及旧草稿恢复；`npm run verify:v144-manual-refund` 覆盖应用入口、已知金额、并发调用、故障和响应丢失；相关回归包含充值、积分、会话/润色结算、管理员及共享隔离运行器。验证证据见 docs/verification/v144-manual-refund.md；隔离转账事实是测试输入，不表示真实用户收付款或目标服务器验证。
