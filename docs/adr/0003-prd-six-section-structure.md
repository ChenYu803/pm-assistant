# ADR-0003 — PRD 结构重构为 AI 执行版六章骨架

MVP 的 prd.md 落地版采用「五维度」结构（用户流程/状态机/字段规范/文案规范/异常处理），是给人阅读的文档。ADR-0002 已定 PRD 读者是 AI（「只会执行的程序员」），「直接拿去 vibe coding」是字面要求。五维度结构对 AI 有四个缺口：缺页面清单（AI 不知道要建哪些 route、页面怎么连）、缺实体级数据模型（字段按功能散落而非按实体聚合，同一实体的字段散在多个功能里，AI 会读到矛盾或重复）、缺功能优先级/MVP 边界（AI 的「完成主义」会把排除项也做掉）、缺验收标准（AI 完成后无自检依据）；「文案规范」对 AI 零价值（无法执行的主观指导，占用注意力预算）。

**决策：prd.md 重构为六章骨架，细节见 `.scratch/prd-structure/ai-prd-structure.md`：**

1. **概念**——核心用户、要解决的一件事、产品形态、商业模式、外部依赖声明（如「支付走微信 SDK，不自研」——这是业务承诺不是技术决策，AI 读到正约束即可防自研）
2. **Out of Scope / 范围冻结**——排除项清单，每项附一句理由（叙事素材 + 显式边界）
3. **页面清单**——每页：目的 / 元素（结构非 UI 细节）/ 操作 / 入口·出口（导航图）/ 依赖声明；是任务拆分 Agent 的切分骨架
4. **实体级数据模型**——每实体：定义 / 字段表（业务级类型：引用/枚举/数字，非 DB 类型）/ 状态机（集中定义，是「比文字更精确」的决策编码）/ 关系；**字段单源定义**，其他章节引用
5. **用户流程 + 验收标准**——按用户故事组织（行为跨功能，不按功能切碎）；主路径 + 异常并入流程分支（不单独成章）；每条带验收标准（可验证行为契约：当 X → 系统 Y → 结果 Z，3~5 条）
6. **文案基调**——三行封顶：语气一句话 + 示例 1~2 个 + 命名约定（示例比抽象描述有效）

配套决策：

- **精简版 PRD 文档退役**：精简版的存在目的是流程控制（低成本方向确认防返工），保留为流程中的确认产物（三视角确认 → 概念版 ≤300 字 → 范围冻结，对话内完成，不落盘）；但不再作为章节写入 prd.md——双重身份（流程产物 + 文档章节）导致同一事实两处定义，破坏单源
- **Testing Decisions 维度不进 PRD**：「怎么测」是技术决策，按路线 A 划分留给 AI；第 5 章验收标准已覆盖「测什么」（业务语义）
- **外部依赖声明放概念章**：正面产品承诺（用什么）与范围章的「不做 X」（用户可见排除）语义不同；单源定义，「不自研」隐含在正约束中，范围章不重复
- **设计原则**：完备性（AI 需要的业务语义一字不少，不需要的一字不多）/ 单源事实 / 可定位（章节 = AI 检索单元，取用 O(1)）/ 显式边界（「不做 X」与「做 X」同等重要）/ 可验证（可验证表述替代主观描述）；另：**可切分性**（任务拆分 Agent 能可靠切分）是 PRD 质量的客观验收手段——切不动/切出重复 = 结构缺陷

**被否备选**：路线 B（PRD 写死数据模型/API 契约，AI 纯执行——见 ADR-0002，变技术设计文档）；五维度打补丁（缺页面的问题补不进功能维度里）；精简版继续写入文档（破坏单源）；保留 Testing Decisions（「怎么测」属技术决策，且 to-spec 的 Testing Decisions 服务于既有代码库场景，从零 vibe coding 无惯例可依赖）。

**后果**：PRD Agent system prompt 重构（原六步流程 → 新流程：二次确认 → 概念+范围 → 直接嵌入原型.md 的页面/流程 → 实体聚合 + 业务规则 grilling → 验收 → 文案基调 → 六章输出）；`%%%FILE_BEGIN%%%` / `%%%SCOPE_FROZEN%%%` 协议不变；prd.md 文件模板更新（六章 + changelog 头）；「可切分性」成为 PRD 质量的客观验收手段（v1.0 验收 = 作者拿真实 PRD + issues vibe coding 一次跑通，见 ADR-0004）。
