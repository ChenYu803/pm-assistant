## 备什么

| 内容 | 依据与备份方式 |
|---|---|
| 完整项目 MySQL 数据库 | 账号、项目、迭代/会话、聊天、成果文件、候选、任务集合、变更记录、原型 HTML 等在项目表中。导出完整项目库，包含表结构、数据和 schema_migrations；只下载成果 Markdown 不够 |
| 部署配置与必要密钥 | 加密保存生产环境变量、登录签名密钥、数据库连接配置、入口服务/站点配置、服务启动配置、软件版本、数据目录挂载与权限说明；不把真实密钥提交 Git |
| 可恢复的代码版本 | 保留已部署的 Git 提交号、对应源码、锁文件与部署说明，保存在自己的电脑或独立私有代码仓库，不能只在 VPS 上有源码 |
| 实际上传目录（如新增） | 当前核对的数据正文主要存在 MySQL；正式部署时清点额外持久化目录。以后增加图片/附件本地存储，必须把这些目录纳入备份 |

无需反复备份 node_modules、可重建的构建缓存和全部操作系统；恢复环境需要软件版本与配置。账号权限须在重建数据库后重新创建和验证，项目库导出本身不等于备份了 MySQL 系统账号。

## 推荐执行频率与位置

1. 每天北京时间凌晨执行一次完整项目库导出，将备份加密后上传独立厂商的私有对象存储。数据库导出工具应与实际 MySQL 版本匹配；InnoDB 可采用一致性事务导出，备份期间不并行做表结构迁移。不能把运行中的 MySQL 数据目录直接复制当作可靠备份。
2. 部署配置变化后立即加密备份；每次网站发布、数据库迁移或重要演示前另做一次数据库和配置备份，注明代码版本。
3. 异地存储保留最近 7 份每日备份和最近 4 份每周备份。使用时间戳对象名，周备份在相应窗口内也保留，避免每天覆盖唯一文件。保留清理必须在确认新备份已安全上传后执行。
4. 每周下载最近一次完整备份至个人电脑，至少保留两份不同日期的副本。加密解密口令或密钥独立保存在个人密码管理器/离线安全位置，不能只在 VPS 或同一个备份包中。
5. 自动任务记录导出/加密/上传退出状态，校验文件大小、解密解压完整性与 SHA-256；记录最后一次成功上传时间。连续超过 24 小时无成功异地备份，或任务失败时向本人发告警；通知渠道在部署时配置，不在本轮发消息。

预算极紧时可先每日导出后用 SFTP 下载到电脑，不增加云存储支出；这依赖电脑开机和人工执行，不能称为无人值守自动异地备份。更可靠的首发方案是自动上传对象存储，电脑副本作为补充；厂商不需要与 VPS 同家，且应使用独立账号。

对象存储按实际容量、请求、传输/恢复流量和地区计费，不必先买 100 GB 包，也不承诺固定月费。若每份压缩加密备份 100 MB，7 份日备份加 4 份周备份约 1.1 GB，尚不含每次发布备份。以账单为准，限制下载与共享，定期核对费用。

系统盘和数据盘在同一家 VPS 上，任一盘上的副本都不能抵御整机丢失或服务商消失。服务商快照可辅助快速恢复，但不能替代独立异地备份。备份包含用户数据和密钥，使用私有存储、加密及受限凭据；有条件时以版本保留/不可变策略及独立权限保护旧备份，避免服务器受侵后连历史备份一起被删除。

## 如何证明能恢复

首次备份完成后，在独立临时测试库中恢复，不能覆盖本机原库或线上正式库。恢复使用匹配的软件版本和同一份备份对应的代码，重新创建应用账号权限，验证登录、项目、聊天、成果文件与 HTML 原型的读取、数量和关键内容。测试环境禁用真实模型调用/通知等外部动作；未运行中的历史生成任务按应用恢复规则收口，备份不保证恢复正在生成的回答。

之后每月至少恢复一次；数据库结构大改后补一次。仅有 SQL 压缩包、文件校验成功或对象存储显示上传成功，均不能代替恢复验证。

整机丢失时的顺序：准备新机 → 安装匹配运行环境 → 拉取对应代码 → 恢复数据库、文件和加密配置 → 重建应用权限 → 使用测试入口验证 → 切换域名解析并配置 HTTPS。域名账号和解析控制权应由用户自己保管。

若每天一次备份且每次异地上传成功，通常仍可能丢失上次成功备份后的近 24 小时变更；任务失败会更久。若以后不能接受这段损失，再考虑每小时备份或 binlog 异地归档与时间点恢复。恢复网站仍需要新机和操作时间，备份不等于自动故障切换，也不保证供应商网络质量。
