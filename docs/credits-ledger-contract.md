# v1.44 积分来源与审计契约

#04 只实现管理员赠送、补偿、赠送余额纠正与查账。购买入账、兑换、预留结算和退款由后续工单实现；管理员正常模型调用也交给后续统一计费覆盖。

## 数值与余额

积分采用 DECIMAL(28,8)，服务端以 10^8 为单位的 bigint 计算，HTTP / JSON 使用十进制字符串。最多八位小数，超精度输入直接拒绝；显示保留全部有效小数，不改写真实余额。人民币来源字段采用 DECIMAL(28,8)，本票不写入实付。

credit_sources 是余额唯一事实来源：每个来源保留账号、赠送/购买类别、原始积分、可用积分、预留积分、原始实付、业务引用和必要上下文快照。账号两类余额分别汇总来源的 available / reserved；没有来源时为零，不补造历史。

## 写入与幂等

所有后续来源、兑换、预留、结算和退款写入，必须在同一 MySQL 事务内先通过 lockCreditUsers 按账号 ID 排序锁定 users 行，再锁定来源。禁止先锁来源再锁账号。来源更新、流水和业务记录同事务提交。

管理员操作以 actor_id + request_id 全局唯一。相同目标、类型、金额和原因重试返回原流水；同 key 改参数返回 409。失败回滚后可原 key 重试。客户端保留未确认请求，响应丢失时提供原样重试；确认成功后才生成下一操作身份。

管理员新增赠送或补偿产生 gift 来源；负向纠正仅扣 gift.available，不能动 reserved 或 purchased。购买类增减须由后续充值/退款入口核验原实付和原来源，不能借管理员调整伪造购买或损坏可退款依据。

## 审计与业务删除

credit_entries 追加保存稳定流水 ID、账号与操作者 ID/邮箱快照、业务类型、原因、请求标识、精确变动、来源分摊、前后两类余额和时间。context_snapshot 保存后续项目/会话稳定标识与名称快照，不保存对话或文件正文。流水、来源均不对项目、会话设置级联删除外键，业务对象删除后保留必要追溯信息。原始入账积分与实付金额不覆盖；后续消耗、纠正、退款通过新流水与来源分摊反映。

查询在同一只读一致性事务内返回余额、分页总数和流水。个人查询从会话身份确定账号，管理员逐接口服务端鉴权；不接受客户端指定个人查询目标。
