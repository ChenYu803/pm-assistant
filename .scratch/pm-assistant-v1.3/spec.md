# PM Assistant v1.3 — Spec

Status: ready-for-agent

> 本 spec 将 v1.3 grilling 已确认的产品决策转为实现契约。`Status` 是仓库内部 triage 元数据，不是交付给外部编程 AI 的 ticket 字段。

## Problem Statement

PM Assistant 当前使用 MongoDB。v1.2 已建立消息恢复、显式冻结、项目隔离、文件来源、tab 并发、级联删除和 tickets 版本交付等可观察行为，但这些行为与 Mongoose/MongoDB 的查询、条件更新、事务回退和文档结构深度耦合。

用户希望面向未来部署，把应用数据库切换为 MySQL Community Server。旧 MongoDB 数据对当前用户没有保留价值，因此不应为旧数据迁移增加额外复杂度；同时，数据库替换不能顺便删减或改变现有产品行为。

## Solution

v1.3 将 MySQL 作为 PM Assistant 的唯一应用数据库，使用本机 MySQL 9.7.2 LTS 作为第一验收环境。MySQL 从空数据库开始，按全新安装流程注册用户和创建项目；旧 MongoDB 数据不导入，MongoDB 原库不删除但不再是应用运行依赖，也不提供切回 MongoDB 的产品回退路径。

实现应把现有 MongoDB 持久化对象和行为转换为关系型数据结构，保留 v1.2 的外部契约：登录、四环流水线、消息状态与恢复、冻结两阶段、项目 ownership、文件来源、并发幂等、级联删除、自动命名和 tickets 版本交付。数据库初始化/升级通过可重复执行的项目命令完成，连接信息通过环境变量或本机配置提供；Workbench 可继续使用 `root`，应用使用仅服务本项目的专用连接身份。

## User Stories

### 安装与首次使用

1. 作为当前唯一用户，我想在空的 MySQL 数据库上直接看到正常注册页，以便不需要理解数据库初始化流程。
2. 作为新用户，我想注册后创建项目并进入现有工作流，以便空数据库仍然提供完整产品体验。
3. 作为用户，我不希望旧 MongoDB 账号、项目或聊天记录自动出现在 MySQL 中，以便新版本的数据边界清晰。
4. 作为维护者，我想重复执行数据库初始化/升级命令不会产生重复表、重复索引或破坏已有 MySQL 数据，以便本机和未来部署都能可靠准备环境。
5. 作为维护者，我想在开发环境重置项目数据库后重新从空库开始测试，以便不必手动删除多层关联数据；该能力不能在生产环境执行。
6. 作为维护者，我想通过配置提供数据库地址、端口、库名、连接身份和密码，以便换电脑或未来部署时不修改业务代码。
7. 作为用户，我想应用不依赖 Workbench 界面才能启动，以便数据库管理工具和网站职责分离。
8. 作为维护者，我想应用连接身份只拥有项目数据库所需权限，以便网站故障不会影响 MySQL 中的其他数据库；Workbench 仍可使用 `root`。

### 既有工作流兼容

9. 作为用户，我想正常注册、登录、退出和刷新会话，以便数据库替换不改变身份体验。
10. 作为用户，我想创建、查看、重命名和删除项目，以便项目边界与 v1.2 一致。
11. 作为用户，我想创建、查看、重命名和删除工作记录，以便工作记录仍然属于正确的项目。
12. 作为用户，我想创建多个 tab 并选择四类 Agent，以便需求分析、原型、PRD 和任务拆分流水线不受影响。
13. 作为用户，我想 Agent 上下文只加载当前项目允许的文件，以便 MySQL 关系查询不会引入跨项目数据。
14. 作为用户，我想正式文件、中间工作文档、HTML 快照和 tickets 继续遵守 v1.2 的可见性与加载边界，以便数据库替换不污染文件树。
15. 作为用户，我想消息按原有时间顺序和角色展示，以便对话阅读和 Agent 上下文保持一致。

### 消息、生成与冻结

16. 作为用户，我想开始生成时就建立正式 assistant 消息，以便停止、刷新和重连都能找到同一条消息。
17. 作为用户，我想看到生成中、完成、中断和失败等消息状态，以便知道结果是否可以继续使用。
18. 作为用户，我想零 token 失败仍保留失败消息，以便历史记录和重试语义不丢失。
19. 作为用户，我想重生成或编辑重发先成功生成新结果，再替换旧历史，以便失败不会删除旧回答。
20. 作为用户，我想停止生成后保留已经生成的部分并标记中断，以便内容不会静默丢失。
21. 作为用户，我想刷新或重连后每条 assistant 只显示一次，以便数据库状态和界面不会形成重复气泡。
22. 作为用户，我想 Agent 提议冻结时看到明确控件，普通聊天文字和历史消息不能触发冻结，以便不可逆操作只由我主动确认。
23. 作为用户，我想冻结经历“处理中 → 文档生成 → 文件写入确认 → 正式冻结”的阶段，以便每一步都可理解、可取消、可恢复。
24. 作为用户，我想重复点击冻结或网络重试不会重复生成或重复写入，以便操作结果稳定。
25. 作为用户，我想冻结生成失败、取消或刷新后能看到真实状态，以便可以重试而不误把范围视为已冻结。

### 一致性、并发与删除

26. 作为用户，我想同一 tab 的重复请求不会重复发送、写入或推进状态，以便网络重试不会制造重复成果。
27. 作为用户，我想多窗口同时修改同一 tab 时收到明确冲突提示，以便我手动决定下一步，不被静默覆盖。
28. 作为用户，我想自动命名不会覆盖我已经手动设置的工作记录名称，以便迟到的 AI 结果不改变我的决定。
29. 作为用户，我想删除项目时清理其工作记录、tab、消息、文件上下文、项目文件、快照和相关操作记录，以便不留下不可见残留。
30. 作为用户，我想删除工作记录时只清理其 tab、消息、文件上下文和操作记录，并保留项目级文件，以便 ownership 边界清楚。
31. 作为用户，我想删除失败时得到明确失败结果，重复发起清理不会造成额外副作用，以便可以安全重试。
32. 作为用户，我想删除后通过旧 URL 无法继续访问资源，以便物理删除结果可观察且一致。

### 故障与诊断

33. 作为用户，我想 MySQL 服务未启动、端口错误或连接配置失效时看到通俗的暂时不可用提示，以便知道操作没有成功。
34. 作为维护者，我想技术错误保留在日志或响应诊断信息中，以便可以把具体错误带回定位，而不把原始数据库报错直接暴露给用户。
35. 作为用户，我想 MySQL 瞬时断开时当前操作明确失败并可手动重试，以便系统不偷偷排队、无限重试或重复提交。
36. 作为维护者，我想 v1.3 不要求实际线上部署，但配置和数据库结构不能写死本机路径，以便未来可以部署到独立服务器。

### 迁移验收

37. 作为维护者，我想在 MySQL 空库上运行完整 v1.2 replay 综合入口，以便一次验证所有既有外部行为。
38. 作为维护者，我想 replay 入口在运行前确认使用固定回放模式，不调用真实模型，以便回归成本和结果可控。
39. 作为维护者，我想失败输出包含专项类别和可定位摘要，以便区分数据库连接、schema、业务行为和验证夹具问题。
40. 作为用户，我想从零完成注册 → 项目 → 工作记录 → 四环交付的人工冒烟，以便确认迁移后的产品仍能完成核心目标。
41. 作为维护者，我想验证 MySQL 中可观察的数据关联、唯一约束、版本和删除结果，以便“页面能打开”不被误认为迁移成功。
42. 作为维护者，我想明确记录 v1.3 只支持本机 MySQL 9.7.2 LTS 的第一验收结论和兼容性边界，以便未来部署不产生未经验证的承诺。

## Implementation Decisions

- **应用数据库**：所有生产应用读写从 MongoDB 切换到 MySQL；MongoDB 原库可以留在本机，但不再作为应用运行依赖，也不提供双写、数据回搬或切回路径。
- **旧数据**：不导入旧 MongoDB 数据，不补建旧账号；MySQL 以空库开始，按全新安装注册。
- **版本边界**：本机第一验收目标为 MySQL 9.7.2 LTS；实现应记录驱动/ORM 实际验证的兼容范围，不宣称任意 MySQL 版本均受支持。
- **关系模型**：现有 User、Project、WorkRecord、Tab、Message、ProjectFile、AgentFileContext、PrototypeSnapshot、TabOperation、MessageFileWrite 等持久化对象必须有可追溯的关系型表示；父子 ownership、组合唯一性、排序字段、状态字段、时间字段和消息自引用关系不得因转换而丢失。
- **标识符**：现有 API 和会话中的 MongoDB ObjectId 契约需要统一转换为 MySQL 可持久化且可安全序列化的标识符；前端可见 URL、请求参数和 ownership 校验必须保持一致，或提供完整兼容边界，不允许只改数据库后留下半套 ID 语义。
- **一致性**：MongoDB 中由条件更新、嵌入式许可、唯一索引、事务/补偿和集合复查提供的外部行为，迁移后必须由 MySQL 事务、行级条件更新、唯一约束、外键/应用级级联和幂等记录等等价机制重建。具体 ORM、驱动和表名属于实现决策，不写入产品契约。
- **事务与删除**：涉及消息与来源记录、文件与写入记录、ticket 整套交付、冻结绑定和级联删除的多表改变必须具备原子提交或可安全重试的补偿语义；不能报告成功后留下可见半套结果。
- **初始化**：提供可重复执行的初始化/升级命令，负责建立或升级表、索引、约束和应用连接身份；不得要求用户手工在 Workbench 执行一长串 SQL。
- **连接配置**：数据库地址、端口、库名、应用连接身份和密码通过环境变量或本机配置提供，真实凭据不写入代码或仓库。Workbench 可继续用 `root`；应用使用仅服务本项目的专用连接身份。
- **开发重置**：可提供开发环境专用的清空并重建命令，但必须检测并阻止生产环境执行；该工具不是用户功能，也不阻塞主迁移交付。
- **错误语义**：数据库连接失败或瞬断时，用户看到通俗、可行动的失败提示；原始技术细节保留在日志或可带回的诊断信息中。不新增专门的数据库初始化页面，不做无限自动重试或后台排队。
- **用户界面**：不向用户展示数据库类型、版本或内部连接状态；空库直接走现有注册页。
- **行为兼容**：v1.2 已确认的消息事实源、生成恢复、显式冻结、项目隔离、文件协议与来源、tab 并发、自动命名、级联删除、HTML 快照和 tickets 版本交付全部属于迁移后的必须保持项。
- **测试 seam**：最高测试 seam 是 MySQL 空库上的 replay/API 综合入口，复用现有 Playwright 驱动、API 断言和固定回放模式；必要时补最小 schema/约束可观察检查，不以 ORM 内部函数为主验收对象。

## Testing Decisions

- 测试只断言用户可见页面、HTTP/SSE 结果、消息列表、文件列表、快照/tickets 版本和 MySQL 中可观察的关联与约束结果，不断言具体 ORM、SQL 写法或函数签名。
- 第一层是环境探测：确认 MySQL 9.7.2 LTS 可连接、初始化命令可重复执行、应用专用连接身份可用，并确认 replay 模式不会调用真实模型。
- 第二层是现有 v1.2 replay 综合入口迁移到 MySQL：覆盖安全渲染、冻结两阶段、项目/工作记录删除、消息恢复、tab 并发和命名、项目隔离、文件边界/来源、HTML 快照、tickets 版本交付。
- 第三层是从零人工冒烟：注册 → 创建项目 → 创建工作记录 → 需求分析 → 原型 → PRD → tickets，并检查文件、消息和版本交付结果。
- 数据断言必须检查用户/项目/工作记录/tab/消息/项目文件/上下文/快照/操作记录/文件来源之间的 ownership、唯一性、顺序、版本和删除结果；不迁移旧 MongoDB 数据，因此不包含 MongoDB→MySQL 内容比对。
- 故障专项至少覆盖：MySQL 服务未启动或配置错误、初始化重复执行、唯一约束冲突、事务中途失败、瞬断后的明确失败与手动重试、删除/文件来源/ticket 交付的原子或补偿语义。
- 真实模型不参与日常迁移回归；只有需要确认 prompt 理解时才按仓库纪律另行批准 live 冒烟。
- 综合入口只汇总专项退出码和类别，专项脚本保留具体断言；迁移失败必须能区分环境、schema、业务行为和测试夹具问题。

## Out of Scope

- 旧 MongoDB 数据导出、清洗、迁移、回搬、双写或自动切回。
- MongoDB 删除、卸载或数据恢复承诺；MongoDB 可留存，但不属于 v1.3 应用运行链路。
- 新的用户可见产品功能、页面、Agent、工作流或体验改版。
- 实际线上部署、云数据库采购、域名、HTTPS、监控、备份策略和 DBA 运维体系。
- 为数据库状态制作专门的用户页面或管理员后台。
- 让用户在网站页面清空数据库；开发重置只能是受保护的本机开发工具。
- 同时兼容所有 MySQL 版本；未在 9.7.2 LTS 或实现者明确验证的版本上不作支持承诺。
- 以低层 ORM 单元测试替代最高 seam 的用户行为回归。

## Further Notes

- v1.3 的主要风险不是“能否连接 MySQL”，而是关系、原子性、幂等、删除和历史状态在新数据模型中是否保持外部行为。
- 由于 MySQL 从空库开始，v1.3 的人工验收必须使用新注册账号，不能把旧 MongoDB 数据存在与否当作通过条件。
- 实现前应先按本 spec 的依赖拆票：运行时/配置基础 → 关系 schema 与数据访问 → 业务一致性迁移 → 初始化/错误与开发工具 → 综合回放与人工冒烟。
- `ready-for-agent`、实现完成和验证通过是三个独立事实；本 spec 不表示代码已经迁移完成。
