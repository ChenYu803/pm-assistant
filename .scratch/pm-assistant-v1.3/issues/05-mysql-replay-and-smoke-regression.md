# 05 — MySQL 综合回放与从零人工冒烟

**What to build:** 提供以 MySQL 空库为前提的 v1.3 综合回放入口，并完成一次从零注册到四环交付的人工冒烟，证明数据库替换没有改变 v1.2 用户行为。

**Blocked by:** #01 — MySQL 运行时与初始化基础；#02 — 关系模型与数据访问替换；#03 — 业务一致性与核心 API 迁移；#04 — 空库首次使用与诊断边界

**Status:** ready-for-agent

- [ ] 综合入口运行前确认服务端连接的是 MySQL 9.7.2 LTS，并确认使用固定回放模式，不调用真实模型。
- [ ] 复用现有最高 seam 的 Playwright/API replay 方式，覆盖 Markdown 安全、冻结两阶段、级联删除、消息恢复、tab 并发/命名、项目隔离、文件协议/来源、HTML 快照和 tickets 版本交付。
- [ ] 测试在 MySQL 空库或受控开发重置后的空库上创建测试用户，不依赖旧 MongoDB 数据。
- [ ] 综合入口只汇总专项退出码、名称和类别；专项脚本保留具体断言和失败上下文。
- [ ] 数据断言覆盖实体 ownership、唯一约束、排序、状态、版本、关联记录、删除结果和整套 tickets 版本，不测试 ORM 内部实现。
- [ ] 完成一次人工冒烟：注册 → 创建项目 → 创建工作记录 → 需求分析 → 原型 → PRD → tickets，并确认交付文件和消息可回看。
- [ ] 输出明确区分环境未就绪、schema/初始化失败、业务回归和测试夹具问题；不在失败时切换到 live 模式。

## 相关 spec

见 v1.3 spec 的“迁移验收”和“Testing Decisions”。

## 验收标准

- MySQL replay 综合入口的所有专项通过，或失败报告能准确定位到类别和专项。
- 从零人工冒烟完成四环交付，用户可见结果与 v1.2 一致。
- `tsc`、相关脚本语法检查和 `git diff --check` 通过；未获批准时不运行真实模型回归。
