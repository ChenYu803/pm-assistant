# 03 — 业务一致性与核心 API 迁移

**What to build:** 将现有 API 和业务服务迁移到 MySQL 数据访问边界，重建 v1.2 的消息恢复、冻结、并发、文件来源、级联删除、自动命名和 tickets 交付等外部行为。

**Blocked by:** #02 — 关系模型与数据访问替换

**Status:** ready-for-agent

- [ ] 注册、登录、项目、工作记录、tab、消息、文件、快照和 tickets API 全部改用 MySQL，不再读取 MongoDB。
- [ ] 保留生成中/完成/中断/失败消息事实源、先生成后替换、刷新恢复和停止生成语义。
- [ ] 保留显式冻结两阶段流程、冻结文档绑定、取消/失败恢复和重复请求幂等。
- [ ] 用 MySQL 等价机制重建 tab 版本、操作锁、request id 幂等和并发冲突提示，不静默覆盖其他窗口结果。
- [ ] 保留项目/工作记录 ownership、文件上下文过滤、文件来源记录、文件版本递增和 HTML 快照边界。
- [ ] 保留项目与工作记录物理级联删除、事务优先或可重入补偿、孤儿清扫和删除后旧 URL 不可访问语义。
- [ ] 保留自动命名条件更新、消息文件来源与重生成一致性提示、tickets 整套替换/另存版本规则。
- [ ] 数据库瞬断或事务失败时当前操作明确失败，可由用户手动重试；不引入后台排队、无限重试或重复提交。

## 相关 spec

见 v1.3 spec 的“既有工作流兼容”“消息、生成与冻结”“一致性、并发与删除”和“故障与诊断”。

## 验收标准

- v1.2 各专项 replay 在 MySQL 空库上通过，外部 API、SSE、UI 状态和可观察数据与原契约一致。
- 并发、幂等、冻结、文件来源、删除补偿和 ticket 版本交付没有出现半套提交、静默覆盖或孤儿数据。
- 数据库连接失败和瞬断不会泄露密码或造成前端重复消息/重复写入。
