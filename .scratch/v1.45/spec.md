# v1.45：需求分析题卡访谈、显式成果输出与基础体验修整

Status: ready-for-agent
Version: v1.45
日期：2026-11-09

依据：Q1–Q40 产品澄清、用户对整体共享理解的确认，以及本次 to-spec 授权。本文是本版实现与验收的规格，取代同主题访谈中的早期建议；访谈继续保留原始讨论过程。本次只发布规格，不创建实现票，不修改运行时提示词、业务代码或生产数据。

## 1. 问题陈述

v1.44 的人工验收只完成了验证码相关部分，其他流程已暴露出成组的功能与体验问题。继续把它们加入历史验收票，会混淆版本范围、实施依赖和验收责任。v1.45 需要独立组织这些改动，并为后续实现留痕。

当前需求分析把普通聊天、访谈推进和文件生成混在一起。用户说“写入”或“别写入”可能影响模型是否输出文件块，模型也可能在不合适的时机生成工作文档或正式成果。文件块、文件候选和确认创建并不能清楚表达用户何时授权生成交付物；模型曾出现忽略任务、正文过短、输出不适当文件等问题。

普通聊天式的需求澄清也缺少组织感。用户需要逐轮作决策，同时能中途补充、调整前提、回看原问题和答案；仅把回答拼成普通聊天历史，容易丢失问题归属和更正关系。新的交互应改善参与感，同时保留 LLM 根据用户反馈自主提问和推进的能力。

工作台顶部信息重复占高，滚轮和内容区滚动不正常，输入框与发送按钮不容易完整看见。跨阶段提示使用了不能严谨代表“已有确认成果”的启发式判断，无法准确解释产品依靠 Markdown 交付物传递上下文的工作方式。AI 回复缺少清晰气泡，复制没有恰当反馈。

个人中心视觉需要重做；邀请码管理为单管理员增加了原因填写、内容遮挡和临时展示等无用操作，却缺少批量作废、完整码长期查看及清晰的领取信息。账号界面的密码输入也缺少显示／隐藏功能。

## 2. 解决方案

保留四环工作流，以及需求分析内部的“需求挖掘 → 需求取舍 → 实现方案”三阶段。三阶段规定分析内容，在各阶段内借鉴 grilling 的问题依赖、分轮推进和根据反馈调整问题的方法。LLM 负责访谈判断，程序负责可靠呈现、问答关联、权限、存储与计费。

需求分析采用按轮组织、逐题呈现的题卡，配合同一会话内的自由输入框。每题单选，最后一个选项允许自由填写；用户可切题、修改草稿、部分提交或中途补充。所有轮次的问题与答案持续保留，未提交历史轮仍可作答提交，已提交轮只提交一次。题卡是交互呈现方式，不是预先锁死路径的固定问卷。

所有阶段通过醒目的显式输出入口生成并保存正式成果。普通聊天里的文件措辞和模型自发文件块都没有写入权限。输出按实际模型用量计费，与“完成本阶段”独立；正常、完整生成并成功保存后才更新成果，支持紧邻上一版的单次回退。

合并工作台项目信息与四环导航，修复滚动和输入区域可见性。后三环每个新会话开始前提醒用户主动注入所需 Markdown，允许不注入直接开始。统一 AI 回复气泡与复制反馈，简化邀请码管理，为所有密码框增加显示／隐藏。

需求分析 system prompt、个人中心和题卡等重要视觉交互，在后续专门的实现票中由用户与 Agent 协作敲定。接口、数据结构、调用协议、迁移和验证方案由 Agent 负责，不要求用户承担技术设计。

## 4. 实施决定

### 4.1 领域边界与模块职责

- **四环阶段**：需求分析、原型设计、PRD、任务拆分，属于产品迭代的工作流。
- **需求分析内部阶段**：需求挖掘、需求取舍、实现方案，组织分析内容，不等于四环切换。
- **阶段会话**：某个产品迭代、某个四环阶段内的一段独立聊天。同阶段可有多个会话，彼此对话上下文独立；各自产出仍保存在项目共享文件树。
- **问题轮**：需求分析会话内的一组问题及关联答案。新一轮、刷新、切回会话都不等于新建阶段会话。
- **成果输出**：用户显式发起的正式交付物生成与保存，与阶段完成独立。
- **任务拆分文件集**：一次成功输出的整套任务文件，按阶段会话归属、整套更新和回退。

| 职责模块 | 负责内容 | 权责边界 |
| --- | --- | --- |
| 需求分析访谈 | 三阶段内容、问题规划、反馈理解、改题、阶段推进和收尾 | LLM 负责内容判断；不执行项目文件写入或外部工具调查 |
| 会话与问题轮状态 | 问题、选项、答案、草稿、提交状态、补充、更正及先后关系 | 程序保证身份与关联正确，不判断反馈是否改变前提 |
| 模型调用与计量 | 明确调用任务、上下文组装、流式结果、幂等、并发、停止和用量结算 | 复用现有调用基础设施，不另建逐题后台调用链 |
| 成果输出与项目文件 | 输出授权、成果归属、命名、原子保存、唯一上一版及变更记录 | 只有输出动作可授权 Agent 生成并保存正式成果 |
| 工作台交互 | 合并导航、题卡与输入框、历史回看、提醒、气泡、复制和按钮状态 | 展示和操作不承担访谈语义裁判职责 |
| 账号与邀请码 | 密码可见性、管理员列表、完整码、批量作废和基本操作记录 | 保留账号权限与积分权益边界 |

### 4.2 三阶段方法与 system prompt

三阶段及其服务交付物的内容继续保留：

| 内部阶段 | 分析内容与方向 |
| --- | --- |
| 需求挖掘 | 理解目标用户、使用场景、现有替代方式、痛点与候选需求 |
| 需求取舍 | 围绕需求是否真实、是否强烈、发生频率作分析，与用户校准范围，记录不做项及理由 |
| 实现方案 | 讨论保留需求的功能、MVP、优先级和边界，形成用户与场景、用户故事、功能范围、成功指标及排除清单 |

1. 在各阶段内借鉴 grilling：按问题依赖规划当前可问的问题，获得反馈后重算下一轮；同轮不提前依赖尚未回答的决策。提供有助于决策的选项及解释，而不是机械盘问。
2. 首次想法输入后必须开始一轮提问。后续是否提问、如何改题、是否回到前阶段补问，由 LLM 在角色和交互约束内自主裁定。
3. 三阶段之间由 LLM 自主判断并适时总结后推进，取消单独的“可以进入下一阶段吗”确认关卡。阶段内容仍要通过实际问答校准，不能因取消流程确认而跳过分析。
4. 提示词必须明确要求模型自检：本轮是否过于冗长、重复；现有信息是否充分；是否已经达到阶段结束信号，应进入下一阶段。不得为维持访谈硬凑题目。
5. 三阶段信息充分时，简短总结并建议输出；历史、补充和输出入口继续可用。新信息仍可触发必要澄清。此建议不自动生成文件、完成四环阶段或跳转。
6. 不设置固定题数、轮数、服务端信息充分评分或“答够五题”门槛。信息不足时如何组织成果交由 LLM 决定，不强制逐项套用固定未知标签。
7. 用户选择中途输出时，原有“四段全部逐项确认才允许输出”不再作为硬门槛。对应分析内容继续服务交付物；普通访谈中的工作记录保存在会话状态中，不由模型自动写成项目文件。
8. system prompt 的具体文字由用户与 Agent 在协作票中共同撰写、审阅和敲定。Agent 应先提供能讨论的草稿、与旧规则的差异及代表性样例，再根据用户反馈迭代；本 spec 不替代这项协作。

### 4.3 题卡、历史与输入状态

1. LLM 一次规划整轮，前端逐题呈现。每题为单选，最后一个选项提供自由填写；不做多选或独立的“暂不确定”选项。自由填写可表达不确定、组合意见、解释和前提变化。
2. 题卡至少有“上一题”“下一题”“提交”。切题、点选、编辑只整理作答，不逐题请求 LLM；当前答案在切题和切换展示后保留。
3. 支持提交部分或全部答案，不以全部必答阻止提交；未答项必须仍是未答，不能填成默认选择或用户确认。
4. 输入框承载“补充／提问／其他输入”，与题卡属于同一阶段会话。中途发送时携带相关未提交草稿并明确标记状态，不自动算整轮提交，也不自动答完某题。模型先处理补充／提问，再决定沿用、调整、收回或重组问题。
5. 每轮问题、选项、答案、提交状态及关联的补充持续保留，可通过轮次入口回看。切换浏览轮次只改变展示，不移除、替换或重排模型所需的会话历史。
6. 程序保留稳定的轮次和题目标识、原始表达、未答状态、草稿与提交快照、补充及更正的来源与顺序。调用时组织清楚“问了什么、如何回答、何时补充、此次在做什么”，不能只把“A”“是”等孤立答案拼进普通聊天链路。
7. 刷新或切回已有会话后可恢复已保留的轮次、问答和未提交草稿，不因此自动调用模型或新建会话。具体轮次选择位置、题卡与输入框展开方式、布局和动效在实现协作中确定。

每轮是否还能作答提交，以**提交状态**为准：

| 情况 | 行为 |
| --- | --- |
| 尚未提交的当前轮 | 可修改作答，提交部分或全部答案 |
| 尚未提交的历史轮，包括模型已另组新轮的情况 | 仍可作答、修改和提交，不因不再默认展示而失效 |
| 已提交轮，包括只答了一部分就提交 | 保留提交时快照供回看，不能补答后再次提交；后续意见走补充入口 |
| 已发送携带草稿的补充 | 保留关联与草稿状态，不等于提交题卡 |
| 已中途输出成果 | 只改变成果；原未提交轮仍可继续作答提交 |
| 模型收回或重组问题 | 保留历史，用户可以不答旧题；不取消旧未提交轮的提交资格 |

例：第一轮未提交，经补充出现第二轮，用户仍可回第一轮提交。第一轮只答两题就提交后，其余题目保持未答，不能补完后再次提交。模型接收历史轮提交时必须知道它的来源、原问答及后续补充顺序，由模型理解语义，不将其误当成新轮答案。

现有消息编辑、重生成和失败重试须服从上述历史规则及输出权限。不能借普通消息编辑改写已提交轮，不能因重生成裁掉已经保留的轮次问答，也不能借重试将普通聊天升级为成果输出。

### 4.4 调用契约、上下文与计费

- 服务端明确区分访谈动作与成果输出动作；不能依据用户正文里的“写入”“别写入”或模型回复猜测模式。提交、补充、继续澄清与成果输出都应有明确请求身份和所属会话。
- 优先复用现有一次模型调用：访谈结果可包含面向用户的说明，以及结构化问题轮或调整动作。前端在结构完整、校验通过后呈现题卡；正文成果继续流式展示。不引入额外后台规划调用或工具执行链。
- 结构校验只检查可执行的契约，例如轮次、题目及选项关联、答案归属、动作合法性。服务器不判断需求好坏、信息是否充分或补充是否改变前提；这些交给 LLM。
- 当前供应商对专用结构化格式或工具 API 的支持尚未实测。实施时选择与现有模型链路兼容的结构化返回方式；不将 SDK 类型存在当作供应商能力已经验证，不强制某种工具 API。
- 无效或未完整返回的题卡结构不能覆盖原题卡和答案，按现有失败处理提供重试；不自动开启多轮修复调用。
- 调用上下文包含当前明确任务、同会话轮次问答与相关补充、更正，以及用户实际授权的文件正文。保留原决定与后续反馈的关系，不由服务器生成替代用户表达的“最终事实”。
- 项目文件正文仍只来自当前阶段会话的上下文文件区域。题卡改造不意味着自动读取前几轮阶段成果或整个项目文件树。
- 复用已有请求幂等、会话并发控制、积分预留、停止和用量结算。重复点击、网络重试不能重复提交问题轮、重复生成成果或重复扣分；浏览器断开不等于用户主动停止模型。

| 用户动作 | 是否调用模型 | 计费与状态 |
| --- | --- | --- |
| 切题、点选、编辑、打开输入框、回看轮次 | 否 | 不单独收费；可保存界面进度和草稿 |
| 提交部分或全部答案 | 是 | 按实际调用用量计费，该轮只提交一次 |
| 发送补充／提问 | 是 | 按实际调用用量计费，草稿仍未提交 |
| 明确请求继续澄清 | 是 | 按实际调用用量计费，不逐题自动调用 |
| 通过输出入口确认生成成果 | 是 | 按实际调用用量计费，不额外收取固定题数套餐费用 |
| 开始对话、完成阶段、复制、回退 | 不因此调用 | 这些动作不暗中生成成果 |

### 4.5 唯一显式成果输出

1. 输出入口授权一次正式交付物的生成与保存。普通聊天、答题和补充没有该写入权限；用户正文中的写入措辞、模型自然语言承诺、自发文件标记都不能提升权限。这一边界必须由服务端执行，不能只写在 prompt 里。
2. 退出旧“文件块 → 候选 → 确认创建”正式成果流程。旧候选确认接口、历史候选按钮和手动提出整套候选等旁路，不能继续绕过显式输出授权；历史文本可查看复制。
3. 需求分析从首轮题卡出现后，在模型空闲时持续提供输出入口，无须答完整轮。输出携带本次相关的未提交答案，明确草稿与未答状态，不为传递这些答案再单独调用一次模型。
4. 需求分析选择输出时，先显示生成前 pop_confirm，提醒继续回答可让模型获得更多信息；用户确认后才开始生成。不在生成后再次提供“候选／确认创建”。具体提示文案在协作时敲定。
5. 后三环输出按钮位于“完成本阶段”左侧，两者均应显眼。按钮文案表达交付物类型；名称示例不替代首次保存时的实际命名规则。
6. 输出与完成独立：成功输出不自动完成或跳阶段；完成阶段不暗中调用模型或生成文件。不以“已有确认成果”判定阻止自由进入后续阶段。
7. 这里约束 Agent 的正式成果生成与保存，不撤销用户已有的文件编辑、改名、删除和回退能力；这些操作继续遵守既有项目权限。

| 四环阶段 | 正式成果 | 输出入口表达 |
| --- | --- | --- |
| 需求分析 | Markdown | 输出需求分析文档 |
| 原型设计 | Markdown | 输出原型文档；对话 HTML 仍可生成预览，非文件树正式交付物 |
| PRD | Markdown | 输出 PRD 文档 |
| 任务拆分 | 整套任务文件 | 输出整套任务文件，不误称只输出一份 Markdown |

### 4.6 成果归属、原子保存和一版回退

- 新阶段会话首次输出创建自己的成果，即使上下文注入旧成果也不获得覆盖旧文件的授权。同会话后续输出更新自己上次成功输出的成果。
- 普通 Markdown 首次命名采用“阶段名-主题.md”，同名自动加序号，首次保存后保持文件名。以稳定的成果身份关联会话，不能靠文件名猜测应覆盖哪份文件。
- 不提供跨会话覆盖目标选择，不因目标经过手工修改而新增覆盖提醒或确认。覆盖时应保存实际被替换的当前正文作为唯一上一版。
- 任务拆分按会话各有一套，同一产品迭代的 A、B 会话可并存多套；各自后续输出只更新自己的文件集，分别整套回退。沿用项目资产归属、来源迭代／会话、变更记录及未冲突的生命周期规则。
- 正式文件及其唯一上一版，只能在生成正常完整结束、交付物结构有效且保存成功时原子更新。任务拆分必须整套提交，不能部分成功。重复请求复用同一结果，不能生成重复文件集或覆盖备份多次。
- 用户停止、调用失败、输出达到上限而截断，或保存失败时，不创建或替换正式成果，也不改原有备份；已展示文字继续可查看复制。计量层把调用视为可结算，不代表业务层可把截断成果保存为正式文件。
- 仅保留紧邻上一版，不提供版本列表或多级历史正文。A → B → C 后只可 C → B；回退消耗备份，不能继续到 A，也不能重做到 C。之后新的正文变化重新形成唯一上一版。任务拆分以整套为单位执行同样规则。
- 删除阶段会话不连带删除已保存项目资产、备份和变更记录。新会话原则不能变成会话删除时丢失成果的理由。

### 4.7 工作台、上下文提醒与消息

1. 合并项目信息栏与四环进度／导航，保留必要项目、积分和返回入口，减少顶部占高。合理桌面视口下完整输入框和发送按钮应稳定可见，对话区独立滚动，鼠标滚轮有效；适配实际题卡和长回复，避免叠加模块再次推长页面。
2. 用户可自由进入四环任何阶段。取消按阶段完成、文件名或文件数量推断“已有确认成果”的旧提醒逻辑，也不实现已作废的顶部悬浮 Alert 方案。
3. 原型、PRD、任务拆分的每个新阶段会话，开始聊天前醒目提示在侧边栏注入所需 Markdown，并说明不注入可能缺少前序需求、范围和约束，导致回复或成果与原决定不一致。呈现可采用红框、红字等，具体视觉与最终文案通过页面协作敲定。
4. 提供“开始对话”按钮；无论有没有选择文件，都可开始。点击后将该会话已开始的状态持久保存，刷新、切回或继续此会话不重复提醒。该按钮本身不调用模型。提醒不是检测条件，也不是注入门禁。
5. 侧边栏文件选择必须与实际发送给模型的正文相符；移除的文件不能继续被静默注入，不自动代选前序成果。已有对话中曾经出现的信息仍属于该会话历史，不因移除文件而伪称已被模型遗忘。
6. AI 说明、自由回复和成果正文有清晰气泡，与用户消息区分；长文宽度适合阅读，不能铺满整个工作台。结构化问题轮使用专门题卡，相关说明与题卡保持清楚联系。
7. 复制使用该回复保留的模型输出原文，保留 Markdown 和原有文本，不改用净化后的展示内容或渲染后的纯文本，也不擅自剥离模型输出中的标记。
8. 复制成功只让该条复制按钮的图标暂时变为 `√`，随后恢复；按钮附近不显示“已复制”或等价文案，页面顶部无复制成功提示。复制失败时，页面顶部 Toast 提示并在两秒后消失。

### 4.8 个人中心、邀请码和密码框

- 个人中心与邀请码管理分为两个页面，共享视觉系统。具体视觉由用户和 Agent 在实际页面上迭代确认，不在本规格预先锁定配色、组件布局或动效。
- 移除创建原因、作废原因输入及接口强制原因要求；保留管理员身份校验，以及最基本的动作、操作者、时间记录，不以额外必填字段增加操作负担。
- 新邀请码持久保存完整码，管理员可长期查看复制。取消内容遮挡、“仅本次显示”及独立的“本次生成的 100 个邀请码”模块。
- 列表用邀请码本身替代“邀请码 ID”展示，领取账号与领取时间分列。保留原有邀请码状态和必要管理操作；完整码仅在应有的管理员权限内提供。
- 支持批量作废未领取码；已领取码不可通过此操作作废，领取记录及已到账积分不追回。旧完整码只存摘要，不能声称可还原。
- 版本接续时，将旧未领取码统一作废，再生成 100 个新码；保留已领取记录、账号关联、领取时间及已到账积分。此为实施任务，尚未在本次规格工作中执行。
- 所有密码输入框增加可点击的眼睛图标切换显示／隐藏，覆盖登录、注册及确认密码、找回密码及确认、个人中心修改密码的全部密码字段。每个按钮只切换对应输入，不清空内容或意外提交表单，提供可辨识的操作名称。

### 4.9 人机协作、旧数据与工程实施边界

| 后续工作类型 | 用户参与 | Agent 负责 |
| --- | --- | --- |
| 需求分析 system prompt | 共同撰写、评审访谈与成果样例、敲定表达和产品取舍 | 提供草稿和差异、接入任务模式与结构契约、验证运行行为 |
| 个人中心、邀请码页、题卡及关键工作台视觉 | 看实际页面，反馈并确认视觉和交互体验 | 先完成可审阅页面，按反馈迭代布局、状态、响应式与动效 |
| 接口、数据、权限、调用与计费、回退、验证 | 不要求额外技术设计输入；如出现真实产品冲突再报告 | 自主选择并实现方案，完成验证、风险说明和留痕 |

后续拆票必须显式注明“需要用户协作的环节／产品经理提供的输入”；纯技术票应写“无新增产品输入”，给出 Agent 可直接执行的定义和验收条件。需要用户参与不等于让用户先写接口、数据库或测试方案；Agent 应把页面、提示词草稿和样例准备到可具体讨论的程度。

旧任务数据按用户已确认的低成本原则处理：当前只有本人使用，旧数据零价值，可选择方便的清理或过渡方式，不设计复杂无损兼容，也不从历史共同修改记录猜定唯一会话归属。该取舍适用于本次改造的旧过程／任务数据，不扩大为任意清理账号、积分、权限或已领取权益。

本规格不冻结数据库表名、路由名称、供应商专用协议或题卡组件结构。Agent 可在上述产品行为内决定具体实现；涉及协议、持久化、计量及数据接续时按高风险变更验证。生产执行另按部署纪律安排，不在编写规格时提前实施。

## 5. 测试决定

以下是后续实现的验证要求，不代表这些功能已实现或已经完成行为验收。

### 5.1 首选验证接口与已有先例

优先使用一个贯穿产品行为的验证入口：**真实应用的公开 HTTP／浏览器入口 → 隔离 MySQL → 公开查询和页面结果**。通过已有本地 HTTP 模型供应商替身控制返回内容、计数调用并核对注入请求；不为题卡、计费或成果分别另建一套测试框架，也不依赖生产数据库和真实邮件。

好测试检查用户可观察行为及持久结果：看到什么题卡、提交后还能做什么、模型实际收到哪些授权信息、文件如何变化、实际调用与积分如何结算。不要通过组件内部 state、私有函数调用次数、提示词全文快照或数据库列名来代替行为断言。数据准备可以使用隔离夹具，结果尽量通过公开查询和界面读取。

复用先例：

- `scripts/verify-v141-isolated-replay.mjs`：独立数据库、正式应用、场景回放、证据输出及清理；现有场景路径校验尚未接受 v1.45，实施时小幅扩展版本登记，不复制第二套运行器。
- `scripts/verify-v141-iteration-lifecycle.mjs`：浏览器与工作台 API、阶段会话、上下文选择和持久状态。旧软门禁等已被本版替代的行为断言须按新规格调整。
- `scripts/verify-v144-stop-billing.mjs` 及对应场景：本地供应商替身、停止、断线、延迟用量、并发和结算故障。
- `scripts/verify-v144-gift-invites.mjs`、`scripts/verify-v144-email-auth.mjs` 及对应场景：管理员／普通账号、邀请码、账号表单和隔离邮件边界。
- `scripts/verify-mysql-project-artifacts.mjs`：项目文件与成果持久化的相关先例；先核对仍适用的规则，再选择回归范围。

旧需求分析脚本中“自然语言促成输出”“自动工作文档”“文件候选确认”等断言不再代表本版正确行为，不能为了让旧断言通过而保留写入旁路。真实模型测试不承担可靠权限与存储边界的主要验证职责。

### 5.2 行为验收矩阵

| 编号 | 场景 | 必须观察到的结果 |
| --- | --- | --- |
| T01 | 首次自由输入、题卡呈现和切题 | 首次输入后出现问题轮；单选加最后自由填写；上一题／下一题保留草稿，切题不增加模型调用或扣分 |
| T02 | 全部提交、部分提交及重复提交 | 两种提交都只提交一次；未答项仍未答；已提交轮不能再提交，重复请求不重复调用、扣分或形成第二次提交 |
| T03 | 补充打断与历史未提交轮 | 补充带上未提交草稿及来源；出现新轮后仍能回旧未提交轮作答提交；已提交轮的更正走补充，原问答快照保留 |
| T04 | 历史回看、刷新和会话隔离 | 轮次、选项、答案、草稿和补充关系保留；浏览不改变上下文或调用模型；不同会话不会混入彼此问答 |
| T05 | 结构错误、失败和重试 | 不完整或无效题卡不覆盖原题卡和答案；失败可恢复；编辑／重生成不抹掉已提交轮或历史关联，不自动多轮修复 |
| T06 | 上下文和反馈先后 | 本地供应商捕获的请求包含正确问题、答案、未答状态、草稿身份及更正顺序；不出现孤立选项字母或把旧轮冒充新轮 |
| T07 | 唯一输出权限 | 聊天中要求写入、禁止写入或模型自发文件块，都不保存正式成果；只有输出动作能生成保存；历史候选及旧接口不能绕过 |
| T08 | 中途输出及生成前提示 | 首轮题卡出现后可空闲时输出；生成前提示可取消，取消不调用；确认后带草稿一次生成，不先额外提交；原未提交轮仍可继续 |
| T09 | 新建、更新、撞名和会话归属 | 新会话注入旧成果仍新建，撞名自动区分；同会话只更新自己的成果并保持名称，来源记录正确；两个任务会话各有独立文件集 |
| T10 | 一版回退与整套原子性 | A → B → C 只能回 B，不能继续回 A 或重做到 C；任务文件集整套提交／回退；手工修改后的实际当前正文成为被替换备份 |
| T11 | 主动停止、失败、截断及保存故障 | 首次输出不留下半份正式成果；更新不改旧正文和备份；已显示文字仍可看和复制，任务文件集无部分落地 |
| T12 | 计费、并发和断线 | 各真实调用沿用现有用量结算；纯 UI 操作零额外调用；重复点击／重试无重复扣分；停止与断线遵守已有处理和待核对机制 |
| T13 | 输出与完成独立、原型预览 | 输出不自动完成／跳阶段；完成不生成成果或新增调用；原型 HTML 可预览，任务输出明确为整套文件 |
| T14 | 后三环新会话提醒 | 各新会话开始前均有醒目提醒和开始按钮；有无文件都可开始；刷新和切回不重复；不按完成状态、文件名或数量决定显示与准入 |
| T15 | 文件选择与实际注入 | 模型实际请求只注入获授权的文件正文，加载与移除即时对应；不自动读取前序成果或其他会话文件正文 |
| T16 | 布局、滚轮与气泡 | 合并顶部栏后，典型桌面视口完整看到输入和发送；滚轮能读长对话；AI 与用户有明确容器区分，长文宽度合理 |
| T17 | 复制成功与失败 | 剪贴板逐字符合原始输出并保留 Markdown／标记；成功只有当前按钮暂变 √，无成功文字或顶部提示；失败顶部 Toast 两秒消失 |
| T18 | 邀请码管理及权益 | 创建／作废不需原因；完整码长期可见可复制；列表分列且无独立临时生成模块；批量仅作废未领取码，已领取记录与积分不变，普通账号无管理权限 |
| T19 | 旧码接续 | 隔离演练后旧未领取码不可再兑换，新生成 100 个且完整值可查；已领取记录和权益保持，重复执行防止重复发放；生产执行另留核对记录 |
| T20 | 全部密码字段 | 登录、注册、找回、修改密码及各确认框逐一验证显示／隐藏；值不变、切换只作用于对应字段，不触发表单提交 |

上述场景按需要合并进少量连续回放，覆盖高风险分支即可，不为每个用户故事编写重复测试。涉及别的账号、项目或会话标识的请求应继续受既有归属和身份校验保护。

### 5.3 提示词与视觉协作验收

- 提示词先用可审阅样例确认三阶段分析内容、问题依赖、逐轮推进、补充调整和自然收尾。真实模型短程验收至少覆盖：首次想法开问、范围中途变化、历史轮反馈、信息充分收尾，以及携带部分草稿输出。
- 需要看到内容质量的独立证据：是否理解用户意图、是否重复追问、是否忽略要求、长文本是否完整。题卡和输出按钮解决交互与授权，不足以证明原来的短文、跑题或忽略长度问题已经修复。不把模型语义质量变成服务端打分门槛。
- 页面协作使用实际可操作的个人中心、邀请码页、题卡和工作台，由用户反馈后收敛设计。题卡要覆盖长题干、长选项、自由填写、历史轮、部分提交和生成中状态；不能只展示静态理想状态。
- 桌面初始验收基线采用 1440 × 900 与 1366 × 768，并检查窄屏不丢关键入口；长回复、打开侧边栏和题卡切换时仍应可操作。基础键盘操作、焦点和可辨识按钮名称纳入页面检查。
- 视觉“通过”需要用户对实际页面的反馈与确认；结构化替身可验证程序流程，不能代替用户的视觉判断或真实模型的访谈效果。

### 5.4 验证成本与完成条件

按仓库规则分级：文案或数值为 L0，单层 UI 行为通常为 L1，输出授权、协议、轮次持久化、计量、文件与备份、邀请码数据接续为 L2。相关改动先批量收齐再按风险验证，不改一处就重复跑完整对话。

确定性回放优先，不产生真实模型或邮件费用。真实模型验收说明要验证的假设、预计时长及调用范围；预计超过 10 分钟先取得用户同意。技术验证由 Agent 准备和执行，用户参与提示词行为与实际页面体验的评审。

实施完成时须有对应行为证据、适用的编译与专项检查结果、必要的用户协作验收记录和已知限制。记录实际结果，不把本规格中的验收计划记成已经通过的测试。
