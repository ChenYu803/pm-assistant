## Q6：Proton 收到验证码却不能注册——事实与尚缺证据

用户报告：3037116719@proton.me 可正常收到验证码，但输入邮件里的正确验证码后出现“验证码错误，请核对邮箱及用途后重试”。这是尚未修复的真实缺陷，不能因另一邮箱的既有验收结果而关闭。

### 当前代码实际做了什么

1. 发送与注册接口都先用同一个函数规范化邮箱（去掉首尾空白并转小写），没有 Proton 域名的独立拒绝分支。
2. 注册页面发送固定使用 register 用途；注册接口也固定按 register 校验，注册请求不依赖用户手写用途。
3. 发送时产生六位随机数字，对“邮箱 + 用途 + 验证码”使用 AUTH_SECRET 计算 HMAC 摘要，登记到数据库，再把同一个 code 参数交给腾讯云模板。
4. 供应商受理后将当前凭证从 pending 改为 ready。收到邮件说明投递到达了收件箱；不证明邮件模板展示值、注册提交值、当时数据库登记的有效凭证三者一致。
5. 注册重新计算提交值的摘要，与数据库里的当前摘要比较，成功后才同事务建号并消费验证码。
6. 用户看到的原始错误 **只对应 code_digest 为空或 HMAC 摘要不一致**。没有凭证、已用、发送未完成、已过期、次数过多分别有其他提示；前次把它们混称为同一个分支不准确。

### 其他阶段与正式交付物

在“完成本阶段”左侧添加显眼的输出按钮，两者都要足够显眼。正式交付物沿用：需求分析 Markdown、原型 Markdown、PRD Markdown、任务拆分整套文件。任务拆分入口须表达整套输出，而不是误称仅输出一个 Markdown。原型 HTML 仍可在对话中生成预览，它不是项目文件树中的正式交付物。

**成果输出与完成阶段相互独立**：输出成功不自动完成或跳阶段；完成不暗中生成文件。自由进入后续阶段和 Q7 的 Markdown 注入提醒继续适用。

同一阶段会话再次输出普通 Markdown 时，默认更新本会话上一次成功输出的同一份文件（Q24）。首次命名沿用“阶段名-主题.md”，同名自动加序号；首次保存后，再次输出维持该文件名（Q26）。

新会话即使注入了旧成果，也默认新建自己的成果；不增加“在输出入口明确指定覆盖目标”的设计。旧成果可由用户自行删除，或不将其注入下一阶段（Q27）。Q32 已确认该原则同样适用于任务拆分：每个阶段会话各有一套，后续仅更新自己的文件集，各套分别整套回退一版；由此取代旧的每迭代至多一套数量约定，见 ADR-0009。

提供仅回退一个版本的功能（Q24）。不因目标已有手工或其他会话的新修改而增加覆盖提醒、覆盖前确认或额外交互分支，依靠一次回退恢复误覆盖（Q29）；这与既有 v1.41 不额外警告或阻止较旧候选覆盖的领域约定一致。新显式输出路径仍需接入已有回退能力。

生成被停止、失败或达到输出上限时，已展示文字仍可查看和复制，但不创建或替换正式文件，也不改动原有上一版备份；任务拆分整套同样处理。请求正常结束且保存成功后才替换正式成果（Q28）。

### Q31 对服务端与提示词的含义
