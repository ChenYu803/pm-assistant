# PM Assistant v1.0 — Spec

Status: ready-for-agent

## Problem Statement

MVP 验证了「多 Agent 流水线 + md 交接物」的概念，但交付物达不到 v1.0 的验收要求——**PRD 拿去 vibe coding 会卡壳**：

1. 落地版 PRD 是「五维度」人读文档，对 AI（「只会执行的程序员」）太粗犷：没有页面清单（AI 不知道建哪些路由、页面怎么连）、字段按功能散落而非按实体聚合（AI 拼不出数据模型，同一实体的字段散在多个功能里会读到矛盾）、没有排除项（AI 的「完成主义」会把不做的东西也做掉）、没有验收标准（AI 完成后无自检依据）——「文案规范」对 AI 零价值（见 ADR-0002/0003）。
2. 流水线只有两个环节，中间缺两环：**原型产出**（页面清单与用户流程在行业惯例中属原型阶段产物，且用户对文本确认的把握度低于看图）和**任务拆分**（PRD 是可切分的，但没有 Agent 把 PRD 切成 issues——用户外部 vibe coding 的消费方式是「每 issue 一个对话」，单对话装整个 PRD 会逼近模型「变蠢区间」）。
3. 现有 prompt 纪律不足：Agent 会一次抛多个问题、跳过阶段确认、漏写输出结构、在对话流刷大表格——「输出低质」与「对话体验差」并存（方案 B 五项目标）。

v1.0 完成标志：作者本人（唯一用户）从零走完「想法 → 需求分析.md → 原型.md → prd.md → issues 文件集」，拿到的 PRD + issues 实际 vibe coding 一次跑通。

## Solution

流水线扩展为四环（= matt 主流程的产品化）：**需求分析（≈grill）→ 原型产出（≈prototype）→ PRD 撰写（≈to-spec）→ 任务拆分（≈to-tickets）**，用户外部 vibe coding（≈implement）为终点。

- **prd.md 重构为六章骨架**（读者是 AI，见 ADR-0003）：概念（含外部依赖声明）/ Out of Scope（排除项附理由）/ 页面清单 / 实体级数据模型（字段单源聚合 + 状态机）/ 用户流程 + 验收标准（按用户故事组织，异常并入分支）/ 文案基调（三行封顶）。精简版 PRD 退役为纯流程确认产物（对话内完成，不落盘）。
- **新增原型 Agent**：确认工具（非展示品）。交付物 = 结构化文本（页面清单 + 用户流程，格式即 PRD 第 3、5 章）；HTML 只是可视化媒介，不参与交付。提案式访谈（先给方案再问）。
- **新增任务拆分 Agent**：PRD → issues 文件集。垂直切片、blocking edges、引用 PRD 章节而非复制。
- **方案 B 输出保障**：一次只问一个问题 / 显式确认推进 / 输出完整性保障 / 表格控制。
- **需求分析 Agent 微调**：功能范围段充实（做 X + 不做 Y 及理由）。

## User Stories

未列出的 MVP stories 继续有效（账户、项目、工作记录、文件系统基础、错误与边界）。

### 原型 Agent

1. 作为一个用户，我想在创建标签页时看到「原型」Agent 类型，以便开始原型阶段。
2. 作为一个用户，我想原型 Agent 采用提案式访谈（先给方案再问，与需求分析 Agent 的诘问式相反），以便快速看到方向而不是被反复追问。
3. 作为一个用户，我想原型 Agent 主动声明「可生成简单 HTML 原型，下载后浏览器打开」，以便我选择是否查看可视化形态。
4. 作为一个用户，我想下载 Agent 生成的 HTML 原型并在浏览器中打开，以便直观确认页面布局与用户流程。
5. 作为一个用户，我想在对话中指出页面或流程的问题，Agent 据此修订结构化文本，以便修正设计。
6. 作为一个用户，我想每轮修订后 Agent 重新生成 HTML 快照，以便我的可视化确认始终对应最新设计（确认闭环）。
7. 作为一个用户，我想原型确认「完满」后必须显式确认（肯定词），Agent 才写入原型.md，以便我掌控产出时机。
8. 作为一个用户，我想原型.md 的内容是页面清单 + 用户流程的结构化文本（即 PRD 第 3、5 章格式），以便 PRD Agent 直接嵌入、零转换。
9. 作为一个用户，我想原型.md 出现在项目文件树并可预览/下载/编辑，以便审查和复用。
10. 作为一个用户，我想原型 Agent 的对话回复保持对话形态（一次一个主题、无整屏表格），以便确认过程不疲惫。

### 任务拆分 Agent

11. 作为一个用户，我想在创建标签页时看到「任务拆分」Agent 类型，以便在 PRD 完成后开始切分。
12. 作为一个用户，我想任务拆分 Agent 切分前先 quiz 我（issue 粒度偏好 / 依赖如何处理 / 是否需要合并拆分），以便切分结果符合我的消费习惯。
13. 作为一个用户，我想 Agent 把 PRD 切成垂直切片（一个 issue = 窄但完整：该页面的 schema/API/UI/流程，大小 = 一个全新上下文窗口能完成），以便我每个 issue 开一个 vibe coding 对话。
14. 作为一个用户，我想每个 issue 包含 what to build（用户视角端到端行为）+ acceptance criteria（直接从 PRD 验收标准带走）+ blocked by，以便我切分后即可开工。
15. 作为一个用户，我想 issue **引用 PRD 章节而非复制内容**，以便 PRD 修改后 issue 不产生版本漂移。
16. 作为一个用户，我想 issues 文件按依赖序编号（NN-<slug>.md）输出到 issues/ 下，以便我按序逐个实现。
17. 作为一个用户，我想 issues 文件出现在项目文件树中（子目录展示）并可下载，以便我拿到项目外 vibe coding。
18. 作为一个用户，我想逐个确认/拒绝每个 issue 的写入，以便我对切分结果有控制权。
19. 作为一个用户，我想在切分结果与 PRD 不一致时要求重新切分，以便修正切分错误。

### PRD 六章（PRD Agent 重构）

20. 作为一个用户，我想 PRD Agent 创建时自动加载需求分析.md 和原型.md，以便二次确认而非从零讨论。
21. 作为一个用户，我想 PRD Agent 先二次确认需求分析的结论（不重新讨论），以便对齐基线。
22. 作为一个用户，我想概念章包含核心用户 / 要解决的一件事 / 产品形态 / 商业模式 / **外部依赖声明**（如「支付走微信 SDK，不自研」），以便 AI 读到正约束、不擅自自研。
23. 作为一个用户，我想 Out of Scope 章列出排除项并**每项附一句理由**（引用需求分析功能范围段），以便 AI 不做排除项、理由兼作叙事素材。
24. 作为一个用户，我想页面清单章覆盖每页的目的 / 元素（结构非 UI 细节）/ 操作 / 入口·出口 / 依赖，以便 AI 知道建哪些路由、页面怎么连。
25. 作为一个用户，我想实体级数据模型章按实体聚合定义字段（单源，业务级类型：引用/枚举/数字，非 DB 类型）并集中定义状态机，以便 AI 建 schema 不拼错、不重复。
26. 作为一个用户，我想用户流程 + 验收标准章按用户故事组织（行为跨功能，不按功能切碎），主路径与异常并入流程分支，每条带 3-5 条可验证验收标准（当 X → 系统 Y → 结果 Z），以便 AI 执行后能自检。
27. 作为一个用户，我想文案基调章三行封顶（语气一句话 + 示例 1-2 个 + 命名约定），以便 AI 文案风格受约束而不占用篇幅。
28. 作为一个用户，我想精简版 PRD 在对话内完成（三视角确认 → 概念版 ≤300 字 → 范围冻结确认），但不写入 prd.md，以便流程控制保留、文档单源。
29. 作为一个用户，我想范围冻结协议保留（肯定词确认 + %%%SCOPE_FROZEN%%% 标记），确认后不可更改，以便防跳步。
30. 作为一个用户，我想 PRD 输出前六章必须齐全（缺任何一章 = 输出未完成，Agent 必须补全后再输出文件），以便交付物结构完整。
31. 作为一个用户，我想外部依赖声明只在概念章定义一次，以便单源不重复。

### 方案 B 输出保障（需求分析 Agent + PRD Agent）

32. 作为一个用户，我想需求分析 Agent 每次只问一个（最多两个）问题，以便对话节奏可控。
33. 作为一个用户，我想两个 Agent 的阶段推进都必须先获得我的显式确认（肯定词校验），以便不跳步。
34. 作为一个用户，我想四段分析必须完整输出（用户与场景 / 用户故事 / 功能范围 / 成功指标 缺一不可），以便需求分析.md 完整。
35. 作为一个用户，我想需求分析「功能范围」段充实为「做 X + 不做 Y（附理由）」，以便范围界定与排除理由在需求分析阶段问出（PRD 第 2 章直接引用）。
36. 作为一个用户，我想 Agent 的对话流回复不使用整屏大表格（结构化内容写进文件，对话保持对话形态），以便对话感不被挤压。
37. 作为一个用户，我想 Agent 一次回复末尾以「一个待回答问题」结尾（未确认不推进），以便交互可控。

### 流程与 UI

38. 作为一个用户，我想管线指示器显示四阶段（需求分析 → 原型 → PRD → 任务拆分），以便我知道自己在流水线哪里。
39. 作为一个用户，我想创建标签页时可选四种 Agent 类型（需求分析 / 原型 / PRD / 任务拆分），以便按需开环节。
40. 作为一个用户，我想各 Agent 的空态提示文案适配自己的职责，以便不困惑。
41. 作为一个用户，我想已有行为不回归：滚动条隔离、Markdown 渲染、确认弹窗、401 弹窗、文件删除等，以便 v1.0 不引入新障碍。

## Implementation Decisions

### Agent 类型扩展

- `src/lib/agent-constants.ts`：`AGENT_TYPES` 增加 `"prototype"`（原型）与 `"ticket_splitter"`（任务拆分）两个值，同步 LABELS / DESCRIPTIONS。Tab schema 无需改（enum 引用常量）。
- 自动加载规则扩展：`prototype` 类型创建时自动加载 `需求分析.md`；`mvp_prd` 创建时自动加载 `需求分析.md` + `原型.md`（若存在）；`ticket_splitter` 创建时自动加载 `prd.md` + `需求分析.md`。

### Prompt 层（`src/lib/agent-prompts.ts`）

- **PRD Agent 重构**（原六步 → 新流程）：二次确认 → 概念 + 范围（引用需求分析功能范围段）→ 直接嵌入原型.md 的页面清单/用户流程（第 3、5 章）→ 实体聚合 + 业务规则 grilling（用业务语言提问，如「地址记下单时的还是跟买家资料走？」）→ 验收标准推导 + 用户确认 → 文案基调 → 六章输出。`%%%FILE_BEGIN%%%` / `%%%SCOPE_FROZEN%%%` 协议不变。
- **原型 Agent 新增**：提案式访谈纪律（先给方案再问、一次一个主题）、结构化文本输出格式（= PRD 第 3、5 章格式）、主动声明 HTML 可下载、每轮修订重生成 HTML 快照、冻结协议（复用肯定词校验 + %%%SCOPE_FROZEN%%%，`Tab.scope_frozen` 字段语义泛化为「该 tab 的流程冻结标记」）。
- **任务拆分 Agent 新增**：学习 /to-tickets 切分规则——垂直切片、blocking edges、切分前 quiz 用户（粒度/依赖/合并拆分）、issue 格式（what to build + acceptance criteria + blocked by）、引用 PRD 章节不复制、按依赖序编号。
- **需求分析 Agent 微调**：功能范围段充实（做 X + 不做 Y 及理由），interview 阶段问出。
- **方案 B 纪律**：一次只问 1-2 个问题（回复以待回答问题结尾）；阶段推进显式确认；输出完整性硬规则（四段/六章缺一 = 未完成须补全）；对话流禁大表格。Prompt 重写参考公开 skills（grill-me 的 interview 纪律）。

### 协议与运行时（chat route）

- **协议标记三处一致**（重构 prompt 时的高危耦合点，需同步修改并静态断言）：`%%%FILE_BEGIN%%%` / `%%%FILE_END%%%`、`%%%SCOPE_FROZEN%%%`、肯定词清单 —— 出现在 ① prompt（agent-prompts.ts）② chat route 冻结执法逻辑 ③ ChatArea marker 解析三处。
- 冻结执法逻辑泛化：`prototype` 类型的冻结确认复用现有 `SCOPE_FREEZE_CONFIRM_RE` 肯定词校验（不新增 marker）。
- 完整性保障：prompt 层硬规则（方案 C「输出后置校验」仍不进 v1.0），结构完整性由验证脚本断言兜底。

### 原型 HTML 快照（新机制）

- HTML 快照**不进文件树、不参与交付**（HTML 只是可视化媒介）：原型 Agent 在对话中输出单文件 HTML（代码围栏或独立 marker 段），前端提供「下载 HTML 原型」按钮（Blob 下载，浏览器打开）。不新增存储/API。
- 每轮修订后 Agent 重新输出 HTML 快照，保证可视化确认闭环。

### Issues 文件集（新写入形态）

- 写入 API（`POST /api/projects/[id]/files`）的 filename 支持 `issues/NN-<slug>.md` 路径形式（`(project_id, filename)` 唯一索引不变）。
- 文件树支持 issues/ 子目录展示（缩进或分组），下载沿用现有下载 route（支持子路径文件名）。
- 任务拆分 Agent 一次输出多个 issue 文件：前端沿用现有 marker 解析，按序逐个弹确认框（用户逐个确认/跳过）。
- 写入模式：`prototype` / `ticket_splitter` / `mvp_prd` 为整文件替换；`requirement_analyst` 保持追加模式。

### UI

- `PipelineProgressIndicator`：两阶段 → 四阶段（需求分析 → 原型 → PRD 撰写 → 任务拆分）。
- ChatArea 空态文案：按四种 agentType 适配。
- 标签页自动命名沿用「Agent类型 #N」。

## Testing Decisions

- **测试接缝（沿用 MVP，唯一接缝）**：浏览器 E2E（playwright-core + 本机 Edge）+ API Routes（`page.evaluate` fetch）+ 直连 MongoDB 断言，LLM 走真实 DeepSeek API。不引入单测框架。
- **新增 `scripts/verify-v1-flow.mjs`**（四环全流程验收，走真实对话）：
  - 注册 → 建项目 → 需求分析（诘问 → 四段 → 需求分析.md；断言「功能范围段」含「不做 Y」）
  - 原型 Agent（提案式访谈 → HTML 快照可下载 → 冻结确认 → 原型.md；断言结构化文本含页面清单 + 用户流程）
  - PRD Agent（自动加载需求分析.md + 原型.md → 六章输出；断言六章齐全、第 3/5 章与原型.md 一致、外部依赖在概念章单源）
  - 任务拆分 Agent（quiz → issues 文件集；断言垂直切片格式、blocked by、引用而非复制、按依赖序编号、文件树可见）
  - 数据断言：文件树/DB 状态、协议标记落库正确
- **新增 `scripts/verify-protocols.mjs`**（静态一致性）：断言 %%%FILE_BEGIN%%% / %%%SCOPE_FROZEN%%% / 肯定词清单在 prompt ↔ chat route ↔ ChatArea 三处一致（防重构 prompt 时漏改）。
- **回归**：现有 6 个 verify 脚本继续通过（滚动条/弹窗/Markdown/删除/401 等不回归）。
- **不测试**：PRD 六章的内容深度质量（v1.0 验收 = 作者本人拿真实 PRD + issues 实际 vibe coding 一次跑通，人工验收）；prompt 具体措辞。

## Out of Scope

- 模板案例、新手引导、成果导出（v2，v1.0 出维持——下载功能 MVP 已有）
- 拖拽文件加载（v2）
- 原型 HTML 的视觉保真（HTML 只是媒介，非交付物）
- 竞品分析 Agent、技术顾问 Agent（v2+，选择标准：不直接提升「PRD → vibe coding」链路）
- 多用户协同、移动端适配、国际化、付费
- 方案 C（输出后置结构化校验）、方案 A（流程状态机）

## Further Notes

- 产品流水线 = matt 主流程的产品化（需求分析≈grill / 原型≈prototype / PRD≈to-spec / 任务拆分≈to-tickets / 用户外部 vibe coding≈implement）——亦是三步走第 2 步（小红书教学）的叙事素材。
- v1.0 验收：作者本人（唯一用户）走完四环 + PRD/issues 实际 vibe coding 一次跑通（dogfooding）。
- 原型冻结与 PRD 范围冻结共两次显式确认——实现要轻，防流程过重。
- 验证脚本走真实 DeepSeek 会消耗 token；验证时控制对话轮数。
- 待定项（implement 阶段定）：六章模板的精确格式（含 changelog 头惯例）、文案基调示例风格、原型.md 的 changelog 头惯例、任务拆分 Agent 的 UI 展示名。
