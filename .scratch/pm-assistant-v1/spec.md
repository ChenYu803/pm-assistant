# PM Assistant v1.0 — Spec

Status: ready-for-agent

## Problem Statement

MVP 验证了多 Agent 流水线概念（需求分析 → PRD 两环），但交付物面向人读：prd.md 五维度结构（用户流程/状态机/字段规范/文案规范/异常处理）对 AI 太粗犷——缺页面清单（AI 不知道建哪些页面）、缺实体级数据模型（字段按功能散落而非按实体聚合）、缺功能优先级/MVP 边界（AI 的完成主义会把排除项做掉）、缺验收标准（AI 完成后无自检依据），「文案规范」对 AI 零价值。实际「拿去 vibe coding」会卡壳。

流水线本身缺两个环节：① 页面清单与用户流程（PRD 第 3、5 章）在行业惯例里本属原型阶段产物，现有流程没有原型环节，用户对文本确认的把握度低于看图；② PRD 产出后没有任务切分环节，用户外部 vibe coding 的消费方式是「每 issue 一个对话」（避免模型变蠢区间），没有 issues 交付物则无法开工。

此外 prompt 纪律薄弱（真实对话暴露）：Agent 会跳步、一次抛多个问题、输出漏写结构维度、对话流刷整屏大表格，输出质量不稳定。

## Solution

产品流水线扩展为**四环**：需求分析 → 原型产出 → PRD 撰写 → 任务拆分（= matt 主流程的产品化：grill / prototype / to-spec / to-tickets，用户外部 vibe coding ≈ implement）。

交付物升级：需求分析.md（四段，功能范围段充实「做 X + 不做 Y 及理由」）→ **原型.md**（页面/流程结构化文本，格式即 PRD 第 3、5 章，HTML 仅为可视化媒介不参与交付）→ **prd.md**（六章骨架，读者是 AI，精简版退役为纯对话内流程产物）→ **issues/ 文件集**（垂直切片，引用 PRD 章节而非复制）。

每个 Agent 的流程纪律统一强化（方案 B）：一次只问 1-2 个问题、阶段推进显式确认、输出完整性保障、对话流表格控制。最终交付物 = PRD + issues，可直接 vibe coding——v1.0 完成标志：作者本人从零走完四环，拿到的 PRD + issues 实际 vibe coding 一次跑通。

## User Stories

### 原型 Agent（新增）

1. 作为一个 PM，我想要创建工作台中的「原型」标签页，以便开始原型产出阶段。
2. 作为一个 PM，我想要原型 Agent 自动加载已完成的 需求分析.md，以便不重复讨论需求。
3. 作为一个 PM，我想要原型 Agent 采用**提案式访谈**（设计师式：先给方案再问，与需求分析 Agent 的诘问式相反），以便我通过选择而非回忆来推进。
4. 作为一个 PM，我想要原型 Agent 产出**页面清单**（每页目的/元素/操作/入口出口/依赖）的结构化文本，以便确认产品形态。
5. 作为一个 PM，我想要原型 Agent 产出**用户流程**（按用户故事组织，异常并入分支）的结构化文本，以便确认关键路径。
6. 作为一个 PM，我想要原型 Agent 主动声明「可生成简单 HTML 原型，下载后浏览器打开」，以便我选择是否可视化确认。
7. 作为一个 PM，我想要下载 HTML 原型并在浏览器打开查看，以便直观感受页面流与交互步骤。
8. 作为一个 PM，我想要对原型提出修改意见后，原型 Agent 修订结构化文本，以便迭代。
9. 作为一个 PM，我想要每轮修订后原型 Agent 重新生成 HTML 快照，以便我看到的可视化始终是最新版（可视化确认闭环）。
10. 作为一个 PM，当我显式确认原型「完满」时，原型 Agent 冻结原型（原型冻结协议，肯定词校验），以便正式进入 PRD 阶段。
11. 作为一个 PM，我想要原型冻结后原型 Agent 将结构化文本写入 原型.md（替换模式，含 changelog 头），以便交付物落盘。
12. 作为一个 PM，我想要 原型.md 出现在文件树中并可下载，以便留存与交接。
13. 作为一个 PM，我想要 PRD Agent 直接嵌入 原型.md 的页面/流程（零转换），以便不重复讨论、单源。
14. 作为一个 PM，我想要原型中浮现的页面元素成为 PRD 实体字段的起点（PRD Agent 聚合而非从头追问），以便效率。
15. 作为一个 PM，我想要原型未冻结前可以反复对话调整，以便原型充分迭代。

### 任务拆分 Agent（新增）

16. 作为一个 PM，我想要创建工作台中的「任务拆分」标签页，以便把 PRD 切分为可执行任务集。
17. 作为一个 PM，我想要任务拆分 Agent 切分前先 quiz 我（粒度偏好/依赖/合并拆分），以便切分符合预期。
18. 作为一个 PM，我想要任务拆分 Agent 按**垂直切片**切分（一个 issue = 窄但完整：该页面的 schema/API/UI/流程，大小 = 一个全新上下文窗口能完成），以便每个 issue 可独立开工。
19. 作为一个 PM，我想要每个 issue 包含 what to build（用户视角端到端行为）+ acceptance criteria + blocked by，以便我按依赖序逐个执行。
20. 作为一个 PM，我想要 issue 引用 PRD 章节而非复制内容，以便单源维护。
21. 作为一个 PM，我想要切分完成后 issues 文件集（`NN-<slug>.md`，按依赖序编号）出现在文件树中并可逐个下载，以便外部 vibe coding 消费。
22. 作为一个 PM，我想要切分后可以要求合并/拆分某些 issue，以便粒度调整。

### PRD 六章（PRD Agent 重构）

23. 作为一个 PM，我想要 PRD Agent 在原型冻结后自动加载 原型.md 的页面/流程，以便直接嵌入、不重新讨论。
24. 作为一个 PM，我想要 PRD Agent 在对话内完成三视角（用户/商业/技术）二次确认 + 概念版 ≤300 字，以便低成本方向确认。
25. 作为一个 PM，我想要范围冻结流程保留（显式确认 + 肯定词校验 + `%%%SCOPE_FROZEN%%%`，对话内完成不落盘），以便我掌控范围。
26. 作为一个 PM，我想要精简版 PRD 不再作为章节写入 prd.md，以便单源（同一事实只定义一次）。
27. 作为一个 PM，我想要 prd.md 落地版为**六章骨架**：① 概念（含外部依赖声明）② Out of Scope（排除项附理由）③ 页面清单 ④ 实体级数据模型 ⑤ 用户流程+验收标准 ⑥ 文案基调，以便 AI 可直接开工。
28. 作为一个 PM，我想要概念章包含外部依赖声明（如「支付走微信 SDK，不自研」），以便 AI 读到正面承诺而不自研。
29. 作为一个 PM，我想要 Out of Scope 章每项排除附一句理由，以便 AI 不会因完成主义把排除项做掉。
30. 作为一个 PM，我想要实体级数据模型按实体聚合、字段单源定义（业务级类型：引用/枚举/数字），以便不重复不矛盾。
31. 作为一个 PM，我想要实体状态机集中定义（决策编码，比文字精确），以便状态流转无歧义。
32. 作为一个 PM，我想要用户流程按用户故事组织（行为跨功能）、异常并入流程分支（不单独成章），以便流程完整。
33. 作为一个 PM，我想要每条用户故事带可验证验收标准（当 X → 系统 Y → 结果 Z，3~5 条），以便 AI 有自检依据。
34. 作为一个 PM，我想要文案基调三行封顶（语气一句话 + 示例 1-2 个 + 命名约定），以便约束 AI 默认行为而非自由发挥。
35. 作为一个 PM，我想要 PRD Agent 的补缺 grilling 用业务语言（如「地址记下单时的还是跟买家资料走？」）而非技术语言，以便我无需懂技术也能决策。
36. 作为一个 PM，我想要落地版输出前覆盖全部六章（缺任何一章视为未完成、必须补全），以便输出完整。
37. 作为一个 PM，我想要六章 prd.md 出现在文件树并可下载，以便交接与留存。

### 方案 B 输出保障（全部 Agent 通用纪律）

38. 作为一个 PM，我想要每个 Agent 每次回复只问 1-2 个问题，以便对话聚焦（参考 grill-me 的 relentless interview 纪律）。
39. 作为一个 PM，我想要 Agent 未获显式确认不得推进阶段（确认对齐词校验），以便我掌控节奏、防止跳步。
40. 作为一个 PM，我想要 Agent 输出文档时覆盖规定结构的每一部分（缺部分 = 未完成），以便产出完整。
41. 作为一个 PM，我想要 Agent 在对话流中保持对话形态（结构化内容写进文件而非刷屏），以便不被整屏大表格淹没。
42. 作为一个 PM，我想要需求分析 Agent 的四阶段诘问中每阶段结束都有显式确认，以便防跳步。

### 需求分析 Agent 微调

43. 作为一个 PM，我想要需求分析 Agent 的「功能范围」段包含「做 X + 不做 Y（及理由）」，以便范围界定与排除理由完整（PRD 第 2 章直接引用）。
44. 作为一个 PM，我想要 需求分析.md 四段结构保留（用户与场景 / 用户故事 / 功能范围 / 成功指标），以便独立交付物价值（学习/求职叙事）不丢失。
45. 作为一个 PM，我想要「成功指标（产品层）」与「验收标准（功能层）」在概念上区分、互不打架，以便层级清晰。

### 流水线整体

46. 作为一个 PM，我想要 PipelineProgressIndicator 显示四环（需求分析 → 原型 → PRD → 任务拆分），以便知道自己在哪个环节。
47. 作为一个 PM，我想要导航不锁定（跳过/回退/跳入始终允许），以便按需工作。
48. 作为一个 PM，我想要每个 Agent 产出文件都带 changelog 头（版本/迭代/时间），以便版本清晰。
49. 作为一个 PM，我想要创建标签页时可选择全部四种 Agent 类型，以便按需启用。
50. 作为一个 PM，我想要从零走完四环后拿到的 PRD + issues 直接 vibe coding 跑通，以便完成标志达成（作者本人验收）。

## Implementation Decisions

### Agent 类型与入口

- `AGENT_TYPES` 扩展为四值：需求分析 / 原型 / PRD（显示名从「MVP-PRD」调整为「PRD 撰写」）/ 任务拆分。标签、描述、空态文案、自动命名随之扩展；`Tab` schema 的 agent_type 枚举引用常量，无需迁移。
- 标签页创建时自动加载前序交接文件：原型 Agent 自动加载 需求分析.md；PRD Agent 自动加载 原型.md（替代原「自动加载 需求分析.md」）；任务拆分 Agent 自动加载 prd.md（+ 需求分析.md 作参考）。
- PipelineProgressIndicator 阶段由两环扩展为四环；导航仍不锁定。

### 六章 prd.md 结构（决策编码，来自 PRD 结构课题）

```
1. 概念          核心用户 / 要解决的一件事 / 产品形态 / 商业模式 / 外部依赖声明
2. Out of Scope  排除项清单，每项附一句理由
3. 页面清单      每页：目的 / 元素(结构非 UI 细节) / 操作 / 入口·出口(导航图) / 依赖声明
4. 实体级数据模型 每实体：定义 / 字段表(业务级类型:引用/枚举/数字) / 状态机(集中定义) / 关系；字段单源，其他章节引用
5. 用户流程+验收标准 按用户故事组织；主路径 + 异常并入流程分支；每条带验收标准(当 X → 系统 Y → 结果 Z, 3~5 条)
6. 文案基调      三行封顶：语气一句话 + 示例 1-2 个 + 命名约定
```

- 设计原则：完备性 / 单源事实 / 可定位（章节 = AI 检索单元）/ 显式边界 / 可验证；**可切分性**是 PRD 质量的客观验收手段（任务拆分 Agent 切不动/切出重复 = 结构缺陷，人工反馈闭环）。
- Testing Decisions 不进 PRD（「怎么测」是技术决策，第 5 章验收标准已覆盖「测什么」）。
- 精简版 PRD 退役为纯流程产物：三视角确认 → 概念版 ≤300 字 → 范围冻结，全部对话内完成、不落盘；prd.md 不再含精简版章节。

### 原型 Agent

- 交付物 = 结构化文本（页面清单 + 用户流程，格式即 PRD 第 3、5 章），写入 原型.md（整文件替换模式，含 changelog 头）。
- HTML 只是可视化媒介：Agent 主动声明可生成「单文件、自包含、浏览器可直接打开」的 HTML 快照；每轮修订重新生成快照；快照生成/下载机制复用现有文件产出确认通道（协议级兼容：快照不写入项目文件树，仅对话内展示/下载）。
- 原型冻结协议：用户显式确认「完满」+ 肯定词校验（机制同范围冻结），冻结后写入 原型.md；未冻结可继续迭代。
- 提案式访谈纪律写进 prompt：先给方案再问、一次 1-2 个问题、方案用可选项呈现。

### 任务拆分 Agent

- 切分单元：PRD 第 3 章页面清单（骨架）+ 第 5 章依赖声明（blocking）+ 验收标准（直接带走为 issue 字段）。
- issue 格式（决策编码）：

```
what to build（用户视角端到端行为，非分层实现）
acceptance criteria（来自 PRD 第 5 章，直接带走）
blocked by（依赖声明）
```

- 引用 PRD 章节而非复制（单源）；输出 `issues/NN-<slug>.md` 文件集，按依赖序编号；文件树以「issues」分组展示，下载复用现有文件下载通道。
- 切分前 quiz：粒度偏好 / 依赖理解 / 合并拆分意愿；切分后可要求调整。

### PRD Agent prompt 重构（原六步 → 新流程）

- 新流程：二次确认（三视角，基于原型结论而非从零）→ 概念 + 范围（对话内确认）→ 范围冻结（`%%%SCOPE_FROZEN%%%`）→ 嵌入 原型.md 页面/流程 → 实体聚合 + 业务规则 grilling（业务语言）→ 验收标准 → 文案基调 → 六章输出。
- 方案 B 纪律统一写入全部 Agent prompt：一次只问 1-2 个问题 / 显式确认推进（对齐词校验）/ 输出完整性保障（缺部分 = 未完成）/ 对话流表格控制（结构化内容进文件）。参考公开 skills（grill-me 等）的 interview 纪律写法。
- 需求分析 Agent prompt 微调：功能范围段充实（做 X + 不做 Y 及理由），其余三段不动。

### 协议与耦合点（v1.0 高危区）

- `%%%FILE_BEGIN%%%` / `%%%FILE_END%%%` / `%%%SCOPE_FROZEN%%%` 协议不变；原型冻结沿用同一机制（具体 marker 实现时定，优先复用）。
- **三处一致清单**：协议标记与肯定词清单同时存在于 prompt、对话运行时（冻结执法）、前端（marker 解析/渲染）——任何改动必须三处同步，并有静态一致性检查脚本兜底（见 Testing Decisions）。
- 对话运行时：冻结执法逻辑（肯定词正则 + 剥标记）对原型冻结复用/扩展；prompt 组装（system + 已加载文件 + 历史）机制不变，文件全文注入策略在 v1.0 保持不变（上下文瘦身属后续优化，不在本 spec 范围）。

## Testing Decisions

- **测试接缝（唯一，沿用 MVP）**：浏览器 E2E（playwright-core + 本机 Edge）+ API Routes + 直连 MongoDB 断言。LLM 走真实 DeepSeek API（验证真实协议行为；消耗 token 属预期）。不引入单测框架——v1.0 的验收本质是「四环全流程走通 + 产出物结构达标」的端到端问题，核心逻辑在 prompt 与流式运行时，非纯函数可拆。
- **`verify-v1-flow.mjs`（新增）**：四环全流程——注册 → 建项目 → 工作记录 → 需求分析对话（四段 + 功能范围含做/不做断言）→ 原型对话（提案式访谈 → 结构化文本 → 冻结 → 原型.md 落盘断言）→ PRD 对话（嵌入原型 → 六章齐全断言 → 冻结 → prd.md 落盘断言）→ 任务拆分对话（quiz → issues 文件集格式/编号/blocked by/引用断言）→ 文件树与下载可见性断言 + DB 状态断言。
- **`verify-protocols.mjs`（新增）**：协议一致性静态检查——协议标记与肯定词清单在 prompt ↔ 对话运行时 ↔ 前端三处一致；跑在每次 prompt 改动后。
- **回归**：现有 verify-fixes / verify-delete / verify-401 等脚本继续通过（方案 B 与协议改动不得破坏既有行为：确认弹窗、滚动条、401、删除清理）。
- **不测试**：PRD/原型内容深度质量（六章内容好坏）——由作者本人 vibe coding 验收（v1.0 完成标志），脚本只断言结构与协议行为。

## Out of Scope

- 模板案例、新手引导、成果导出（下载功能 MVP 已有）——v2 范围
- 竞品分析 / 技术顾问等更多 Agent——后续版本
- 原型 HTML 的视觉保真与在线预览编辑器——HTML 只是可视化媒介，非交付物
- 拖拽加载文件、移动端适配、多用户、国际化
- 上下文瘦身（prompt 全量注入优化）——后续优化项
- 单测框架引入

## Further Notes

- 产品流水线 = matt 主流程的产品化（需求分析 ≈ grilling / 原型 ≈ prototype / PRD ≈ to-spec / 任务拆分 ≈ to-tickets / 用户外部 vibe coding ≈ implement）——亦是三步走第 2 步（小红书教学）的叙事素材。
- v1.0 验收 = 作者本人从零走完四环，拿真实 PRD + issues vibe coding 一次跑通（Dogfooding 兼作验收）。
- 待实现细化项（to-tickets/implement 阶段定）：六章模板精确格式（含 changelog 头惯例）、原型.md 命名与 changelog 惯例、HTML 快照生成/下载具体机制、原型冻结 marker 具体形式、文案基调示例风格。
- 本 spec 基于 CONTEXT.md 决策表与 ADR-0001~0004；PRD 结构课题完整推理见 `.scratch/prd-structure/ai-prd-structure.md`。
