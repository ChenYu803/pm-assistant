## 关键认知校准(为什么「上下文过长」不是核心矛盾)

- PRD 量级:中等产品一份 AI 执行版 PRD ≈ 6k~12k 字(10k~30k tokens),远小于窗口
- 「变蠢区间」≈ 140k~150k tokens(ask-matt smart zone 同值),会话累积(PRD + AI 自产代码 + 历史)才可能触及
- 真实机制:① lost-in-the-middle 有效注意力衰减 ② 会话累积稀释 ③ **AI 反复取用而非一次读完**(PRD 是全程精确取用的数据库)
- 结论:结构设计服务「可定位/可切分」,而非「装不下」

## 设计原则(五条,贯穿全部决策)

1. **完备性**:AI 需要的业务语义一字不少,不需要的一字不多
2. **单源事实**:同一事实只定义一次,其余引用;重复 = 版本漂移,AI 读到矛盾版本会随机信一个
3. **可定位**:章节是 AI 的检索单元,取用 O(1)
4. **显式边界**:「不做 X」与「做 X」同等重要;不写排除项,AI 会因「完成主义」做过头
5. **可验证**:可验证表述替代主观描述(文案基调一行 + 示例;「友好报错」→ 具体场景 + 文案)

另:**可切分性**(Tickets Agent 能可靠切分)是 PRD 质量的客观验收手段——切不动/切出重复 = 结构缺陷。

## 已敲定决策

### D1 PRD 物理形态:prd.md 单文件

- 不按主题拆多文件;模块化发生在产品功能层(issues),不在文件层
- Tickets Agent 输出 issues 文件集,每个 issue **引用 prd.md 章节而非复制**(单源)

### D2 PRD 六章骨架(落地版,取代五维度)

| # | 章节 | 内容 | 替代/吸收 |
|---|---|---|---|
| 1 | **概念** | 核心用户、要解决的一件事、产品形态、商业模式、**外部依赖声明**(如「支付走微信 SDK,不自研」——业务语义非技术决策;**已敲定:放概念章,单源定义,范围章保持用户可见排除的纯净语义**) | 吸收精简版「核心用户/一件事/技术前提」 |
| 2 | **Out of Scope / 范围冻结** | 排除项清单,**每项附一句理由** | 吸收精简版「本版本不做什么」+ 叙事素材(取舍) |
| 3 | **页面清单** | 每页:目的 / 元素(结构非 UI 细节)/ 操作 / 入口·出口(导航图)/ 依赖 | 新增;切分单元 |
| 4 | **实体级数据模型** | 每实体:定义 / 字段表(业务级类型:引用/枚举/数字,非 DB 类型)/ **状态机**(集中定义,决策编码)/ 关系;字段单源定义,其余章节引用 | 重构「字段规范」(按功能散落 → 按实体聚合) |
| 5 | **用户流程 + 验收标准** | 按**用户故事**组织(非功能——行为跨功能);主路径 + **异常并入流程分支**(非独立章);每条带验收标准(可验证行为契约:当 X → 系统 Y → 结果 Z,3~5 条);标注涉及页面/实体 + 依赖声明 | 重构「用户流程/异常处理」+ 新增验收标准 |
| 6 | **文案基调** | 三行封顶:语气一句话 + 示例 1~2 个 + 命名约定 | 降级「文案规范」(对 AI 零价值 → 约束默认行为) |

### D3 精简版 PRD:流程保留,文档退役

- 三件套拆解:三视角确认(流程)、概念版 ≤300 字(内容,被第 1、2 章吸收)、范围冻结(流程 + `%%%SCOPE_FROZEN%%%` 执法点)
- **精简版的存在目的是流程控制**(低成本方向确认,防落地版返工),不取消
- 但**不再作为文档章节写入 prd.md**(原 1.4 节「精简版 PRD 结论」取消)——双重身份(流程产物 + 文档章节)导致同一事实两处定义,破坏单源
- 保留为流程中的确认产物:对话输出 → 用户确认 → 冻结,不落盘

### D4 需求分析.md:四段结构不动,内容规格微调

- 四段(用户与场景/用户故事/功能范围/成功指标)保留;需求分析就做需求分析该做的事,不越界
- **「功能范围」段充实:做 X + 不做 Y(理由)**——范围界定与排除理由是需求分析 Agent 的职责,interview 阶段问出,PRD 第 2 章引用
- 概念厘清:**成功指标(需求分析,产品层「怎么算成功」)与验收标准(PRD,功能层「怎么算做好」)层级不同,不重复、不打架**
- PRD Agent 的补缺 grilling 用**业务语言**(「地址记下单时的还是跟买家资料走?」)而非技术语言

### D5 新增 Agent:原型 Agent + 任务拆分 Agent(两个)

#### 原型 Agent

- 定位:**确认工具**(非展示品);最终交付物 = **结构化文本**(页面清单 + 用户流程),**HTML 只是给用户看的可视化媒介,不参与交付**
- 流程:需求分析敲定后 → **提案式讨论**(先给方案再问,与需求分析 Agent 的诘问式相反)→ 主动声明「可生成简单 HTML 原型,下载后浏览器打开」→ 用户看可视化确认/修正 → 改结构化文本 → **每轮修订重新生成 HTML 快照**(保可视化确认闭环)→ 用户显式确认「完满」→ 进入 PRD 阶段
- 妙处:HTML=媒介 → 模型代差(视觉上限)与验证闭环两个质量差距被结构性消解,DeepSeek + 特化 prompt 足够
- 输出格式 = PRD 第 3、5 章格式(单源,PRD Agent 直接嵌入零转换);实体字段起点从原型「页面元素」浮现,PRD Agent 聚合而非从头 grilling
- 新交接物:原型.md(页面与流程结构化文本)
- **已进 v1.0**(范围划线修改,待原会话更新 CONTEXT.md)

#### 任务拆分 Agent(中文名已定;英文即 Tickets Agent)

- 输入:prd.md + 需求分析.md;输出:issues 文件集
- 切分规则(学习 `/to-tickets`):**垂直切片**(一个 issue = 窄但完整:该页面的 schema/API/UI/流程)、每个 issue 大小 = 一个全新上下文窗口能完成、blocking edges(依赖)声明
- 切分单元:第 3 章页面清单(骨架)+ 第 5 章依赖声明(blocking)+ 验收标准(issue 字段,直接带走)
- issue 格式:what to build(用户视角端到端行为,非分层实现)+ acceptance criteria + blocked by;**引用 PRD 章节而非复制**
- 流程:切分前 quiz 用户(粒度/依赖/合并拆分)
- **选择标准修订(已敲定,待写 CONTEXT.md)**:新增 Agent 以「提升『PRD → vibe coding 跑通』完整链路(PRD 质量本身 + 落地性)」为第一标准;新手引导性/环节丰富度为第二标准,不因「看起来丰富」而加。依据:PRD 质量高低由链路质量决定、由 vibe coding 成功与否评判

## 原型 Agent 与原型阶段对照(关键洞察)

- 行业惯例里,页面清单、用户流程(及实体字段起点)由原型阶段产出——**v1.0 用原型 Agent 承接该职责**(从 v2 提前,范围划线已改,text-first 替代方案作废)
- 关键设计:**HTML 只是可视化媒介,结构化文本才是交付物** → 「原型 Agent 产出质量 vs Claude Code」的担忧被结构性消解:能力上限(视觉)与验证闭环都不参与交付,DeepSeek + 特化 prompt 足够
- 原型 Agent = **提案式访谈**(设计师式:先给方案让用户选),与需求分析 Agent 的诘问式(苏格拉底式)相反
- 旧五维度没有页面清单且流程按功能散落 = 没有原型替代物的体现;新结构 + 原型 Agent 一并解决
- 补充设计点(用户已确认):① 每轮修订重新生成 HTML 快照(可视化确认闭环)② 原型冻结显式确认协议(肯定词校验,同范围冻结;注意与 PRD 范围冻结共两次确认,实现要轻)③ 输出格式 = PRD 第 3、5 章格式 ④ 提案式访谈纪律写进 prompt
