# 08: 任务拆分整套提交与归属权限

**What to build:** 将任务拆分从普通单文件列表改为“一个产品迭代拥有一套 issue 文件夹”。Agent 或所属迭代用户可以一次提出整套任务集合，用户必须整体确认；整套可以新增、更新和删除 issue，并支持一次整套撤回。其他迭代只能查看、下载和加载这些 issue，不能修改或接管任务文件夹。

**Blocked by:** 05: 普通文件候选确认与通用耐久写入；07: 普通文件修订、一次撤回与变更记录

**Status:** needs-info（任务集合审阅/整套确认/撤回主界面原型或复用确认尚未补齐；补齐后改为 `ready-for-agent`）

## 产品经理在 Agent 开始前提供

### 必须确认

- 任务集合候选的整体审阅界面，以及新增、更新、删除差异的展示方式。
- “整套确认”“整套放弃”“撤回整套更新”的主操作入口。
- 其他迭代查看任务文件夹时的只读和加载表现。
- 如果不需要新的视觉方案，明确写“复用现有候选确认/文件详情视觉风格”。

### 可选提供

- 任务文件夹或 issue 行的固定文案。`NN-` 序号、整套确认和所属权规则不可由原型改写。

### 不需要提供

- issue 数据表、集合快照结构、事务实现、解析器、API 或测试脚本。

## Agent 负责

- 每个产品迭代最多拥有一个任务拆分文件夹；文件夹的稳定归属是产品迭代稳定编号，不因改名或其他迭代操作改变。
- 每个 issue 文件名为系统生成的 `NN-自由描述.md`：`NN-` 在该文件夹内单调递增，删除后不复用，允许出现缺号；AI 和用户只能修改自由描述，不能修改系统序号。
- 任务候选集合代表该文件夹新的完整唯一真相；一次确认可以新增、更新和删除多个 issue，但不能只确认其中一部分。
- 每次整套确认在一个原子变更组中提交：成功时所有新增、正文变化、重命名和删除一起生效；失败时当前完整集合保持不变，候选继续可处理。
- 每个 issue 保留稳定文件身份和单调递增内容修订；正文变化增加修订，重命名和删除只产生操作记录；同一整套动作的记录归入同一个变更组。
- 每次成功整套变更只保存一份更新前的完整集合快照，包含恢复所需的 issue 身份、序号、路径、正文和修订事实；下一次成功变更替换这份快照。
- 撤回整套变更时原子恢复旧集合：恢复被删 issue、移除本轮新增 issue、还原被更新正文；正文恢复产生新的 restore 修订，纯重命名恢复不增加内容修订；撤回消耗快照且不支持重做。
- 只有任务文件夹所属迭代可以通过 Agent 或用户编辑、重命名、删除、整套更新和撤回；其他迭代只能查看、下载和加载上下文。
- 退役旧的 `issues/vN` 版本目录、替换/另存两种交付模式和逐 issue 部分确认；新语义只有一个当前集合和一个上一整套快照。

## Agent 不负责

- 不允许其他迭代“接管”、迁移或改写旧任务文件夹。
- 不把任务候选拆成可独立确认的 issue，不因用户只选中部分而部分落盘。
- 不保存完整 Git 式任务历史或提供多次重做。
- 不替产品经理决定 issue 的业务内容、依赖取舍、验收文案或集合差异的视觉风格。

## 验收标准

- [ ] 同一迭代最多出现一个任务拆分文件夹；创建新 issue 的 `NN-` 不复用，删除后出现缺号是允许的。
- [ ] 修改 issue 名称只能修改 `NN-` 后缀，不能修改或借用系统序号。
- [ ] 候选集合同时包含新增、更新和删除时，用户必须整体确认；确认后集合与候选完全一致，不能出现新旧 issue 混杂。
- [ ] 整套提交或整套手动操作失败时，不出现半套结果，候选仍可重试。
- [ ] 整套撤回原子恢复更新前集合：新增项被移除、删除项恢复、更新项正文恢复且修订规则正确；撤回后不能再次重做。
- [ ] 所属迭代可编辑自己的任务文件夹；其他迭代可以查看、下载和加载，但编辑、删除、重命名、整套更新和撤回均被拒绝。
- [ ] 不存在 `issues/vN`、逐 issue 确认、替换/另存分支或跨迭代接管行为。
- [ ] 任务集合审阅、只读和撤回主界面与产品经理提供的原型或明确复用方案一致。
