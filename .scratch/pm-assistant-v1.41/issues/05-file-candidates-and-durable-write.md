# 05: 普通文件候选确认与通用耐久写入

**What to build:** 统一四环 Agent 产出普通项目文件的候选和确认流程。Agent 先在当前阶段会话中提出候选，用户审阅后明确选择创建、覆盖或放弃；只有确认写入后，纯 Markdown 正文才进入项目文件树。该票建立后续原型交付、修订和任务拆分复用的通用写入边界。

**Blocked by:** 02: 四环导航、阶段状态与多会话；03: 项目级文件树与基础操作；04: 手动上下文与 Agent 读取边界

**Status:** needs-info（候选确认主界面和特殊文案尚未补齐；补齐后改为 `ready-for-agent`）

## 产品经理在 Agent 开始前提供

### 必须确认

- 候选预览和确认区域的主界面。
- 用户如何选择“确认创建”“确认覆盖”“放弃候选”；创建与覆盖需要在确认区域明确区分。
- 如果不需要新的视觉方案，明确写“复用现有候选确认/消息视觉风格”。
- 四个阶段 Agent 的用户可见职责和对应树枝是否沿用以下固定映射：需求分析→需求分析，原型设计→原型，PRD→PRD，任务拆分→任务拆分。

### 可选提供

- 你特别想固定的确认文案或按钮名称。普通加载、生成、失败和重试状态由 Agent 按主界面补齐。

### 不需要提供

- marker 格式、事务实现、数据库结构、来源字段设计、API 或测试脚本。

## Agent 负责

- Agent 生成的普通文件候选只保存在产生它的阶段会话中；候选出现、重新生成或预览不会创建项目文件、修订号或项目级变更记录。
- 候选只能指向当前阶段对应的树枝，不能由 Agent 或客户端把文件写入其他树枝。
- 普通文件名使用对应类型前缀加 AI 自由描述；用户可以在确认前修改文件名，但仍必须留在对应树枝。
- 按精确路径判断操作类型：路径不存在为创建，路径已存在为覆盖；确认界面必须显示操作类型和目标路径。
- 用户确认创建或覆盖后，原子地写入纯 Markdown 正文；用户放弃后，项目文件和所有修订/变更记录保持不变。
- 写入失败时，候选继续留在原会话，目标文件正文、修订、上一版备份和变更记录均保持写入前状态；用户可以重试。
- 不增加“候选基于旧内容”的过期警告；用户确认的最后一次写入直接生效。
- Markdown 存储、预览、上下文读取和下载使用同一份纯业务正文，不嵌入 changelog、版本号、来源迭代或写入记录。
- 工作文档和概念版只作为阶段内部过程状态，不自动进入项目文件树或上下文文件区域；只有用户主动保存为耐久成果时，才走同一候选确认和写入流程。
- 写入来源由服务端根据真实的产品迭代、阶段、阶段会话和消息确定；不接受 Agent 文本或客户端传入的自由来源字符串。
- 所有四环会话平等：任一会话都能提出候选，每次实际写入都必须单独由用户确认。
- 退役旧固定正式文件名、需求分析追加写入、自动写入、旧 scope-freeze/冻结锁定对普通文件写入的约束，以及任何把未确认内容直接落盘的路径。

## Agent 不负责

- 不替用户决定候选是否认可、是否覆盖或是否放弃。
- 不在本票实现完整修订详情、一次撤回、文件时间线或任务拆分整套更新；这些由第 07、08 票完成。
- 不自行设计缺失的核心视觉方向、固定文案或业务取舍；原型和 spec 冲突时必须报告阻塞。
- 不保留完整正文历史，不提供 Git 式重做、分支或冲突解决。

## 验收标准

- [ ] 四个阶段各生成一个普通文件候选时，候选均留在当前会话，未确认前项目文件树和项目数据库事实不变。
- [ ] 新路径候选的确认区显示“创建”；已存在路径候选的确认区显示“覆盖”；用户可在确认前改名但不能改树枝。
- [ ] 用户确认写入后，只有对应树枝出现当前纯 Markdown 文件；用户放弃后文件树、修订和变更记录均不变。
- [ ] 注入一次写入失败后，原文件正文不被部分修改，候选仍可重试。
- [ ] 不出现额外的“内容可能过期”警告；确认覆盖直接生效。
- [ ] Agent 不能通过固定文件名、追加语义、自动写入或旧冻结协议绕过用户确认。
- [ ] 工作文档和概念版不会自动出现在项目文件树或上下文文件区域；用户主动保存时可以转为普通候选。
- [ ] 文件正文、预览、上下文和下载均不含 changelog 或系统元数据。
- [ ] 每条已确认 Agent 写入都能由服务端关联到真实迭代、阶段、会话和消息；客户端伪造来源被拒绝。
- [ ] 候选确认主界面与产品经理提供的原型或明确复用方案一致。
