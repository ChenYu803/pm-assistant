# v1.41 原型交付清单

本文件给产品经理使用。它回答“每张 v1.41 实现票开始前，我要交什么原型”。它属于 v1.41，不是通用项目纪律；它不是技术方案，也不要求产品经理设计数据库、接口、组件、提示词、事务或测试脚本。

## 交付规则

每个原型包至少包含：

- 一个可访问的 open-design 链接或仓库内文件路径；
- 从入口到主要成功结果的主流程；
- 本票涉及的关键交互、关键状态和不可逆操作；
- 固定文案、素材或明确的复用来源；
- 若某个界面不需要新设计，明确写“复用 <来源>”；
- 实现 Agent 能直接访问的文件或链接，不依赖只存在于产品经理本地的临时截图。

原型包可以是 open-design HTML、粗线框、多个画板或已有界面的明确复用说明。它需要表达产品决策，不需要表达实现代码。

## 当前交付状态

本文件是产品经理的逐票清单和交付模板，不是实际原型包本身。当前 01-18 号票都还没有收到可被 Implement Agent 直接访问的实际原型链接/路径或完整复用确认，因此这些实现票保持 `Status: needs-info`。19-24 号是验收票，不新增产品页面；它们复用前置票输入，只需补充验收视口、数据和故障场景说明。

交付某票的原型包后，产品经理需要把实际链接或仓库路径、复用来源、固定文案和特殊行为补齐，并确认与 spec 没有冲突。只有这些输入可访问且检查通过后，该票才能把 `Status` 改为 `ready-for-agent`；不能只因为清单已经列出要求就提前开工。

## 原型包提交模板

产品经理交付一个原型包时，按下面的信息说明即可：

```text
原型包名称：
可访问链接或仓库路径：
覆盖实现票：
主流程：从哪里进入，用户依次做什么，成功结果是什么
必须展示的状态：只列本票有特殊产品要求的状态
固定文案/素材：
复用来源：不重新设计的页面或区域
与 spec 冲突的地方：没有则写“无”
开工结论：已覆盖本票关键输入 / 仍缺少……
```

不需要为普通加载、网络失败、按钮禁用、无特殊要求的移动端适配逐一制作原型。若这些状态没有特殊产品要求，Agent 按已确认的主界面补齐。原型与 spec 对同一行为有冲突时，先由产品经理做选择，再开始实现。

## 按实现票准备的原型

下表的“最小原型范围”是该票的开工输入，不要求一次画完整个产品。实现票是执行边界，原型包是交付单位；一个 open-design 文件可以包含多个画板并被多张票复用，不等于每张票都要制作独立 HTML。

建议的复用方式：

- 项目迭代入口单独一包；四环导航和阶段状态可以共用工作区画板。
- 项目文件树和手动上下文可以共用文件树/上下文画板。
- 普通文件修订与文件详情、来源时间线可以共用文件详情画板。
- 任务文件夹归属、整套提交和整套撤回可以共用任务拆分画板。
- 阶段会话删除和产品迭代删除可以共用确认/归档画板。
- 工作台整合只补前面画板没有表达的跨区域布局，不重复画全部页面。

| 实现票 | 最小原型范围 | 必须在原型或说明中明确 |
|---|---|---|
| 01 创建与管理产品迭代 | 项目进入迭代列表、创建迭代、进入工作区、修改名称/目标 | 目标填写与暂不填写分支、风险确认、展示名称与稳定编号层级 |
| 02 四环导航与工作区入口 | 迭代工作区和四环一级导航 | 四环顺序、当前阶段、跳过/返回/进入后续阶段的入口 |

## 交付完成检查

产品经理把原型交给 Agent 前，逐票确认：

- 主流程可以从原型中完整走通；
- 本票列出的关键状态和后果有明确呈现；
- 固定文案、素材和复用关系已经写明；
- 文件或链接对 Implement Agent 可访问；
- 没有把待决定的行为留在“以后再说”状态。

完成以上检查后，才把对应 ticket 的 Status 改为 ready-for-agent。在此之前，ticket 只是等待产品输入的计划，不应被 Implement Agent claim。
