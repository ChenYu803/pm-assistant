# PM Assistant v1.41 - 四环实践工作台重铸

Status: ready-for-agent

## Problem Statement

当前四环流程不仅视觉粗糙，而且难以理解和操作。需求分析、原型设计、PRD、任务拆分虽然已经能够端到端产出文件，但现有工作台仍以“工作记录拥有一套文件”的方式组织内容，阶段入口、会话、文件、上下文和交付状态混在一起。用户很难一眼回答：我现在在哪一环、Agent 实际读了哪些文件、这次迭代改了什么、某个文件来自哪次工作、确认写入后还能否撤回。

这种信息架构也不符合真实开发场景。真实项目会持续经历多个产品迭代，但需求分析、原型、PRD 和任务文件仍应共同存在于同一项目中，并被不同迭代按需读取、讨论和修改。把文件藏在某个工作记录下，会割裂项目资产；让 Agent 默认读取全部文件，又会造成不可控的上下文和错误假设。

v1.41 需要同时解决“难用”和“丑”两个问题：把四环重构为清楚、可回看、可跳转的产品工作流，把文件重构为项目级长期资产，并用专业、安静、紧凑的 AI 产品工作室视觉呈现这些关系。目标用户仍是第一次使用完整 PM 工作流的求职 PM / 新手，但产品不能以过度保护代替用户判断。

## Solution

每个项目只保留一棵项目级文件树，固定包含需求分析、原型、PRD、任务拆分四个树枝。项目可以有多个产品迭代；产品迭代负责组织本轮目标、稳定编号、四环状态、阶段会话和“本轮写入”，但不拥有项目文件。任何迭代都能看见项目文件目录，只有用户手动加载到当前会话的文件才会向 Agent 提供正文。

四环作为产品迭代工作区的一级导航始终可见，给出推荐顺序但不设置硬门禁。每一环都允许多个地位相同的阶段会话；任一会话都可以提出创建或覆盖文件的候选，但只有用户确认后才真正改变项目文件。阶段进度由“未开始 / 进行中 / 已完成”表达，并由用户的进入、完成和重新打开动作控制，而不是由文件是否存在自动推断。

项目文件使用纯 Markdown 正文，版本、来源和操作历史全部由系统元数据维护。普通文件保存当前正文和唯一上一版，支持一次撤回；任务拆分以所属产品迭代的整个 issue 集合作为原子单位更新和撤回。每次耐久变更都能追溯到产品迭代、阶段、会话或用户操作，即使来源会话或迭代随后删除，项目文件和来源记录仍然存在。

界面重构为专业 AI 产品工作室：四环总览和阶段交接保持舒展，聊天、文件树和上下文操作保持紧凑；桌面端提供完整生产工作台，移动端通过单栏、抽屉和分步切换承载同一核心流程。用户将在 open-design 中按实现票提供关键主流程原型或明确复用来源；原型决定视觉与具体布局，本 spec 决定行为、状态、权限和数据事实。普通加载、失败、禁用和无特殊要求的移动端状态由 Agent 按已确认的视觉方向补齐。

## User Stories

### 产品迭代与目标

1. 作为项目用户，我希望一个项目可以承载多个产品迭代，以便持续推进同一产品而不拆散项目文件。
2. 作为项目用户，我希望产品迭代与项目文件树在界面上被明确区分，以便理解“迭代组织工作、文件属于项目”。
3. 作为项目用户，我希望产品迭代创建时自动获得项目内单调递增的稳定编号，以便后续文件归属和变更记录始终指向同一迭代。
4. 作为项目用户，我希望已删除迭代的编号不再复用，以便历史来源不会指向另一项工作。
5. 作为项目用户，我希望可以修改产品迭代的展示名称但不能修改稳定编号，以便兼顾可读性与历史身份稳定性。
6. 作为项目用户，我希望界面以展示名称作为主标题、以“迭代 NN”作为次级信息，以便先理解工作主题，再识别稳定身份。
7. 作为创建迭代的用户，我希望“填写本轮目标”和“暂不填写”均不被默认选择，以便由我明确决定是否提供目标。
8. 作为选择填写目标的用户，我希望目标随产品迭代保存，以便四个阶段的 Agent 都知道本轮要解决什么。
9. 作为选择暂不填写目标的用户，我希望先看到一次明确的风险确认，了解 Agent 已知哪些事实以及仍不知道本轮要改变什么，以便作出知情决定。
10. 作为在风险确认中改变主意的用户，我希望返回后保留此前选择和目标草稿，以便不用重新输入。
11. 作为确认暂不填写目标的用户，我希望创建过程不再重复警告，并能在之后补充目标，以便流程明确但不过度阻拦。
12. 作为未填写目标的用户，我希望系统和 Agent 不根据迭代名称、文件目录或未加载正文擅自猜测目标，以便我的真实意图不被错误替代。

### 四环导航与阶段状态

13. 作为产品迭代用户，我希望需求分析、原型设计、PRD、任务拆分四个阶段始终作为一级导航可见，以便随时知道当前环节和完整工作流。
14. 作为新手用户，我希望四环呈现推荐顺序，以便理解从想法到可开发任务的典型路径。
15. 作为已有成果的用户，我希望能够跳过、返回或直接进入任一阶段，以便工作流不会成为硬性门禁。
16. 作为缺少前置成果却进入后续阶段的用户，我希望看到可能影响后仍可继续，以便由我判断当前材料是否足够。
17. 作为产品迭代用户，我希望每个阶段只显示“未开始、进行中、已完成”三种状态，以便进度含义简单明确。
18. 作为使用多个阶段会话的用户，我希望阶段状态属于整个阶段而非某个会话，以便多个会话共同服务同一阶段进度。
19. 作为首次创建或打开阶段会话的用户，我希望阶段自动从“未开始”变为“进行中”，以便状态反映真实进入行为。
20. 作为正在工作的用户，我希望只有我明确点击“完成本阶段”后状态才变为“已完成”，以便系统不替我判断工作是否结束。
21. 作为没有写入文件的用户，我希望仍可完成阶段，以便探索、讨论或确认无需变更也能结束。
22. 作为仍有待确认候选的用户，我希望候选不会阻止完成阶段并继续留在原会话中，以便阶段状态与文件确认互不混淆。
23. 作为等待 Agent 生成的用户，我希望生成结束或被停止前不能完成阶段，以便不会出现仍在生成却已完成的矛盾状态。
24. 作为重新进入已完成阶段的用户，我希望阶段回到“进行中”，以便状态准确反映工作已重新开启。
25. 作为刷新页面或跨设备访问的用户，我希望四个阶段状态保持一致，以便进度不依赖本地界面状态。
26. 作为产品迭代用户，我希望文件写入、候选出现或其他迭代的变化都不会自动改变阶段状态，以便进度只由我的工作动作决定。
27. 作为第一次进入某阶段的用户，我希望看到该 Agent 的职责、所需输入、可能写入的树枝以及阶段位置，以便知道该从哪里开始。
28. 作为打开空阶段的用户，我希望系统只展示可执行的开始提示，而不自动创建会话或发送消息，以便由我控制工作的起点。

### 阶段会话

29. 作为阶段用户，我希望同一阶段可以创建多个阶段会话，以便把不同问题或探索方向分开讨论。
30. 作为使用多个阶段会话的用户，我希望所有会话地位相同，以便任一会话都能提出对正式成果的创建或更新候选。
31. 作为切换阶段会话的用户，我希望每个会话保留独立的消息、过程状态和上下文文件集合，以便不同讨论不会相互污染。
32. 作为从不同会话得到候选的用户，我希望每次实际写入仍由我单独确认，以便会话平等不等于自动覆盖项目文件。
33. 作为删除阶段会话的用户，我希望确认框明确说明未确认候选将随对话丢失，以便删除后果可预期。
34. 作为删除过已写入文件的阶段会话的用户，我希望文件变更记录仍保留迭代、阶段和会话名称快照，以便来源追溯不依赖原消息存在。

### 项目文件树与耐久文件

35. 作为项目用户，我希望整个项目只有一棵由所有产品迭代共享的文件树，以便项目资产集中在同一个地方。
36. 作为任一产品迭代中的用户，我希望都能查看项目当前全部文件目录，以便基于真实的项目现状开展工作。
37. 作为项目用户，我希望文件树固定分为需求分析、原型、PRD、任务拆分四个树枝，以便资产结构与四环职责一致。
38. 作为阶段 Agent 的用户，我希望 Agent 只能向对应树枝提出耐久文件候选，以便成果不会落入错误分类。
39. 作为接收普通文件候选的用户，我希望文件名采用“类型前缀 + 自由描述”的形式，以便既能识别类型又能表达实际内容。
40. 作为确认候选的用户，我希望可以在写入前修改文件名，以便最终路径符合我的项目表达。
41. 作为项目文件用户，我希望写入后也能重命名文件，以便项目命名可以随理解演进。
42. 作为重命名文件的用户，我希望不能把文件移动到另一树枝，也不能占用已有路径，以便分类和路径唯一性保持稳定。
43. 作为确认文件写入的用户，我希望系统按精确路径判断本次是创建还是覆盖，并在确认区域清楚标明，以便知道操作后果。
44. 作为主动确认覆盖的用户，我希望覆盖直接生效且不再收到“内容可能过期”的额外警告，以便系统尊重我的判断。
45. 作为项目用户，我希望只有确认写入或主动保存的耐久内容进入文件树，以便讨论草稿不会污染正式项目资产。
46. 作为阶段用户，我希望工作文档和概念版自动保留为阶段内部过程状态但不出现在文件树和上下文文件区域，以便过程记忆与正式成果分离。
47. 作为认可过程内容的用户，我希望能够主动将其保存为对应树枝中的耐久文件，并经过正常命名与写入确认，以便草稿可以明确升级为正式资产。
48. 作为下载项目文件的用户，我希望 Markdown 只包含业务正文而没有内嵌 changelog，以便文件能直接参与真实开发。
49. 作为使用原型 Agent 的用户，我希望可视化 HTML 预览继续作为独立快照而不进入项目文件树，以便反复预览不会污染正式成果。
50. 作为确认原型成果的用户，我希望结构化原型 Markdown 经确认后进入“原型”树枝，以便后续 Agent 可以在我加载后读取。

### 上下文文件

51. 作为阶段会话用户，我希望 Agent 始终知道当前项目、产品迭代、阶段、本轮目标和项目文件目录，以便它能在正确范围内回应。
52. 作为重视上下文控制的用户，我希望未主动加载的文件只暴露目录元数据而不暴露正文，以便 Agent 不会默认全文读取整个项目。
53. 作为选择上下文的用户，我希望只能通过上下文文件区域加载或移除文件，以便“Agent 实际读了什么”有唯一且可见的控制入口。
54. 作为已加载文件的用户，我希望上下文区域保存文件引用，并在每次发送消息时读取其当前正文，以便共享文件被覆盖后下一轮自动使用最新内容。
55. 作为与 Agent 对话的用户，我希望注入的正文和元数据来自同一次读取，以便修订号不会与正文错配。
56. 作为查看项目目录的用户，我希望目录条目包含路径、树枝、当前修订、最近正文写入迭代和可撤回状态，以便识别项目现状而不读取正文。
57. 作为加载文件的用户，我希望 Agent 同时收到位于正文之外的当前修订来源摘要，以便来源事实不会污染 Markdown 内容。
58. 作为加载文件的用户，我希望完整变更时间线默认不进入 Agent 上下文，以便审计信息不会挤占普通工作对话。
59. 作为表达产品意图的用户，我希望加载文件本身不被解释为继承、认可、批判或修改，以便具体意图仍由我在对话中说明。
60. 作为没有加载任何文件的用户，我希望上下文区域明确显示当前为空，以便知道 Agent 看得见目录但看不见任何文件正文。
61. 作为询问未加载内容的用户，我希望 Agent 明确说明自己没有读过该正文，并可建议我加载具体文件，以便它不会伪装成已经掌握内容。
62. 作为使用四环 Agent 的用户，我希望 system prompt 只约束阶段职责、事实边界和写入规范，而不预设我应如何对待旧文件，以便工作流提供规范但不替我决策。

### 候选确认与写入

63. 作为收到 Agent 文件候选的用户，我希望候选先保留在产生它的会话中，以便审阅前不会改变项目文件。
64. 作为审阅普通文件候选的用户，我希望能明确确认创建、确认覆盖或放弃写入，以便项目文件只反映我的最终选择。
65. 作为放弃候选的用户，我希望项目文件及其修订记录完全不变，以便“生成过”不会被误认为“已经交付”。
66. 作为遇到写入失败的用户，我希望候选继续保留且当前文件不被部分修改，以便修复问题后能够重试。
67. 作为已经完成阶段但尚未确认候选的用户，我希望返回原会话时仍可处理候选，以便完成阶段不会暗中丢弃工作。
68. 作为从不同阶段会话覆盖同一文件的用户，我希望最后一次经我确认的写入成为当前正文，以便共享文件树具有单一当前状态。
69. 作为直接编辑文件的用户，我希望编辑发生在当前产品迭代中并进入变更记录，以便手动修改与 Agent 写入一样可追溯。
70. 作为执行用户手动操作的用户，我希望记录明确标记为用户操作且不伪造 Agent 会话或消息来源，以便审计事实真实可信。

### 内容修订、撤回与变更记录

71. 作为项目文件用户，我希望每次创建、覆盖、用户编辑或撤回正文都生成单调递增的内容修订号，以便准确识别当前正文状态。
72. 作为查看文件的用户，我希望内容修订号与产品迭代编号清楚区分，以便不会把文件版本和工作批次混为一谈。
73. 作为覆盖或编辑文件的用户，我希望系统只保存紧邻的上一个正文作为唯一撤回备份，以便具备误操作恢复能力而不扩张成完整版本控制。
74. 作为撤回文件的用户，我希望旧版正文以一次新的 restore 修订写回，而不是让修订号倒退，以便变更顺序始终单调可追溯。
75. 作为完成撤回的用户，我希望该备份被消耗且不能重做刚才被撤回的正文，以便一次撤回边界清晰。
76. 作为再次修改已撤回文件的用户，我希望本次修改重新建立唯一上一版备份，以便撤回始终只针对最近一次正文变化。
77. 作为查看修订信息的用户，我希望明确知道修订号不是完整正文历史，不能用它浏览任意旧版，以便不会误解产品能力。
78. 作为重命名文件的用户，我希望重命名只增加操作记录，不增加内容修订号，也不改变最近正文来源，以便路径变化不会伪装成内容变化。
79. 作为查看文件详情的用户，我希望看到当前路径、当前修订、创建来源、最近正文写入来源、操作方式、时间和可撤回目标，以便快速理解当前文件状态。
80. 作为查看文件历史的用户，我希望通过不可编辑的变更时间线查看创建、覆盖、用户编辑、撤回、重命名和删除记录，以便追溯发生过什么。
81. 作为查看产品迭代的用户，我希望能看到“本轮写入”汇总，以便反向确认该迭代影响了哪些项目文件。
82. 作为删除来源迭代后的用户，我希望相关来源显示为“迭代 NN（已删除）”并保留名称快照但不再跳转，以便历史仍可辨认且不会进入不存在的页面。
83. 作为删除项目文件的用户，我希望在明确确认后永久删除正文及其一次撤回能力，同时保留轻量的已删除占位和路径快照，以便删除真实生效而来源链仍可解释。
84. 作为没有当前产品迭代的项目访问者，我希望仍能查看目录、打开正文和下载项目文件，但不能把文件加载到 Agent 上下文，也不能编辑、重命名、撤回或删除，以便不会产生没有承载会话的上下文引用或无法归因的持久变更。

### 产品迭代删除

85. 作为删除产品迭代的用户，我希望删除操作不删除它创建或修改过的项目文件，以便项目资产不随工作过程消失。
86. 作为删除产品迭代的用户，我希望项目文件的唯一旧版和永久变更记录继续保留，以便撤回与来源追溯不被破坏。
87. 作为删除含阶段会话的产品迭代用户，我希望删除确认明确说明会话和未确认候选会被删除，同时区分仍保留的项目文件与记录，以便删除范围没有歧义。
88. 作为删除产品迭代的用户，我希望存在进行中的 Agent 生成或文件写入时暂时不能删除，并被引导先等待结束或停止生成，以便不会留下悬空请求或半完成写入。

### 任务拆分整套

89. 作为产品迭代用户，我希望每个迭代至多拥有一个以稳定迭代编号标识的任务拆分文件夹，以便一套任务与其产生迭代保持稳定归属。
90. 作为接收任务拆分结果的用户，我希望每个 issue 使用系统生成、单调递增且不复用的 `NN-` 序号和 AI 自由命名的后缀，以便依赖引用稳定且文件名有意义。
91. 作为任务拆分文件夹所属迭代的用户，我希望能够执行 Agent 整套提交以及用户编辑、重命名后缀、删除和撤回，以便所有改变都遵守同一归属规则且系统序号保持稳定。
92. 作为其他产品迭代的用户，我希望只能查看、下载并加载该文件夹中的 issue，而不能修改或接管它，以便历史任务集合不会被跨迭代重写。
93. 作为确认任务拆分候选的用户，我希望候选集合被视为文件夹新的唯一完整真相，以便当前任务集合没有新旧文件混杂。
94. 作为更新任务拆分集合的用户，我希望一次整套更新可以新增、更新和删除 issue，以便任务结构能够真实演进。
95. 作为确认任务拆分集合的用户，我希望必须整套确认而不能只确认部分 issue，以便 `Blocked by` 和验收关系保持一致。
96. 作为完成任务集合变更的用户，我希望系统生成一个变更组并保存更新前的完整集合清单，以便本次变化可以作为整体追溯。
97. 作为撤回任务拆分更新的用户，我希望系统原子恢复旧集合，包括恢复被删项、移除新增项和还原更新项，以便不会得到半恢复状态。
98. 作为遇到整套写入失败的用户，我希望文件夹保持更新前的完整状态且候选仍可处理，以便任务集合不会部分落盘。
99. 作为删除任务文件夹所属迭代的用户，我希望该文件夹保留为“已删除迭代”的只读归档，以便任务来源稳定且新迭代不能接管。
100. 作为新产品迭代的用户，我希望只能创建属于本迭代的新任务拆分文件夹，以便不会通过迁移旧目录篡改归属关系。

122. 作为产品经理，我希望 ticket 的验收标准同时覆盖输入是否就绪、实现行为是否正确和原型是否正确接入，以便双方对完成定义一致。

## Implementation Decisions

- **范围边界**：v1.41 只重做认证后四环实践工作台及其必要入口衔接，不修改 v1.4 AI 产品经理入职体验的业务流程。
- **领域模型**：项目是长期存在的上层容器；每个项目只有一棵项目级文件树。产品迭代只组织本轮目标、四环状态、阶段会话和本轮写入视图，不拥有项目文件，也不决定文件生命周期。
- **产品迭代身份**：产品迭代创建时获得项目内单调递增且不可修改的稳定编号，删除后不复用；展示名称可修改。界面以展示名称为大标题，以“迭代 NN”为较弱且不可编辑的小标题。
- **本轮目标**：创建产品迭代时，“填写本轮目标”和“暂不填写”均不默认选中。每次从填写切换到不填写或直接选择不填写，都先说明 Agent 已知与未知的信息并提供“返回重新选择”和“确认暂不填写”；返回保留草稿，确认后本次创建不重复警告。创建后仍可补充或修改目标。系统不根据名称、目录或未加载正文推断目标。
- **四环导航**：需求分析、原型设计、PRD、任务拆分作为始终可见的一级导航，保留推荐顺序但采用软门禁；缺少前置成果时说明影响，用户仍可跳过、返回或从既有项目文件开始。
- **阶段状态**：每个产品迭代持久保存四个阶段各自的未开始、进行中、已完成状态。创建或打开阶段会话后自动进入进行中；用户显式点击完成才进入已完成，允许零文件写入；重新打开已完成阶段后回到进行中。生成中暂不允许完成，候选待确认不阻止完成，也不属于阶段状态。
- **阶段会话**：同一阶段可有多个上下文彼此独立、地位相同的阶段会话，它们都可以提出该阶段正式成果的创建或更新候选；每次实际写入仍需用户确认。删除会话时，未确认候选随对话丢弃并在确认中明确告知；已发生的文件变更记录保留来源快照。
- **阶段职责与空状态**：进入每个阶段时，以一句话和紧凑结构说明 Agent 职责、用户可提供的输入、可能写入的文件树枝以及当前阶段位置；空阶段会话只展示可执行的开始提示，不自动创建会话或发送问候消息。
- **双向 ticket 责任契约**：每张 v1.41 实现票必须同时约束产品经理和 Agent，至少包含“产品经理在 Agent 开始前提供”“Agent 负责”“Agent 不负责”“Blocked by”和验收标准。票据必须明确哪些输入是必需、哪些只是参考；产品经理的原型、资源、固定文案、状态、跳转、测试数据或行为取舍属于可被验收的交付输入，不是模糊的背景说明。
- **项目文件树**：固定为需求分析、原型、PRD、任务拆分四个树枝。前三个树枝使用“类型前缀 + AI 自由描述”的文件名；用户可改名但不能换树枝。项目内精确路径必须唯一，路径不存在表示创建，已存在表示覆盖，确认区必须明确标注操作类型。
- **普通文件身份**：普通项目文件具有稳定文件身份、所属树枝、当前路径、当前纯 Markdown 正文、单调递增的内容修订号，以及至多一个紧邻当前正文的旧版备份。改名不改变文件身份。
- **候选与耐久文件**：Agent 产出的未确认候选只保留在产生它的会话中，不创建文件、修订或变更记录。只有用户确认写入或主动保存后，内容才进入项目文件树。系统不增加“候选基于旧内容”的覆盖警告，最后一次经用户确认的写入生效。
- **普通文件内容修订**：创建、覆盖、用户编辑和撤回都会生成新的内容修订号，修订号只增不减。创建得到首个修订；覆盖和用户编辑先用当前正文替换唯一旧版，再写入新正文。
- **一次撤回**：撤回把唯一旧版正文写成一个新的 `restore` 修订并消耗该备份，被撤回的新正文不再保留，也不提供重做。下一次正文变化才重新建立新的唯一旧版。
- **非正文操作**：重命名和删除进入同一条文件变更时间线，但不增加内容修订号。重命名不能占用已有路径；文件删除为永久删除，正文和唯一旧版一并删除且不提供恢复，只保留可解释历史来源的已删除占位与路径快照。
- **文件变更记录**：使用项目级、不可变的文件变更记录统一表示创建、覆盖、用户编辑、撤回、重命名和删除。记录至少包含文件身份或已删除占位、操作前后路径快照、结果修订号（仅正文变化）、来源产品迭代编号与名称快照、操作者、操作类型和服务端时间；阶段、阶段会话与消息属于有真实来源时才记录的条件字段。记录不保存每次修订的完整历史正文。
- **来源生成规则**：Agent 写入来源由服务端沿消息、阶段会话、产品迭代关系确定，不接受 Agent 文本或客户端自由字符串作为来源事实。用户直接编辑、改名、撤回或删除时，来源取当前产品迭代，操作者标记为用户，阶段、会话和消息均允许为空；没有 Agent 参与时不得伪造这些来源。
- **来源记录生命周期**：文件变更记录不能依赖会被删除的消息、阶段会话、产品迭代或项目文件强级联消失。相关对象删除后，记录继续使用稳定编号、名称和路径快照展示；只有删除整个项目才清理该项目的文件及变更记录。
- **普通文件原子写入**：所有正文改变收口到同一个事务边界，完成文件锁定、唯一旧版替换、当前正文写入、修订号递增和变更记录追加；任一步失败都不得留下正文、备份与记录不一致的结果。
- **任务拆分文件夹**：每个产品迭代至多拥有一个以稳定迭代编号标识的任务拆分文件夹。issue 使用系统生成、在该文件夹内单调递增且删除后不复用的 `NN-` 序号，允许出现缺号；AI 和用户只能修改自由描述后缀，不能修改系统前缀。`Blocked by` 与变更记录沿用该稳定序号。
- **任务 issue 修订**：每个 issue 仍是具有稳定文件身份和单调递增内容修订号的项目文件。整套创建或更新时，新增 issue 获得首个修订，正文变化的 issue 获得新修订，改名和删除只产生操作记录；所有 issue 记录都归入同一个任务变更组。
- **任务整套真相**：任务候选集合是该文件夹新的唯一完整真相，一次确认可以新增、更新和删除 issue，但不允许部分确认。整套写入使用一个变更组，在同一事务中保存唯一旧集合快照并提交全部成员；旧集合快照包含恢复每个 issue 所需的稳定身份、系统序号、路径、正文和当时修订事实，下一次成功变更会替换它。失败时当前集合完全不变且候选继续保留。
- **任务手动操作**：所属迭代中的用户可以编辑正文、修改后缀或删除单个 issue，但每次持久操作仍按任务文件夹聚合边界生成一个原子变更组并替换唯一旧集合，不能绕过整套一致性与一次撤回规则。
- **任务整套撤回**：撤回作为新的变更组原子恢复旧集合：被改或曾被删除后恢复的 issue 以同一稳定身份生成新的 `restore` 内容修订；本轮新增的 issue 被删除并记录删除操作；仅改名的 issue 恢复旧路径但不增加内容修订。整个动作消耗唯一旧集合且不支持重做。
- **任务文件夹权限**：只有所属产品迭代能通过 Agent 或用户操作编辑、改名、删除、整套更新或撤回该文件夹；其他迭代只能查看、下载和加载其中的文件作为上下文，用户手动操作也不能绕过所属权。
- **已删除迭代的任务文件夹**：所属产品迭代删除后，其任务拆分文件夹保留为只读归档；其他迭代不能接管、迁移或继续更新。
- **无当前迭代时的权限**：项目级文件树在没有当前产品迭代时仍可查看目录、打开正文和下载，但不能创建上下文引用，也不能编辑、重命名、撤回或删除。把文件加载到上下文文件区域只发生在已有当前阶段会话时。
- **删除产品迭代**：删除不会删除该迭代写入的项目文件、现有唯一旧版或文件变更记录。来源显示为“迭代 NN（已删除）”且不再跳转。存在进行中的 Agent 生成或文件写入时禁止删除，用户需等待完成或先停止；删除确认同时说明阶段会话和未确认候选会被删除。
- **上下文引用**：上下文文件区域保存文件引用而不是加载时的正文快照。每次发送消息时，服务端按引用读取当前正文和同一读取时刻的元数据，因此文件被其他迭代覆盖后，下一条消息读取最新修订。
- **空上下文协议**：Agent 始终获得当前项目、产品迭代、阶段、本轮目标和项目文件轻量目录；目录固定提供路径、树枝、当前内容修订、最近正文写入迭代和可撤回状态，不提供任何未加载文件的正文。
- **已加载文件协议**：用户只能在上下文文件区域加载或移除文件。已加载文件固定附带正文之外的当前修订来源摘要；正文与摘要必须来自同一次读取。完整文件变更时间线不自动进入 Agent 上下文。
- **Agent 意图边界**：加载文件不表示继承、认可、批判或修改。system prompt 只规定阶段职责、事实边界和写入规范，不替用户决定对文件的意图；Agent 不得声称读过未加载的正文，但可以根据目录建议用户加载所需文件。
- **元数据呈现**：文件树以紧凑信息展示当前修订、最近正文写入迭代和可撤回状态；文件详情提供当前路径、创建来源、最近正文来源、操作方式、时间、可撤回目标和完整轻量变更时间线；产品迭代提供“本轮写入”视图。仍存在的来源迭代可跳转，已删除来源只显示占位。
- **纯 Markdown 正文**：Markdown 内嵌 changelog 全面退役。存储正文、文件详情、上下文正文和下载内容使用同一份纯正文；内容修订、来源迭代和变更记录只存在于系统元数据中。
- **阶段过程资料**：工作文档和概念版改为阶段内部自动保存的过程状态，不进入项目文件树，也不出现在上下文文件区域；只有用户主动保存为耐久成果后，才按相应树枝、命名和写入确认规则进入项目文件树。
- **原型快照边界**：原型 Agent 生成的可下载 HTML 预览继续作为独立快照，不进入项目文件树或上下文；确认后的耐久成果是原型树枝中的结构化 Markdown 文件。
- **旧模型退役**：旧固定正式文件名、需求分析追加写入、`issues/vN` 版本目录、tickets“替换 / 另存”、工作文档进入文件树，以及随消息或会话删除来源记录的语义全部退役。
- **旧 changelog 实现退役**：移除写入时的 changelog 生成与解析、展示和上下文读取时的 changelog 剥离、ticket 交付时的头部注入，以及所有依赖该头部的兼容分支；内容比较和冻结摘要若继续使用，均直接基于纯正文。
- **旧数据策略**：v1.41 以清空后的全新 MySQL 数据库开发和验收，不迁移、不回填、不兼容旧工作记录、固定文件、ticket 版本或 changelog，也不伪造旧来源记录。数据库初始化仍须可重复执行。本 spec 本身不执行数据库清空。
- **视觉方向**：工作台采用“专业 AI 产品工作室”而非营销页风格；延续入职体验的品牌基因，但转译为安静、紧凑、适合长期工作的工具界面。四环总览和阶段交接可以舒展，聊天与文件操作保持高信息密度，文件树、上下文和历史会话支持按需展开。
- **响应式责任**：桌面端提供完整生产体验；移动端使用单栏、抽屉和分步切换承载同一核心流程，不以删除关键功能换取适配。
- **open-design 原型责任**：本 spec 锁定信息架构、状态、权限和交互行为；产品经理按实现票在 Agent 开始前提供该票关键主流程的 open-design 原型，或明确复用已有视觉来源。原型可以是粗线框或 HTML，不要求产品经理编写代码、设计数据库或绘制每个异常状态。普通加载、失败、禁用、无特殊要求的移动端适配和技术反馈由 Agent 按已确认的主界面补齐；只有关键产品行为、核心文案或关键视觉区域缺失或冲突时，票据才保持阻塞。完整版本仍需覆盖项目入口与产品迭代创建、产品迭代总览、四个阶段工作台、阶段会话管理、项目文件树、上下文文件区域、普通文件候选确认、任务整套确认、文件详情与变更时间线、一次撤回和删除/权限限制，但可以按票逐步提供，不要求一次完成。
- **原型与规格优先级**：open-design 原型决定视觉层级、布局、控件形态、响应式表现和动效；本 spec 是行为事实源。若原型与本 spec 冲突，Agent 必须在实现前显式指出并等待产品经理选择；Agent 不得自行改变行为，也不得在缺少关键原型状态时擅自完成视觉设计。对于不涉及视觉或交互变化的票，ticket 必须明确写出“复用已确认原型”或“无需新增原型”，不能让是否需要原型变成隐含判断。
- **实现开工门槛**：`to-tickets` 可以在行为 spec 收敛后拆分票据；每张票再声明其产品经理前置输入。关键主流程、核心视觉区域或特殊行为未提供、未确认或存在冲突时，该票保持 `needs-info`/阻塞状态，不得被 Agent claim 为 `ready-for-agent`；普通状态和技术方案缺失不构成阻塞，Agent 应按票据和既有视觉方向补齐。产品经理可以在票据创建后、Agent 开始前补齐对应输入。
- **Agent 责任边界**：Agent 负责把已确认 spec、ticket 和产品经理输入接入现有应用，完成该票的端到端行为、必要测试和原型对照；Agent 不负责自行发明缺失的产品行为、核心文案、视觉方向、资源或业务取舍。发现缺口或冲突时，Agent 必须报告阻塞，而不是以“合理默认”替代产品决策。

## Testing Decisions

- 本次改动同时涉及存储协议、跨 Agent 上下文、权限和文件写入事务，按 L2 高风险改动验证。
- 测试只断言用户可观察行为、公开 HTTP 契约、下载结果和事务最终结果，不断言组件名、内部 helper 调用次数、SQL 形状或 React 局部状态。
- **唯一最高测试 seam**：建立一条 `AI_MODE=replay` 下的 v1.41 四环固定浏览器回放，通过真实应用、公开 API 和 MySQL 可观察结果，从注册、创建项目和产品迭代开始，连续走过四环导航、阶段会话、上下文加载、文件确认、修订与撤回、任务整套更新和删除流程。专项检查只为这条回放提供故障定位，不另建彼此割裂的发布标准。
- 主回放覆盖产品迭代编号递增、删除后不复用、展示名称可修改、本轮目标填写与暂不填写分支、四环软门禁，以及未开始、进行中、已完成、重新打开的状态变化。
- 主回放覆盖生成中禁止完成阶段和删除产品迭代、待确认候选不改变阶段状态、零写入仍可完成阶段，以及删除会话或迭代时对未确认候选的明确提示。
- 普通文件路径覆盖：未确认候选不落盘；新路径创建首个修订；同路径覆盖产生下一修订和唯一旧版；下一次覆盖替换旧版；撤回产生新修订、消耗备份且没有重做；用户编辑、改名和删除均正确归因，改名和删除不增加内容修订。
- 来源路径覆盖：Agent 写入和用户操作使用不同来源类型；删除消息、阶段会话或来源产品迭代后，项目文件、仍适用的唯一旧版和变更记录继续存在；来源显示为已删除占位；删除整个项目才清理全部项目级记录。
- Markdown 路径覆盖：创建、覆盖、详情、上下文和下载获得的正文均不含 changelog；文件修订和来源仍能从系统元数据读取，正文与下载内容保持一致。
- 上下文路径在 AI 供应商请求边界验证：空上下文只注入目录元数据而不泄露任一文件正文；加载文件后注入当前正文和同版来源摘要；文件被另一迭代覆盖后下一条消息读取最新修订；移除文件后下一轮不再注入正文；完整变更时间线从不自动进入普通对话。
- 任务拆分路径覆盖：系统序号在所属迭代文件夹内单调递增且删除后不复用，允许缺号，重命名不能改变 `NN-` 前缀；新增和正文变化产生正确的文件级修订与同组来源记录。所属迭代可整套新增、更新和删除，其他迭代的 Agent 与用户操作均被拒绝；候选不可部分确认；故障注入后不留下半套；撤回以新修订完整恢复旧集合并消耗快照；所属迭代删除后文件夹只读。
- 权限路径覆盖：没有当前产品迭代时持久变更入口不可用；跨项目和跨用户操作被拒绝；普通文件可被其他产品迭代加载和按规则覆盖，任务拆分文件夹仍受所属权限制。
- 既有边界继续覆盖用户身份与项目 ownership、单文件大小限制、HTML 快照与项目文件树隔离、请求幂等和事务失败不留半成品。
- 视觉验收以用户确认的 open-design 原型为基准，在桌面和移动视口检查四环导航、文件树、上下文区域、对话区、确认区、阶段状态和来源信息的层级、无重叠及完整可操作状态。
- 数据库初始化验证只证明新 schema 可从空库创建并可重复初始化，不把表结构断言当作产品行为验收。
- 现有四环综合回放整体替换为 v1.41 回放，因为旧回放硬编码了工作记录、固定文件名、自动加载、工作文档入树、逐 issue 确认和 changelog。
- 现有项目成果验证删除“需求分析追加”“changelog 注入”“issues/vN 另存”等旧断言，保留跨项目权限、大小限制、快照隔离和事务失败无半套。
- 现有文件协议、级联删除和消息变更验证改按新规则断言：阶段会话、消息或产品迭代可以删除，但项目级文件变更记录必须保留；只有项目删除执行完整清理。
- 四个 Agent 的专项质量验证继续保留各自产出结构要求，但移除 changelog 剥离，改用自由文件名和迭代任务目录。旧版本综合回放不再作为 v1.41 发布门，新的发布入口必须从空库开始并包含新模型专项和四环回放。
- 默认验证不调用真实 LLM；仅在需要检查模型对新 system prompt 的理解时，单独向用户报备验证目的、轮数、预计时长和成本。
- 每张实现票在进入实现前检查产品经理输入契约：关键主流程、核心视觉区域、特殊文案或特殊行为已提供并可访问，或票据明确声明复用既有输入/无需新增原型；普通加载、失败、禁用和技术实现不要求产品经理提供。缺失关键输入不得用猜测替代；完成验收时分别检查产品经理输入已被正确接入、Agent 负责的行为已实现，以及 Agent 不负责的内容没有被擅自扩展。

## Out of Scope

- 重做或扩展 v1.4 AI 产品经理入职体验。
- 为每个产品迭代创建独立文件树、复制旧成果或设计“继承 / 派生”关系。
- 由系统判断哪些历史理由会影响当前行动，或自动替用户决定继承、认可、批判、修改哪份文件。
- 在用户未加载文件时自动读取全部文件正文，或把完整变更时间线、历史聊天和完整项目设计史自动注入 Agent。
- 在 Markdown 正文中继续维护 changelog、版本号、来源迭代或写入记录。
- Git 式完整版本控制，包括保存全部历史正文、任意修订浏览与切换、重做、分支、合并和冲突解决。
- 基于旧基线覆盖时的额外过期警告、自动阻止或系统替用户选择较新内容；用户确认的最后一次写入直接生效。
- 文件删除后的恢复；删除只保留轻量来源占位，不保留可恢复的完整正文历史。
- 允许用户自定义树枝、把文件移动到其他树枝，或创建第五种项目文件分类。
- 一个产品迭代拥有多套任务拆分文件夹、恢复 `issues/vN` 版本目录、部分确认任务集合，或把任务文件夹转交给其他产品迭代。
- 在没有当前产品迭代时修改项目文件，或允许其他产品迭代绕过任务文件夹所属权。
- 把工作文档、概念版或未确认候选自动保存为项目文件。
- 迁移、保留、回填或兼容 v1.41 之前的数据库内容。
- 将产品内逻辑文件树同步为用户本地代码仓库、提供 Git 集成或在产品内执行外部 vibe coding。
- 在 spec 中提前规定 open-design 尚未产出的像素值、视觉 token、组件树或具体动效参数。
- 把本轮主观视觉评审扩大为 implement Agent 负责招募或组织真实用户测试。

## Further Notes

- v1.41 的核心不是给现有四个页面换皮，而是把“项目资产、产品迭代、四环阶段、阶段会话、上下文文件”五个概念重新排清楚，再用视觉层级让关系可见。
- 用户选择加载哪些文件，已经足以表达本轮需要哪些事实；是否继承、批判或改写旧方案仍由用户在对话中说明，不创建额外的继承模型。
- 一次撤回只解决最近一次误操作，不承诺完整历史恢复。文件变更时间线解决“发生过什么、由谁、在哪次迭代发生”，不承担保存所有旧正文的职责。
- `to-tickets` 负责把行为 spec 拆成可独立验收的纵向票据；每张票再列出产品经理需要决定或提供的关键主流程、视觉区域、文案和特殊行为。HTML 或粗线框是可选的视觉与交互输入，spec 是行为事实源；二者在关键决策处冲突时不应让实现 Agent 猜测。产品经理不必在拆票前完成所有原型，也不需要提供数据库、API、组件、system prompt、事务或测试脚本；普通状态由 Agent 按已确认方向补齐。
- v1.41 暂以产品作者的主观评审和确定性回放验收，不要求本轮 implement Agent 承担真实用户测试；用户可在版本可用后自行邀请真实用户体验。
- 本 spec 只记录旧数据无需兼容这一实施前提，不执行数据库清空，也不创建实现 tickets。
