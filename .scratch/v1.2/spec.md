# PM Assistant v1.2 — Spec

Status: ready-for-agent

> 本文件顶部的 `Status` 是仓库内部 spec 的 triage 元数据，不是任务拆分 Agent 输出给外部编程 AI 的 ticket 字段。任务拆分产物不包含 `Status` 或 `Implementation`。

## Problem Statement

PM Assistant v1.0/v1.1 已经能把求职 PM 的模糊想法推进到需求分析、原型、PRD 和 tickets，但交付链路在边界条件下仍不够可预测：

1. Agent 输出的 Markdown、代码围栏和链接可能影响页面结构或执行危险协议。
2. 范围冻结依赖自然语言肯定词，否定句、引用文本或历史消息可能被误判为确认。
3. 删除项目或工作记录时，关联的工作记录、标签页、消息、文件上下文和项目文件可能留下残留。
4. 删除或写入中途失败时，用户无法判断数据是否已经部分改变，也没有稳定的重试语义。
5. 重生成、编辑重发、停止生成和零 token 失败可能造成旧消息丢失、重复气泡或刷新后状态不一致。
6. 多窗口或重复请求可能同时修改同一个标签页，造成覆盖和重复写入。
7. 同一用户的不同项目之间存在文件越权读取、加载、修改和删除的风险。
8. 文件写入协议过宽，任意文件名、扩展名和路径会污染文件树或绕过不同文件的写入语义。
9. 原型 Agent 生成的 HTML 预览需要可回看，但不能成为普通文件树或 Agent 上下文的噪声来源。
10. 任务拆分后的 tickets 可能已经交给外部编程 AI；重新切分时不能静默覆盖用户手上的旧交付物。
11. v1.2 需要一套固定回放优先的验证入口，能证明安全、数据一致性、并发和版本交付行为，而不是只证明某次模型回答看起来正确。

## Solution

v1.2 将 PM Assistant 的核心交付链路收敛为“明确意图、可恢复操作、项目级隔离、可追溯交付”：

- 冻结只能由明确的界面操作触发，采用“冻结处理中 → 文档生成 → 写入确认后正式冻结”的两阶段流程。
- 删除采用物理级联；支持事务时使用事务，不支持时使用幂等补偿清理，只有确认全部目标数据清理后才报告成功。
- 生成开始时建立唯一的服务端 assistant 消息，所有完成、失败、中断和刷新恢复都围绕这条消息对账。
- tab 级并发采用版本号与幂等键组合；冲突直接提示“此标签页正在被其他窗口修改”，由用户手动决定。
- 所有项目文件 API 校验父级项目 ownership；文件写入使用根文件白名单、受控中间文件和 `issues/NN-<slug>.md` 路径规则，单文件上限为 3 MiB。
- Markdown 渲染只允许 `http`、`https`、`mailto` 链接协议，并清洗属性注入和不安全的代码围栏语言名。
- HTML 快照作为项目范围的原型资产保存多个版本；可以存在于项目存储，但不显示在普通文件树，也不能加载进 Agent 上下文。
- 任务拆分 Agent 输出稳定的外部交付契约：`What to build`、`Blocked by`、验收标准和必要 PRD 引用；不输出 `Status` 或 `Implementation`。重新切分先生成新结果，用户选择替换当前 tickets 或另存到 `issues/vN/`；编号最大的版本自动视为当前版本。
- 以现有综合回放入口为先例，建立 v1.2 的 replay 优先综合验证和专项覆盖矩阵；真实模型只在确需验证 prompt 理解时进行经批准的有限冒烟。

## User Stories

### 安全输入与 Markdown 展示

1. 作为一名求职 PM，我想在聊天中看到 Agent 输出的普通链接，以便正常打开资料和参考文档。
2. 作为一名求职 PM，我想危险链接协议不被执行或伪装成可点击链接，以便 Agent 输出不能劫持页面或执行脚本。
3. 作为一名求职 PM，我想包含引号、属性片段或恶意 HTML 的 Markdown 仍以安全文本展示，以便错误或恶意输出不会破坏聊天布局。
4. 作为一名求职 PM，我想代码围栏的语言名只影响安全的样式标记，以便不安全字符串不会注入页面属性。
5. 作为一名求职 PM，我想安全清洗不改变普通 Markdown 的可读性，以便安全措施不会让正常 PRD 和 ticket 难以阅读。

### 范围冻结与明确确认

6. 作为一名求职 PM，我想 Agent 提议冻结时看到明确的确认控件，以便知道这是一个需要我主动批准的流程动作。
7. 作为一名求职 PM，我想普通聊天文字、肯定词、否定句、引用文本和历史消息都不能触发冻结，以便聊天内容不会被误当成不可逆操作。
8. 作为一名求职 PM，我想点击确认后看到“冻结处理中”，以便知道系统已经接受操作但文档仍在生成。
9. 作为一名求职 PM，我想冻结处理中不能因为重复点击而重复生成或重复写入，以便网络重试不会产生多个版本。
10. 作为一名求职 PM，我想文档生成完成后再次看到文件写入确认，以便把“同意冻结”和“把文档写入项目”作为两个可理解的动作。
11. 作为一名求职 PM，我想在写入确认前取消，不让文档成为正式冻结结果，以便我可以在最后一步止损。
12. 作为一名求职 PM，我想文档生成失败时保留失败提示并可以重试，不让范围被错误标记为正式冻结。
13. 作为一名求职 PM，我想刷新或重新连接后仍能看到冻结处理中、生成失败和已正式冻结等真实状态，以便不会因为页面状态丢失而重复操作。

### 项目与工作记录删除

14. 作为一名用户，我想删除项目时同时清理该项目的工作记录、标签页、消息、文件上下文和项目文件，以便不会留下不可见的残留数据。
15. 作为一名用户，我想删除工作记录时同时清理其标签页、消息和文件上下文，但保留项目级文件，以便删除范围符合工作记录的 ownership 边界。
16. 作为一名用户，我想删除操作成功时系统确认所有目标数据都已清理，以便我可以相信删除不是半完成状态。
17. 作为一名用户，我想删除操作中途失败时得到明确的失败结果，而不是成功提示，以便知道还需要重试或等待补偿。
18. 作为一名用户，我想对失败的删除重复请求不会产生额外副作用，以便补偿清理可以安全重试。
19. 作为一名用户，我想删除后再次访问原资源得到一致的不存在结果，以便无法通过旧链接继续读取被删除的数据。

### 生成、重生成与消息恢复

20. 作为一名用户，我想开始生成时就有一条正式的 assistant 消息，以便停止、失败、刷新和重连都能引用同一个服务端 ID。
21. 作为一名用户，我想看到消息处于生成中、完成、中断或失败等明确状态，以便知道当前结果是否可继续使用。
22. 作为一名用户，我想模型一个 token 都没有生成就失败时仍保留一条失败状态的空 assistant 消息，以便历史记录完整且可以重试。
23. 作为一名用户，我想重生成先得到新结果，成功后再替换旧 assistant 消息，以便生成失败不会丢失原回答。
24. 作为一名用户，我想重生成失败时旧回答仍在，并看到失败状态，以便可以基于旧回答继续工作或再次重试。
25. 作为一名用户，我想取消重生成时保留已经生成的部分并标记中断，以便已经产生的内容不会被静默丢弃。
26. 作为一名用户，我想编辑一条用户消息并重新发送时，只在新结果准备好后替换后续历史，以便编辑失败不会破坏原对话。
27. 作为一名用户，我想刷新或重连后每条 assistant 结果只显示一次，以便服务端消息和前端流式状态不会形成双气泡。
28. 作为一名用户，我想停止生成后看到服务端正式消息，而不是只看到一个前端临时消息，以便后续删除、重试和上下文加载都基于真实记录。
29. 作为一名用户，我想失败、取消和重试的状态可区分，以便决定是继续使用、删除还是重新生成。

### tab 并发与工作记录命名

30. 作为一名用户，我想同一个 tab 的重复请求不会重复发送、重复写入或重复推进冻结，以便网络重试不会改变业务结果。
31. 作为一名用户，我想多个窗口同时修改同一个 tab 时收到“此标签页正在被其他窗口修改”的提示，以便由我决定保留哪个窗口的结果。
32. 作为一名用户，我想并发冲突不会静默覆盖另一窗口已经完成的消息、文件或冻结状态，以便重要成果不会无提示丢失。
33. 作为一名用户，我想自动命名只在工作记录仍为“未命名”时生效，以便不会覆盖我在等待期间手动设置的名称。
34. 作为一名用户，我想多个 tab 同时触发自动命名时只有符合最新条件的更新成功，以便名称不会被旧请求覆盖。

### 项目隔离与文件 API

35. 作为一名用户，我想只能把当前项目的文件加载进当前项目的 tab，以便不同项目之间不会串入上下文。
36. 作为一名用户，我想已有的跨项目上下文残留会被拒绝或清理，以便历史脏数据不能绕过新的隔离规则。
37. 作为一名用户，我想通过项目 A 的文件 URL 不能读取、修改、下载或润色项目 B 的文件，以便所有文件操作都遵守父级项目 ownership。
38. 作为一名用户，我想非法 fileId 得到明确的参数错误，合法但不存在的 fileId 得到不存在错误，以便区分输入错误和资源缺失。
39. 作为一名用户，我想项目文件写入只接受允许的 Agent 类型、文件名、扩展名和路径，以便文件树不会被任意输出污染。
40. 作为一名用户，我想中间文件可以被系统保存以便排查或回看，但不能进入 Agent 上下文，以便中间产物不会被当成正式事实来源。
41. 作为一名用户，我想单文件超过 3 MiB 时写入被拒绝并得到明确提示，以便系统不会被异常大输出拖垮。
42. 作为一名用户，我想原型 Agent 生成的多个 HTML 快照能在项目范围内回看，但不会出现在普通文件树或被其他 Agent 加载，以便预览媒介和正式交付物保持分离。

### 任务拆分交付与版本

43. 作为一名求职 PM，我想任务拆分 Agent 输出的每张 ticket 都描述完整的用户行为、真实阻塞依赖和验收标准，以便直接交给外部编程 AI 实现。
44. 作为一名求职 PM，我想 ticket 引用 PRD 章节而不是复制完整规则，以便 PRD 仍是业务决策的单一事实来源。
45. 作为一名求职 PM，我想 ticket 不包含 `Status` 或 `Implementation`，以便交付物只包含外部编程 AI 真正需要的实现契约，不伪装成我们没有提供的 issue tracker。
46. 作为一名求职 PM，我想重新切分时先看到新结果，再选择替换当前 tickets 或另存新版本，以便旧交付物不会被静默修改。
47. 作为一名求职 PM，我想选择替换时当前 tickets 作为一个整体被更新，以便文件树不会留下同一套任务的新旧混合状态。
48. 作为一名求职 PM，我想选择另存时新 tickets 写入 `issues/vN/` 子目录并保留旧版本，以便可以回看或继续使用之前交给外部 AI 的版本。
49. 作为一名求职 PM，我想系统自动把版本号最大的 `issues/vN/` 视为当前版本，以便不需要额外维护一个容易忘记更新的“当前版本”标记。
50. 作为一名求职 PM，我想下载或选择 tickets 时能按完整版本目录操作，以便不会把不同版本的 ticket 混在一起交给外部编程 AI。

### 验证与可维护性

51. 作为一名维护者，我想用固定回放验证安全、冻结、文件、消息和数据库外部行为，以便日常回归不依赖真实模型和 API 成本。
52. 作为一名维护者，我想专项脚本失败时能定位到安全、生命周期、消息一致性、并发隔离或交付版本中的具体类别，以便综合入口负责发现、专项入口负责诊断。
53. 作为一名维护者，我想综合入口在运行前确认服务端处于 `AI_MODE=replay`，以便不会误调用真实模型。
54. 作为一名维护者，我想真实模型验证只检查 prompt 和模型行为，并且在运行前说明假设、轮数和成本，以便不会用昂贵的真实回归替代协议测试。
55. 作为一名维护者，我想 triage 状态、实现完成状态和验证结果各自表达单独事实，以便内部 issue 管理不会污染交给外部 AI 的 tickets。

## Implementation Decisions

- **Markdown 安全边界**：渲染层对链接协议采用 `http`、`https`、`mailto` 白名单；危险协议降级为不可执行文本。属性值、引号、HTML 注入片段和代码围栏语言名必须经过安全编码或限制为安全 token。测试关注用户看到的链接和页面结构，不依赖具体 parser 实现。
- **冻结协议**：自然语言（包括肯定词、否定句和历史消息）不再参与冻结判定。Agent 提议冻结时产生明确的用户操作控件；用户确认后进入“冻结处理中”，服务端以幂等请求推进文档生成；生成完成后再次触发文件写入确认，只有写入确认成功后才把流程标记为正式冻结。生成失败、用户取消和重复点击都不能提前正式冻结。
- **删除语义**：项目删除级联 `WorkRecord`、`Tab`、`Message`、`AgentFileContext`、`ProjectFile`；工作记录删除级联 `Tab`、`Message`、`AgentFileContext`。部署支持事务时使用事务；不支持时使用可重入的补偿清理。只有所有目标集合确认清理后才返回成功，失败结果必须可安全重试。
- **消息状态事实源**：生成开始时服务端预创建 assistant 消息并返回正式 ID。消息至少区分生成中、完成、中断和失败；零 token 失败也持久化失败状态的空 assistant 消息。前端停止、刷新和重连通过服务端 ID 对账，不创建没有服务端 ID 的替代事实源。
- **先生成后替换**：重生成和编辑重发先在独立生成上下文中获得结果；成功后一次性替换旧 assistant 或旧消息之后的历史。失败保留旧历史并显示失败状态；取消保留已生成部分并标记中断；重试使用明确的新请求标识，不重复提交旧请求。
- **tab 并发**：所有会改变 tab 事实的操作使用版本号进行乐观并发检查，并使用幂等键吸收网络重试。版本冲突返回可识别的冲突结果，产品提示“此标签页正在被其他窗口修改”，由用户手动决定，不自动合并或静默覆盖。
- **工作记录命名**：自动命名使用条件更新，只能在名称仍为“未命名”时成功；用户手动命名后，旧的自动命名请求不得覆盖新名称。
- **项目 ownership**：tab、文件上下文、项目文件及其所有读写路由都同时校验当前用户和父级项目关系。跨项目残留上下文在读取时过滤，在写入或维护时按幂等清理处理。非法 ObjectId 作为参数错误，合法但不存在作为资源不存在。
- **文件写入协议**：允许的根文件使用白名单；任务拆分 ticket 使用 `issues/NN-<slug>.md` 路径，并为版本目录支持 `issues/vN/NN-<slug>.md`；中间文件可以持久化但不可加载进 Agent 上下文；单文件上限 3 MiB；拒绝非法扩展名、路径段、控制字符和不受支持的 Agent 类型。具体合法根文件清单沿用项目现有正式交付物约定。
- **HTML 快照**：HTML 预览作为项目范围的原型快照资产保存，可有多个版本；即使底层以 `.html` 形式存在，也不出现在普通文件树，不进入 Agent 上下文，也不能被当成 `原型.md` 的单一事实来源。正式交付仍是结构化的 `原型.md`。
- **任务拆分交付**：任务拆分 Agent 借鉴 `/to-tickets` 的垂直切片、blocking edges、expand-contract 和先草案后确认流程，但只输出外部编程 AI 需要的稳定契约：`What to build`、`Blocked by`、验收标准和必要 PRD 引用。不输出 `Status` 或 `Implementation`，也不提供 matt 的实现生命周期。
- **任务重新切分**：已存在 tickets 时，Agent 先生成新切分结果，不直接覆盖。用户选择“替换现有 tickets”时更新当前整套；选择“另存新版本”时写入 `issues/vN/`，保留旧版本。版本号最大的目录自动视为当前版本；新旧版本作为完整目录选择和下载，不混合为一套交付物。
- **验证架构**：以现有综合回放入口为先例，建立 v1.2 综合回放入口，由专项脚本覆盖安全协议、删除级联、消息恢复、tab 并发、项目隔离、文件协议和 tickets 版本。综合入口只依据专项退出码汇总，不复制业务断言。

## Testing Decisions

- **最高测试 seam**：使用 Playwright 驱动的端到端用户流程，结合同一用户会话下的 API 数据断言；以综合回放入口作为发布候选和回归入口，专项脚本负责定位类别。
- **外部行为标准**：只断言用户可见状态、HTTP/SSE 结果、消息列表、文件列表和数据库可观察数据；不测试组件内部 state、函数签名或具体锁实现。
- **固定回放优先**：默认 `AI_MODE=replay`，固定模型回复用于验证 marker、按钮、弹窗、状态、文件写入、版本目录、隔离和删除结果；不得未经批准调用 `AI_MODE=live`。
- **专项覆盖矩阵**：至少覆盖 Markdown 恶意 URL/属性/代码围栏、冻结否定句与历史消息、冻结两阶段失败恢复、项目和工作记录级联删除及补偿、重生成/编辑重发/停止生成的失败刷新重连、tab 版本冲突与幂等重试、自动命名竞态、跨项目文件加载和文件 API、文件名/Agent 类型/大小边界、消息 A/B 同名文件来源、快速关闭 tab、任务重新切分替换与 `issues/vN/` 版本选择。
- **数据断言**：删除测试必须检查所有关联集合；消息测试必须检查服务端 ID 唯一性和零 token 失败空消息；文件测试必须检查项目 ownership、隐藏中间文件不可加载和版本目录的当前版本判定。
- **真实模型边界**：只在需要确认 prompt 遵循或模型理解时安排一次有限 live 冒烟；运行前说明假设、对话轮数和 token/API 成本，并取得用户同意。真实模型不重复覆盖 UI、协议、SSE、文件写入或数据库断言。
- **验证报告**：综合入口输出专项通过/失败数量和类别；专项入口保留具体断言。`ready-for-agent`、实现完成和验证通过是不同事实，不能互相替代。
