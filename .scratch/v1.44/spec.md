# v1.44：首发账号、积分与最小运营后台

Status: ready-for-agent
版本：v1.44
日期：2026-11-02
来源：本次 v1.44 grilling 已确认的产品决策，以及当前代码与领域文档核查。

## 问题陈述

网站已上线，v1.43 视觉迭代已经收尾，但在宣传和真实使用前，用户仍缺少可靠的邮箱验证、可解释的模型计费、赠送额度领取渠道和积分获取方式。运营者无法在网站内集中查看用户使用、模型成本、故障和积分变化，也无法以有记录、可追溯的方式处理极少量人工充值与退款。

当前注册邀请码是注册准入条件，不能满足“不限制正常注册，通过一次性邀请码赠送积分”的营销方式。当前模型封装主要提供文本和流式内容，既有每日请求次数限制不能代替按真实人民币成本计量的积分账本。旧版自动命名仍会调用模型，需要改成本地截取首条提示词。

本版要让用户完成验证注册、兑换赠送积分、使用已有四环工作台并清楚理解余额变化；让运营者用一个简洁后台处理试用与人工收款；让 v1.43 与 v1.44 的成果可靠更新到现有生产环境。

## 解决方案

1. 使用邮箱、密码和注册邮箱验证码建号，提供邮箱验证码重置密码；普通登录不逐次验证邮箱，异常请求通过限流处理。
2. 开放正常注册，新账号初始积分为零。首批提供 100 个一次性赠送邀请码，每码赠送 2000 积分，每个账号只能成功领取一次；注册时或个人中心均可兑换，成功后自动到账。
3. 首发继续使用 DeepSeek 官方 Flash。正常模型消耗按供应商实际人民币成本 × 2000 计算积分，充值 1 元获得 1000 购买积分；赠送积分优先消耗，余额和来源分别可查。
4. 调用前预留积分，完成后按可靠用量结算；工作台展示账号可用积分与冻结积分，回复和润色结果附近展示单次状态与消耗。
5. 首发采用人工充值：用户先通过页面联系方式与运营者确认，再私聊转账，运营者核验后在后台发放购买积分。邀请码兑换保持自动处理。
6. 提供最小运营后台，覆盖用户、使用情况、供应商成本与故障、邀请码、积分调整、人工充值及退款；不加入服务器监控或装饰性动效。
7. 保留现有账号、项目和资料，将 v1.43 视觉成果与本版功能一起更新到现有生产服务器，并完成发布所需验证与备份保护。

## 实现决策

### 1. 沿用现有产品与架构

- 沿用现有 Next.js、MySQL、邮箱密码认证、四环产品迭代、阶段会话、项目文件树与手动上下文模型，不引入换库或新平台迁移。
- 保持现有文件写入确认、上下文读取授权、内容修订、来源追溯及账号数据隔离规则。本版仅为新增账号、积分和运营能力建立必要接口。
- 新增模块集中为邮箱验证与找回、积分账本与结算、供应商用量计量、赠送邀请码、人工充值退款和管理员运营入口。所有真实模型入口接入同一套计量与账本能力，避免分别实现扣费规则。
- 本文描述目标行为；现有代码尚未完成这些能力。不得因原功能已有类似命名，就认定其已满足本版要求。

### 2. 邮箱验证、注册与密码找回

- 注册使用邮箱、密码和 6 位数字验证码；验证码 10 分钟有效，60 秒后可重发。沿用现有邮箱规范化和密码安全存储能力。
- 验证码限定邮箱和用途，成功使用后失效；重发后的有效性规则保持单一、明确，旧码不得被用于绕过验证。失败次数、发送频率和异常请求由服务端限流。
- 仅在邮箱验证成功后创建正常可用的新账号；重复提交不得产生重复账号。密码找回以同类邮箱验证能力完成，找回码不能用于注册或其他邮箱。
- 正常登录不逐次索取验证码；本版不加入手机验证或常驻人机验证。
- 新账号不要求赠送邀请码，默认零积分；注册数量不设产品配额，正常的重复邮箱约束和安全限流继续适用。
- 邮件发送与校验失败必须给出可操作反馈；未配置或发送失败不能假装投递成功，也不能在生产响应或日志中泄露验证码。测试邮件替身仅限隔离测试配置。
- 事务邮件供应商、发信身份、必要凭据和域名设置在实施时核实；本规格不假定它们已经开通，也不将邮件成本归入模型预算。

### 3. 赠送邀请码

- 原注册准入口令退出正常注册条件，赠送邀请码只负责领取积分。
- 首批 100 个独立一次性码，每码自动赠送 2000 积分；每码最多成功领取一次，每账号最多成功领取一次。暂不设置邀请码或积分自动到期。
- 注册时可选兑换，个人中心也可兑换；账号身份成立后由服务端原子完成资格检查、码领取、赠送积分入账和领取记录。
- 同码抢领、同账号同时提交多个码、超时重试只能产生一笔有效赠送。成功后隐藏个人中心兑换入口；失败不消耗账号资格，也不误标记邀请码已领取。
- 注册中的邀请码无效、已用或兑换失败不回滚已经合法完成的注册；告知未获赠送并允许登录后重试。若实际上已到账但响应丢失，重试应返回可核对的已有成功结果，不再次赠送。
- 管理员可查看码状态、领取账号和时间，作废未使用码；作废不能撤销已经发放的积分。

### 4. 积分来源、价格与精度

- API 实际成本是供应商费用，用户积分标价与之分开：正常消耗积分 = 本次 API 实际人民币成本 × 2000；充值 1 元 = 1000 购买积分。
- 赠送积分与购买积分分别记账、分别可见；消耗先使用未被其他调用占用的赠送积分，再使用购买积分。
- 使用可确定重算的金额与积分精度，避免浮点误差累计；允许小数积分，不逐笔向上取整成 1 积分。显示精度不得改变账本真实金额或导致余额与明细相互矛盾。
- 价格计算区分供应商实际支持并适用的输入、输出、缓存等计费项目；按本次请求适用的规则保存可追溯价格依据，不把估计量当成已确认成本。
- 不在规格中固定未经生产核实的供应商单价、并发额度或余额。官方 Flash 的实际模型标识、价格、用量字段和计费口径在实施时验证。

### 5. 计量范围与本地命名

- 真实模型调用必须进入计量，包括四环对话、文件润色以及实施核查发现的其他真实模型入口；按后文的完成、停止、故障和待核对规则确定是否最终扣分。
- 润色已经完成模型生成，即使用户不应用结果，也按正常用量结算；手工编辑和保存本身不计模型费用。
- 不调用模型的项目、迭代、会话、文件浏览、编辑、下载、上下文管理、人工改名和后台管理不扣积分。公共入职体验中不调用模型的预编排内容继续免费。
- 取消旧的模型自动命名。默认会话名直接取首条用户提示词前 10 个字符，不足 10 个取全部；标点和空格均按原文计入，不先 trim、不清洗、不总结。字符截取不得破坏正常 Unicode 字符。
- 用户手动命名不被默认命名覆盖；后续提示词不反复改写已确定名称。移除旧的隐藏命名模型调用，不把内部旧“工作记录”命名误传播为新的产品术语。

### 6. 预留、结算与账号并发

- 真实上游请求发出前，先在服务端取得账号授权并原子预留可支撑本次调用的积分。预留成功之前不能开始产生供应商费用。
- 预留依据为完整输入的保守费用，加本次允许的最大输出费用，再按人民币成本 × 2000 转换。完整输入包括系统提示词、实际发送的历史和注入文件；无法确认的缓存命中不作为减少预留的依据。
- 输入计量使用可靠方法或经验证的保守边界，不能把简单字符换算冒充精确 token 数或已证明的成本上界。输出预算须受真实发给供应商的限制约束，覆盖适用的计费项目。
- 按操作类型设置合理输出预算，减少过量冻结；不得为降低预留而静默截短长文生成。若实测不能建立足够可靠的预算边界，须记录限制并修正方案，不得宣称已能严格防止透支。
- 可用积分不包含已预留额度；工作台冻结积分为账号全部未结算预留的合计，包含正在生成和待核对的调用。用户切换会话或设备后仍基于同一份服务端余额。
- 不同会话可以并行；同一会话同时只允许一个生成任务。新增调用余额不足时不访问供应商，保留输入并引导补充积分，不取消已获预留的调用。
- 每轮 AI 回复生成结束即按可靠用量结算，不等待会话关闭；从预留中扣掉实际消耗，只释放未用部分。购买、赠送两类预留与消耗关系必须可核对。
- 防止重复提交、网络重发、结算重试、并发页面以及进程重启导致同一操作重复执行、重复扣费、额度负数或预留遗失。
- 调用、预留、结算和恢复状态持久化；不得只保存在应用内存。账本和调用状态在事务边界内保持一致，长时间模型请求不占用数据库长事务。

### 7. 完成、停止、故障与待核对

| 结果 | 用户积分处理 | 供应商成本与记录 |
| --- | --- | --- |
| 正常完成且用量可靠 | 按实际成本扣分，释放未用预留 | 记录实际用量、价格依据和成本 |
| 用户主动停止且用量可靠 | 按已发生用量扣分，释放未用预留 | 保存停止状态及可靠计量 |
| 网站或供应商故障导致生成失败 | 首版免单并释放预留 | 已发生的供应商成本由网站承担，不能因用户免单而抹除 |
| 尚未取得可靠用量且未明确故障免单 | 不正式扣分，保留该笔预留并显示待核对 | 区分待确认成本与已确认成本，继续核对 |
| 待核对在 24 小时内取得可靠用量 | 自动按适用规则结算并释放剩余 | 保留核对与结算记录 |
| 进入待核对超过 24 小时仍未核实 | 免单、释放预留，此后不再补扣 | 网站承担相关成本，结束用户侧待核对 |

- 不能根据生成文本长度、用户看到的片段或估计 token 数直接补扣积分。
- 待核对的 24 小时从进入待核对状态计算，不依赖用户保持页面打开。处理机制必须能在生产进程重启后恢复，达到期限后可自动完成免单和释放。
- 已明确故障免单的调用不等待核对期限才释放；之后取得成本只补充网站成本记录，不追扣用户。
- 优先验证官方流式与非流式用量获取方式、主动停止和断流时的可恢复计量能力。未经验证，不能假定供应商一定能事后查询某次请求用量。

### 8. 个人中心与工作台反馈

- 个人中心提供账号 ID、可用及冻结状态、赠送/购买两类余额、邀请码兑换、联系充值和分页积分明细。
- 流水区分充值、赠送、消耗、退款、补偿及待核对状态，能定位相关项目或会话；余额和明细来自同一套账本。
- 四环工作台实时更新账号可用积分与冻结积分，页面刷新后恢复正确状态；可采用适合现有服务的同步方式，不要求持续高频刷新。
- 每条 AI 回复附近及文件润色结果区域显示本次预留、实际消耗或待核对/免单状态，单位明确为积分。正常生成不增加逐次确认弹窗。
- 本次费用展示与账号冻结总额分开表述；用户不应把其他会话的预留误认成本次费用。

### 9. 人工充值与退款

- 获取积分或联系充值页面明确早期试用及人工处理，展示运营者微信联系方式与当前账号 ID，说明先联系确认金额、积分和预计处理时间，再转账。
- 页面不承诺全天候处理或自动即时到账；不搭建在线收款、自动回调或支付订单平台。
- 管理员核验实际到账后，向明确账号添加购买积分，记录实收人民币、发放积分、交易参考号、操作者和时间。同一笔转账重复提交或重复操作不得重复到账。
- 购买积分发放遵循 1 元 1000 积分；赠送或补偿应以对应账本类型记录，不能伪装成实收购买。
- 退款仅针对未消费、未被调用预留的购买积分，金额不超过对应实付与可退部分；赠送积分不折现。
- 人工退款记录关联原充值及对应购买积分扣减，防止重复退款。外部转账失败或后台写入失败应保留可追查状态，不能静默出现钱已退、积分仍可使用或反向重复操作。

### 10. 最小运营后台与权限

- 仅指定管理员可访问页面和管理接口；服务端逐项校验身份与权限，不能依赖前端隐藏入口。
- 用户管理支持查询账号、状态、余额和使用概况，停用异常账号；已存在的登录会话也不能绕过停用限制继续新增模型请求。
- 提供简洁汇总、筛选和分页：用户与使用情况、模型请求及故障、已确认成本与待核对成本、邀请码及领取记录、积分流水、人工充值退款。
- 人工补偿、纠正余额、充值和退款记录操作者、原因或业务说明、时间及前后余额；不能无痕编辑历史消耗。
- 默认不提供任意浏览用户对话或文件正文的后台入口。定位故障以调用标识、状态、用量和必要元数据为主，不将正文与凭据作为普通运营日志。
- 管理员正常使用产品也走积分检查和结算；可通过有记录的后台操作给自己添加测试赠送积分。后台管理本身不扣分。
- 不显示服务器状态；服务器管理沿用云平台。无需装饰性动效、复杂分析系统或高频轮询。

### 11. 持久数据与接口契约

- 在现有 MySQL 上做增量升级，保留现有账号与业务资料。必要新增持久对象包括：用途隔离的邮箱验证凭证、账号管理状态、赠送与购买积分余额、预留及积分流水、模型调用与用量/价格依据、待核对处理状态、赠送邀请码及领取、人工充值退款及管理操作记录。
- 对外区分验证失败、限流、余额不足、同会话正在生成、无权限、已处理和供应商故障；错误提示支持用户修正或安全重试，不泄露其他账号信息。
- 创建账号、领取赠送、预留、结算、退款等接口应具有明确的重复提交语义，不能把超时后的未知结果一律当失败后重新执行。
- 保持既有会话正文、文件树、迭代状态与来源数据兼容；删除业务对象不能令资金流水和审计记录失去必要的追溯快照。
- 现有每日调用次数控制不能替代金额账本；实施时核查其配置及文案与新积分规则的关系，避免旧的试用限制被误认为余额不足或计费结算。

### 12. 成本与生产发布

- 200 元为本轮开发验证至首批试用的累计模型 API 成本预算，不按月重置；服务器、域名和邮件费用单列。后台记录实际成本，不能用用户积分标价推算网站成本。
- 运营者自行维持官方供应商预充值余额并定期查看；本版不实现供应商自动充值或复杂资金管理。
- 现有账号均需保留，不强制已有账号重新注册，也不以本版名义清空项目或资料。旧账号字段按实际情况最小迁移，不虚构其已经完成邮箱验证。
- 将 v1.43 视觉成果和本版功能纳入明确的已提交发布版本，核实远端与目标服务器的真实提交和生效配置；不得将全部工作区改动不加筛选地打包发布。
- 更新或迁移前保存现有可用代码、运行配置与数据库，按项目部署纪律完成服务器之外的安全副本和必要的隔离恢复验证。
- 部署时核实官方模型标识、live 模式、邮箱投递、管理员配置、后台处理机制和真实持久化；不输出密钥，不将生产切到测试邮件或伪用量模式。
- 失败时保护已发生的积分与转账记录，不能通过还原旧数据库丢弃发布后新增资金事实；数据库与代码回退方案必须兼容新增账本。
- 本规格的 ready-for-agent 表示可据此拆票，不代表代码、外部服务、生产迁移或发布已经完成。推送和生产操作继续遵守项目授权与部署纪律。

## 测试决策

### 1. 主要测试边界

以现有应用的浏览器与 HTTP/API 边界作为主要验证入口，通过真实应用服务和隔离 MySQL 验证用户可观察行为。测试不依赖组件内部状态、私有函数调用次数或数据库表名来判断功能正确。

仅在邮件投递和模型供应商这两个外部依赖边界提供可控替身，并提供受限的时间控制以验证验证码过期和 24 小时核对到期；不为每个模块分别暴露生产测试接口。测试替身与时间控制只在隔离测试环境生效，生产不得绕过验证、授权或真实计量。

该测试边界作为本规格的明确方案提交用户核对；不把测试方式已确认与产品规则已确认混为一谈。

### 2. 什么是有效测试

- 从用户或运营者操作开始，断言响应、页面状态、可再次使用的余额和最终持久结果，而非复刻实现公式或内部调用链。
- 对充值、邀请码、预留、扣费和退款使用独立已知输入与预期账单，验证资金守恒、唯一到账和不可重复结算。
- 并发测试从应用入口同时提交请求，验证同码、同账号、同会话和共享余额的最终行为；不通过逐个调用串行模拟并发。
- 故障测试覆盖请求前、供应商调用后、结算写入中和响应丢失等关键边界，验证重试与恢复后仍然只有一份资金结果。

### 3. 自动化覆盖范围

- 账号：正常注册登录、错误与过期验证码、重发间隔、用途隔离、重复注册、密码找回和限流；邀请码为空或失败不影响合法注册。
- 赠送：正常领取、已用或作废码、同码并发、同账号多码并发、重复请求、入账失败与恢复、入口隐藏及领取记录。
- 模型计费：正常完成、润色未应用、零余额拦截且未访问上游、完整输入与适用价格、缓存等用量分类、小数精度和本地命名零模型调用。
- 预留：赠送优先、混合余额、不同会话并行、同会话互斥、账号冻结合计、余额不足仅拦截新增调用、重复提交和进程重启后的状态恢复。
- 异常：可靠用量的主动停止、网站/供应商故障免单、用量缺失、核对成功自动结算、24 小时到期释放、到期后不追扣、明确故障立即释放及已知成本不丢失。
- 人工运营：管理员授权、普通用户越权与跨账号访问、停用账号已有会话限制、充值防重、购买积分退款边界、重复退款、调整原因与审计。
- 界面：工作台余额、单次消耗及润色状态、个人中心来源余额与流水、联系充值说明；覆盖桌面与窄屏，继承 v1.43 视觉与可访问性表现。
- 既有行为：只针对本版触及的登录、会话生成、文件润色及文件/上下文权限边界回归，确保现有四环、文件树与上下文规则不被账号或积分改造破坏。

### 4. 现有测试先例与复用

- 复用现有个人主页账号验证的浏览器登录、改密与账号隔离模式。
- 复用现有隔离 MySQL/replay 运行器、故障场景和发布闸的独立证据保存方式，测试数据不混入日常账号或生产账本。
- 复用现有长生成与停止验证中的流式响应、心跳、取消和错误反馈入口，新增用量与账本断言。
- 既有 replay 主要返回预编排文本，不能直接证明新增计量正确；测试替身需要显式提供可靠用量、缺失用量、错误和延迟场景。
- 调整受本版规则改变影响的自动命名与注册断言；不批量重跑无关的历史 LLM 对话脚本。

### 5. 真实外部核验与发布证据

- 在测试替身通过后，以少量实际邮箱收信核验注册与密码找回投递，以受控的小规模官方 API 调用核验实际模型、用量、流式结束、停止及成本口径。
- 记录真实用量与账本的对应关系，明确区分模拟结果、本机 live 和目标服务器结果。不能用 replay 或供应商估算代替生产真实证据。
- 遵守累计 200 元模型预算，优先低成本针对性请求；预计超过 10 分钟的 LLM 级验证按项目规则提前说明并取得同意。
- 本版涉及金额存储、并发和共享生成逻辑，实施按 L2 风险选择相关完整验证与相邻回归；编译、相关 lint、生产构建和必要的目标机发布核验须有结果。
- 测试不得向真实用户批量发送邮件、操作真实用户资金或以清库方式准备数据。
